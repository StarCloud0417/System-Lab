1要解決什麼問題

現在要看一個變數的值，你得做這些事：

1. 開 QEMU，加 -S 讓它凍住
2. 另一個視窗接上 GDB
3. 想清楚要在哪裡下斷點
4. continue，然後 p/x 那個變數

想知道「程式跑到哪一行了」也一樣 —— 先下斷點，再看它有沒有停。

有了 UART，這一切變成一行 uart_puts("到這裡了\n")。

這不只是方便。M5 要蓋分頁表、M7 要做 context switch，那些東西的中間狀態用斷點看不完 —— 你需要它一邊跑一邊告訴你發生什麼事。所以 M2 排在這個位置：它是後面每個里程碑的除錯基礎設施。

3MMIO：用寫記憶體的方式操作硬體

MMIO = memory-mapped I/O，記憶體對映輸入輸出。

周邊裝置（UART、計時器、中斷控制器）的控制暫存器，被硬體擺在記憶體位址空間裡。你用一般的 ldr／str 讀寫那些位址，就等於在對硬體下指令。

0x0900_0000   ← 這個位址不是 RAM，是 UART 的資料暫存器
              往這裡寫一個 byte = 送出一個字元

M1 的記憶體地圖你看過：0x0 到 0x4000_0000 那一整段都是 flash 和 MMIO，RAM 從 0x4000_0000 才開始。UART 就住在那一段裡。

位址從哪來

不是從資料手冊抄的，是問 QEMU 要的：

$ make dtb          讓 QEMU 吐出它自己的 device tree

pl011@9000000 {
    compatible = "arm,pl011", "arm,primecell";
    reg = <0x00 0x9000000 0x00 0x1000>;      ← 基底位址與大小
    clock-names = "uartclk", "apb_pclk";
    clocks = <0x8000 0x8000>;                ← 指向下面那個節點
};

apb-pclk {
    phandle = <0x8000>;
    clock-output-names = "clk24mhz";
    clock-frequency = <0x16e3600>;           ← 24,000,000 Hz
};

三個沒見過的欄位名：compatible 是「這個裝置是什麼型號」，作業系統靠它決定要用哪支驅動；reg 是「它的暫存器擺在哪、佔多大」；phandle 是節點的編號，讓別的節點可以指過來——上面 clocks = <0x8000> 指的就是下面 phandle = <0x8000> 那個時脈節點。

位址不是免費的：組一個要兩條指令

AArch64 的指令固定 32 位元，所以指令裡塞不下一個 64 位元的常數。編譯器一次搬 16 位：

mov  x0, #0x30              先放低 16 位   x0 = 0x0000_0000_0000_0030
movk x0, #0x900, lsl #16    再塞 bit16-31  x0 = 0x0000_0000_0900_0030

movk = move keep——只改指定的那 16 位，其他位元保留。（mov 會把整顆清掉再寫，所以只能用在第一次。）

所以 每一次 MMIO 存取，光是「產生位址」就花掉兩條指令。現在無所謂，M4 寫中斷處理常式時就會開始計較——那段程式碼每秒要跑幾千次。

PL011 是 ARM 設計的 UART 控制器型號。QEMU virt 和樹莓派 4 用的都是它 —— 這是 M9 移植時驅動能沿用的原因，只有位址不同。

為什麼非要 volatile 不可

編譯器看到「連續寫同一個位址三次」，會認為前兩次沒意義，只留最後一次。對 RAM 這是正確的優化。對 MMIO 是災難 —— 那三次是三個字元。

volatile 就是告訴編譯器：這個位址每一次存取都算數，不准合併、不准省略、不准換順序。

但它不會產生任何指令

這點很容易誤會。把 mmio_write32 的 volatile 拿掉，重編、比對那一條真正寫硬體的指令：

有 volatile   400000c8:  b9000001   str  w1, [x0]
無 volatile   400000c8:  b9000001   str  w1, [x0]
                         ↑ 連機器碼都一模一樣

volatile 不加指令，它禁止編譯器拿掉指令。

所以它的效果只在「有人想拿掉」的時候才看得見——-O0 下沒人要拿，兩邊自然相同；-O2 下有人要拿，那時才擋得住。第 8 節的直覺 2 就是那個場面。

但這件事現在證明不出來

本專案目前沒有加任何 -O 旗標，也就是 -O0。實測 -O0 下加不加 volatile，產出的組語逐位元組相同。

照鐵則五的字面判準（「拿掉它現在會壞嗎」），volatile 現在不會壞。

但把 -O0 換成 -O2，「拿掉 volatile」就會壞了——而且壞的方式非常漂亮，見第 8 節。

講清楚免得誤會：volatile 本身在 -O2 下是有效的，該保留的寫入一條都不會少。會壞的是「拿掉它」那一邊。-O0 看不出差別，只是因為那個等級的編譯器本來就不做這種優化。

所有 MMIO 都走同一個門

static inline void mmio_write32(uintptr_t addr, uint32_t value)
{
    *(volatile uint32_t *)addr = value;
}

專案禁止任何地方直接寫 *(volatile uint32_t *)addr = v。理由是忘記 volatile 不會有任何錯誤訊息 —— 它會安靜地少印字元。集中成兩個函式，就只剩一個地方可能寫錯。

4PL011 的六個暫存器

先講 FIFO

FIFO（first in, first out，先進先出）是一個小佇列。UART 送一個字元到線上要花時間（115200 bps 下約 87 微秒），如果軟體每送一個就得等它走完，CPU 大部分時間都在發呆。

所以硬體準備了一個 16 格的佇列：軟體把字元丟進去就走，硬體自己慢慢送。丟滿 16 個才需要等。

FR 裡的旗標就是在回報這個佇列的狀態：TXFF（transmit FIFO full）滿了、TXFE（empty）空了；RX 開頭的是接收那一側的同名旗標。

偏移名字做什麼
+0x00DRData Register。寫進去 = 送出一個字元
+0x18FRFlag Register。bit5 TXFF = 送出佇列滿了
+0x24IBRD鮑率除數的整數部
+0x28FBRD鮑率除數的小數部，單位 1/64
+0x2cLCR_HLine Control Register (High)。bit4 FEN = FIFO enable；bits[6:5] WLEN = 一個字元幾個 bit
+0x30CRControl Register。總開關
為什麼存取函式叫 mmio_write32——我們不是 64 位元嗎

因為「暫存器」這個詞在這裡指的是兩組完全不同的東西：

住在哪幾位元例子
CPU 的通用暫存器CPU 核心裡面64x0–x30、sp、pc
裝置的控制暫存器PL011 那顆晶片裡面32DR、FR、IBRD、CR

「AArch64 是 64 位元」講的是第一組——那個認知完全正確，x0 確實是 64 個 bit。

但 PL011 是掛在匯流排上的另一顆晶片，它裡面那些暫存器由它自己的設計決定，是 32 位元。兩組暫存器互不相干，只是名字都叫「暫存器」。

證據：一次讀 8 個 byte，讀到的是兩顆黏在一起

IBRD 在 0x09000024、FBRD 在 0x09000028，中間差 4。實測：

分開讀，一次 4 bytes：
  0x09000024 (IBRD) = 0xd
  0x09000028 (FBRD) = 0x1

從 0x09000024 一口氣讀 8 bytes：
  0x09000024        = 0x10000000d
                        ↑        ↑
                      FBRD     IBRD

那不是「一顆 64 位元暫存器」，是兩顆 32 位元的排在一起。 如果 PL011 的暫存器真的是 64 位元，IBRD 和 FBRD 就不會只差 4 個 byte。

所以函式簽章裡兩種寬度都在

void mmio_write32(uintptr_t addr, uint32_t value)
                   ↑ 64 位元        ↑ 32 位元
                   要 64 位元才裝    因為 PL011 的
                   得下 AArch64      控制暫存器就是
                   的位址            32 位元寬

位址是 64 位元，因為它指的是 AArch64 的位址空間。資料是 32 位元，因為那顆硬體暫存器就這麼寬。

寫錯寬度，編譯器不會攔你

兩種都是合法的 C，差別只在產生哪一條指令：

*(volatile uint64_t *)0x09000024 = 0xd;   →  str x1, [x0]   寫 8 bytes ❌
*(volatile uint32_t *)0x09000024 = 0xd;   →  str w1, [x0]   寫 4 bytes ✅

（x1 是 64 位元暫存器，w1 是同一顆的低 32 位元。）

上面那條會把 IBRD 和隔壁的 FBRD 一起蓋掉——鮑率的小數部被清成 0，而沒有任何錯誤訊息。

記憶體你想寫幾位元都行；MMIO 的寬度是硬體規定的。

M4 的中斷控制器確實有 64 位元的裝置暫存器，那時才會需要 mmio_write64——到那時再加。

開機時它們長什麼樣

用 GDB 在 uart_init() 執行之前讀：

CR    = 0x300     bit8 TXE=1、bit9 RXE=1，但 bit0 UARTEN = 0
IBRD  = 0x0       鮑率完全沒設
FBRD  = 0x0
LCR_H = 0x0       字元長度沒設
FR    = 0x90      bit7 TXFE（送出佇列空）=1、bit4 RXFE（接收佇列空）=1

UARTEN = 0，這台 UART 標示為「沒有啟用」。 記住這一點，第 8 節會用到。

5鮑率：一個除法拆成兩個暫存器

鮑率（baud rate）= 一秒送幾個 bit。兩端要講好，不然收到的是亂碼。

UART 拿到一個固定時脈，內部先除以 16，再除以我們給的除數：

divisor = 時脈 / (16 × 鮑率)
        = 24,000,000 / (16 × 115200)
        = 13.0208

13 太慢、14 太快。 所以硬體把除數拆成兩半，用「13 又 1/64」來逼近：

IBRD = 13                        整數部
FBRD = round(0.0208 × 64) = 1    小數部，單位 1/64

實際跑出來的鮑率是 24e6 / (16 × (13 + 1/64)) = 115246.1，誤差 +0.04%。UART 容許約 ±2%，很穩。

寫 LCR_H 才會「鎖上」鮑率

寫進 IBRD 和 FBRD 的值不會立刻生效。PL011 是在你寫 LCR_H 的那一刻，才把那兩個值一起搬進真正在用的內部暫存器——這個動作叫 latch（鎖存）。

所以順序反了（先 LCR_H 再 IBRD／FBRD），鮑率就不會生效，而且沒有任何錯誤訊息——只是對方收到亂碼。

（TRM = Technical Reference Manual，晶片廠給的技術參考手冊。PL011 的是 ARM DDI 0183。上面這條規則就寫在裡面。）

程式碼裡那個 4 是哪來的

與其分別算整數部和小數部，不如整個除數都用 1/64 當單位，只做一次除法：

64 × divisor = 64 × 時脈 / (16 × 鮑率)
             = (64/16) × 時脈 / 鮑率
             = 4 × 時脈 / 鮑率

64/16 = 4。所以 div64 = 4 × clk / baud，然後 IBRD = div64 / 64、FBRD = div64 % 64。

這個寫法順手解掉一個進位問題

如果分開算，小數部四捨五入後可能變成 64 —— 那會溢出 FBRD 只有 6 位元的欄位，寫進去變成 0，鮑率整個跑掉。

用同一個值除／取餘就不會：div64 到了 64 的倍數，IBRD 自己加一、FBRD 自己歸零。兩個暫存器從同一個數字推出來，進位是免費的。

一個我原本寫錯的地方

第一版寫的是 div64 = clk * 4 / baud —— 那是無條件捨去，而 TRM 說的是四捨五入。

在 QEMU 上兩者結果一樣，所以看不出來。但換到樹莓派 4 的時脈就分岔了：

差別多常出現？ 掃 1–100 MHz、每 0.5 MHz 算一次（鮑率固定 115200）：199 個時脈裡有 100 個會分岔——大約一半。

時脈捨去（第一版）四捨五入（TRM）
24 MHz(13, 1)(13, 1) 相同
3 MHz(1, 40)(1, 40) 相同
7.3728 MHz(4, 0)(4, 0) 相同
48 MHz(26, 2)(26, 3) 差一格
9 MHz(4, 56)(4, 57) 差一格

所以不是 48 MHz 特別倒楣，是 24 MHz 剛好躲過——而 24 MHz 正好是這個專案唯一驗得到的那一個。

「那我在 M2 的時候怎麼會知道樹莓派是 48 MHz？」

你不會知道。 這個專案現在沒有任何東西能告訴你——make dtb 問到的是 QEMU 的 24 MHz，手上也沒有實機。

M2 能自己驗證的，是跟平台無關的那一半：「這個寫法是捨去，TRM 說的是四捨五入，兩者在約一半的時脈上不同」。上面那張表全部是本機算的，一個硬體都不需要。

「48 MHz」是以文件為準的補充——樹莓派韌體 init_uart_clock 的預設值，本專案尚無實機可驗，而且 config.txt 改得動它。它在這裡的角色只是「一個真實存在的分岔例子」，不是論證的基礎。把它換成 9 MHz，結論一模一樣。

這正是這個專案兩種引用要分開標的原因：實測的寫數值與量法，文件的只寫「文件說什麼、還沒驗」。混在一起，讀者會以為整段都驗過了。

誤差 0.04% 對 UART 無害，所以捨去版不是 bug —— 但註解不該讓人以為它是標準算法。

改成整數形式的四捨五入：

div64 = (clk * 8 / baud + 1) / 2

（×8 再 +1 除以 2，就是 ×4 之後 +0.5 取整。）

6三個設計選擇

位址放 platform.h

QEMU virt      PL011 @ 0x0900_0000    時脈 24 MHz（device tree 寫死）
樹莓派 4        PL011 @ 0xFE20_1000    時脈由韌體決定

同一份驅動邏輯，只有位址不同。 集中在一個檔案，M9 就是新增一份 platform.h。

但「驅動完全不用改」是句過頭的話

移植到 Pi 4 至少還有兩件事不在驅動裡：

  • GPIO 腳位 muxing：晶片上的接腳不夠用，所以同一根腳可以「切換」成不同功能——UART、I2C、SPI、或單純的開關。這個切換叫 muxing（multiplexing，多工），每種功能有個編號叫 ALT0、ALT1⋯。BCM2711 的 GPIO 14/15 預設不是 UART，要設成 ALT0 才會真的接到腳位上。不做的話 —— 驅動一切正常，畫面全黑。
  • 時脈不是固定值：Pi 4 的 PL011 時脈由韌體（config.txt 的 init_uart_clock）決定，不像 QEMU 這樣寫在 device tree 裡。所以第 5 節那個「48 MHz」是韌體預設值，不是硬體常數——platform.h 的 UART0_CLK_HZ 到 M9 要填什麼，得上板量過才知道。

第一版的註解寫「the driver itself must not need editing」，讀起來像「改三個數字就好」。改成有提到這兩件事 —— 一個看起來完整的抽象層，比一個明說有缺口的抽象層危險。

\n 的轉換放在 uart_putc，不放 uart_puts

終端機收到 \n（換行）只會往下移一行，不會回到最左邊。要回最左邊得送 \r（歸位）。少了它，第二行會從第一行結尾的位置開始，畫面變成階梯狀。

第一版把轉換寫在 uart_puts 裡，結果是：

uart_puts("\n")   →  0d 0a   ✅
uart_putc('\n')   →  0a      ❌ 裸的換行

下一包就會撞到 —— printf 幾乎一定是逐字元呼叫 uart_putc，那時 printf("...\n") 就會輸出裸 LF，而症狀看起來像「終端機壞了」。

所以轉換搬進 uart_putc，讓它成為唯一出口；真正寫暫存器的 uart_putc_raw() 藏在後面。

RXE 沒有寫進去

CR 只設了 UARTEN | TXE，沒有 RXE（接收啟用）。

因為現在沒有任何東西會讀 —— 沒有 uart_getc()、沒有中斷。輸入 echo 是 M2 的第四包，那個 commit 自然會帶來加它的理由。

所以實測 CR = 0x101，不是 0x301。

7C 語言：這些寫法為什麼是這樣

M2 是第一個有 C 的里程碑，也是第一個有標頭檔的。這一節把新出現的 C 寫法一次講完——每一條都對應到 include/ 或 drivers/ 裡真的存在的一行。

標頭檔：#ifndef 三行是幹嘛的

#ifndef MMIO_H      如果還沒定義過 MMIO_H
#define MMIO_H      就定義它
...
#endif

叫 include guard（引入守衛）。#include 是純文字貼上，同一個檔被貼兩次就會「函式重複定義」而編譯失敗。有了守衛，第二次進來時 MMIO_H 已存在，整段跳過。

但這個專案現在拿掉守衛也不會爆

實測把三個標頭的 #ifndef 全部刪掉，pl011.c 和 start.c 照樣零警告編過——因為三個標頭互不 include，目前沒有任何一條會繞回同一個檔的路徑。

它現在是「便宜的保險」，不是「拿掉會壞的東西」。真正需要它的那天是：某個標頭開始 include 另一個標頭。M2 的下一包（lib/string.c）大概就會是那天。

<stdint.h> 和 "mmio.h" 的差別

寫法去哪找
#include <stdint.h>系統路徑
#include "mmio.h"先找原始檔自己的目錄，再走 -I
這個順序咬過我一次

做 lab/m2 的「拿掉 volatile」對照組時，我只加了 -I 指向改過的 mmio.h。結果原始檔還放在原本的目錄，#include "mmio.h" 先找到隔壁那份有 volatile 的——實驗安靜地測到了錯的東西，而且結果看起來像個真實的結論（「編譯器沒刪嘛」）。

正解是把原始檔也複製到改過的標頭旁邊。lab/m2/run.sh 的 novol() 現在這樣做，註解也寫了理由。

明明 -nostdlib，為什麼能用 <stdint.h>？

因為它是 freestanding 標頭。即使沒有標準函式庫，編譯器也必須提供這幾個：

stdint.h   stddef.h   stdarg.h   stdbool.h   limits.h
float.h    iso646.h   stdalign.h stdnoreturn.h

（C99 是前七個，C11 多了最後兩個。本專案用的是 gcc 預設的 C17，所以九個都能用。）

關鍵是它們只有型別和巨集，沒有任何函式——不需要任何東西被連結進來。

memcpy 就不一樣了。但它不是編不過——#include <string.h> 照樣過，因為交叉編譯器的搜尋路徑上有 glibc 的標頭。它死在連結：

undefined reference to `memcpy'
先分清楚三個很像的詞
標準怎麼說後果
未定義行為
undefined behavior		完全不管會發生什麼可能「看起來正常」、可能當掉、可能編譯器整段刪掉。今天正常不代表明天正常
實作定義
implementation-defined		各平台自己決定，但必須講清楚可預測，只是換平台會變。例如 char 有沒有號
違反約束
constraint violation		不合法，編譯器必須出診斷會有警告或錯誤——前提是你有開對旗標

「未定義行為」最容易誤會的地方是：它不保證會出事，也不保證不會。 下面那個 1 << 31 在這台機器上乖乖給你 0x80000000——但那是運氣，不是保證。

uintptr_t：為什麼不用 void *

static inline void mmio_write32(uintptr_t addr, uint32_t value)

uintptr_t 是「大到能裝下一個指標的整數型別」，AArch64 上是 64 位元。

用整數而不是指標，是因為我們拿到的本來就是一個數字，而且要對它做算術：

mmio_write32(UART0_BASE + UART_CR, 0);
             ↑ 0x09000000 + 0x30，這是整數加法

如果參數宣告成 void *，+ 0x30 在標準 C 裡是違反約束（constraint violation）——標準要求編譯器出診斷訊息。GCC 把它當擴充功能，而且預設一句話都不說：

-Wall -Wextra -Werror        完全沉默
-pedantic                    warning: pointer of type 'void *' used in arithmetic
-pedantic-errors             error

「違反約束」和「未定義行為」不一樣：前者標準要求編譯器告訴你，後者標準完全不管會發生什麼。這裡是前者，只是我們沒開 -pedantic，所以沒人告訴我們。

*(volatile uint32_t *)addr 怎麼念

由內往外拆：

addr                        一個 64 位元整數
(uint32_t *)addr            把它當成「指向 32 位元的指標」
(volatile uint32_t *)addr   而且那個目標是 volatile
*(volatile uint32_t *)addr  去那個位址讀／寫
volatile 貼在星號哪一邊 
volatile uint32_t *p    ← p 指向的東西是 volatile   ✅ 我們要這個
uint32_t * volatile p   ← p 這個變數自己是 volatile ⚠️ 保護錯對象

星號左邊修飾「被指的東西」，右邊修飾「指標自己」。 寫錯的話編譯器不會抱怨——它是合法的 C。

實測三種寫法，各連寫三次 *p，-O2：

volatile 在左（目標）    3 條 str   ✅ 正是我們要的
volatile 在右（指標）    4 條 str   ← 沒少，但多了讀指標的雜務
兩邊都沒有              1 條 str   ← 前兩次被合併掉了

所以貼右邊不是「完全沒用」，是「用錯地方而恰好有副作用」：指標自己 volatile → 每次都得重新讀指標 → 目標也就跟著每次重讀。它靠副作用達成了目的，代價是多出來的指令，而且換個寫法（例如把指標存進區域變數）保證就沒了。

依賴副作用得到的正確，跟寫對是兩件事。

static inline 放在標頭裡

先講為什麼會有這個處境。一般函式是「宣告放標頭、定義放 .c」：

mmio.h   void mmio_write32(uintptr_t, uint32_t);   只是宣告
mmio.c   void mmio_write32(...) { ... }            定義在這

但 mmio_write32 只有一行。為它開一個 .c 檔、還要付一次函式呼叫的代價，划不來。所以定義直接寫進標頭。

代價是：#include 是純文字貼上，那份定義會被複製到每一個 include 它的 .c 裡。兩個關鍵字各處理這個複製帶來的一個麻煩。

麻煩一：撞名 → static 解決

pl011.c  貼一份 mmio_write32
uart2.c  貼一份 mmio_write32
連結器： multiple definition of 'mmio_write32'   ❌

static 的意思是「這一份只有我這個 .c 看得到」，於是兩份各自獨立，不會撞。

代價是真的產生兩份程式碼——但函式這麼小，-O2 會展開掉，代價是零。

麻煩二：沒用到會被唸 → inline 解決

這才是 inline 在這裡的真正作用，跟「展開比較快」無關。

標頭被貼進每個 .c。如果某個 .c 只寫不讀，mmio_read32 就成了「定義了卻沒人用的 static 函式」。實測同一份程式碼，只換旗標：

（什麼都不加）    編過，一句話都沒說
-Wall             編過，但有警告
                  warning: 'r32' defined but not used [-Wunused-function]
-Wall -Werror     ❌ 建置失敗
                  error: 'r32' defined but not used [-Werror=unused-function]
-Werror 沒有做任何新檢查

它只是把所有警告升級成錯誤。上面三行的訊息文字幾乎一樣，只有 warning 變成 error。

所以完整的因果鏈有三段：

1. 定義在標頭      →  每個 .c 都貼一份
2. 某個 .c 沒用到  →  -Wall 裡的 -Wunused-function 出來唸
3. 我們有 -Werror  →  唸變成擋

三段裡拿掉任何一段，建置都會過。 inline 是在斷第 2 段——它等於跟編譯器說「這函式住在標頭裡，沒人用是正常的」。

但今天拿掉 inline 也不會壞 
誰 include 了 mmio.h：  只有 drivers/uart/pl011.c
它用到 mmio_write32：  6 次
它用到 mmio_read32：   1 次

把 static inline 改成 static，整個核心重編  →  exit 0

只有一個檔 include，而且兩個函式都用到了，所以第 2 段觸發不了。

照鐵則五的判準，inline 現在不是承重的。但它離承重只差一步——下一個 include mmio.h 卻只寫不讀的 .c 出現，建置就會斷。M2 的下一包 lib/ 很可能就是。

三種寫法的下場

關鍵字作用不寫會怎樣
static inline
我們用的		每個 .c 各自一份，不對外公開；建議展開—
兩個都不寫一個普通的全域函式兩個 .c include 同一個標頭 → multiple definition of 'mmio_write32'
只寫 inline——-O0 下 連結失敗：undefined reference to 'mmio_write32'

最後那一列是重點：inline 單獨用，是給「另有一份外部定義」的情況準備的。編譯器可以選擇不展開，那時就得去找那份外部定義——而我們沒有，於是連結器找不到。

這就是為什麼慣用寫法是 static inline：static 保證每個 .c 都有自己的一份，展不展開都不會缺人。

而且那一列是 -O 相依的

-O2 下同一份程式碼連結得過——因為編譯器真的展開了，根本不需要那份外部定義。

所以「只寫 inline 會壞」這句話，只在 -O0 成立。這正是第 10 節精髓第 2 條說的：「拿掉它現在會壞嗎」要連編譯旗標一起問。

順帶：inline 對「要不要展開」真的只是建議

實測 -O0 下它完全沒展開——mmio_write32 變成一個真的函式，而且是這樣：

<mmio_write32>:
    sub  sp, sp, #0x10      挖 16 bytes
    str  x0, [sp, #8]       把參數存到堆疊
    str  w1, [sp, #4]
    ldr  x0, [sp, #8]       ⋯又立刻讀回來
    ldr  w1, [sp, #4]
    str  w1, [x0]           ★ 只有這條真的碰硬體
    nop
    add  sp, sp, #0x10
    ret

九條指令，八條是雜務。 存下去又馬上讀回來，純粹因為 -O0 不做任何優化。-O2 下整個函式會被展開成那一條 str。

(1u << 5)：那個 u 和那對括號

#define FR_TXFF   (1u << 5)

u： 1 是有號 int，有號數左移到最高位是未定義行為（1 << 31）。我們現在最多移 8 位（CR_TXE）還安全，但旗標是位元樣式、不是數量，本來就該用無號。

括號： 這條我第一版寫反了，值得留下來。

直覺會說「少了括號，x & FR_TXFF 會變成 (x & 1u) << 5」。實測不是。

#define M_NOPAR 1u << 5
#define M_PAR  (1u << 5)

x & M_NOPAR      →  and   w0, w0, #0x20   ┐ 完全一樣
x & M_PAR        →  and   w0, w0, #0x20   ┘
(x & 1u) << 5    →  ubfiz w0, w0, #5, #1  ← 這是另一回事

<< 的優先序高於 &，所以 x & 1u << 5 本來就等於 x & (1u << 5)。位元遮罩這個用法，加不加括號都對。

括號真正救到的是加減法——它們的優先序比 << 高：

M_NOPAR + 1   →   1u << 5 + 1   →   1u << 6   =  64   ❌
M_PAR   + 1   →   (1u << 5) + 1              =  33   ✅
但這個坑在本專案掉不進去

-Wparentheses 在 -Wall 裡，而我們有 -Werror：

error: suggest parentheses around '+' inside '<<' [-Werror=parentheses]

所以那個 64 不是會安靜發生的陷阱，是硬錯誤。真正救到的不是「我記得加括號」這個習慣，是 -Wall -Werror。

（對照上面 void * 那條：同樣是「標準說不行」，那條在 -Wall -Wextra -Werror 下完全沉默，要 -pedantic 才叫。旗標管得到哪些、管不到哪些，沒有規律，只能一條一條試。）

所以規則還是「巨集內容用括號包起來」，但理由不是我原本寫的那個。「這條規則救了我」和「我知道它救了什麼」是兩件事——我照著規則寫對了程式碼，卻把理由講反了，直到有人去編一次才發現。

（順帶：#define UART_DR 0x00 那六個沒有括號，因為單一 token 不可能被拆開。需要括號的是「裡面有運算子」的巨集。）

UL 後綴：運算寬度由運算元決定

#define UART0_CLK_HZ    24000000UL

規則是：運算的寬度由運算元決定，不是由你要存進去的變數決定。

uint64_t x = a * b;    ← a、b 都是 32 位元的話，
                          乘法照樣在 32 位元裡溢位，然後才把壞掉的結果放大
但這裡防溢位的不是 platform.h 的 UL

我原本以為是。實際的算式是：

UART0_CLK_HZ * 8UL / UART0_BAUD

那個 8UL 已經把整式拉到 64 位元了——只要有一個運算元是 unsigned long，另一邊就會被提升上去。

實測：把 platform.h 的 UL 全部拿掉、時脈換成 600 MHz（會讓 32 位元溢位的量級）：

CLK_INT * 8UL / BAUD  →  20833   ✅ 正解，UL 拿掉也沒事
CLK_INT * 8   / BAUD  →   2192   ❌ 兩邊都拿掉才壞
                             warning: integer overflow … results in '505032704'

所以 platform.h 的 UL 目前是備而不用的——它的價值在「下一個人抄這個巨集去寫別的算式」時才兌現。

這一則的教訓不在 UL，在「我以為某個東西在保護我，但保護我的其實是別的地方」。要確認一個防護有沒有作用，只有一個方法：拿掉它，看會不會壞。

(uint32_t)(unsigned char)c：為什麼要兩層

mmio_write32(UART0_BASE + UART_DR, (uint32_t)(unsigned char)c);

char 的正負號是實作定義的——C 標準沒有規定，各平台自己決定。

如果 char 是有號的，c = 0x80（128）會被當成 −128，放大時做符號延伸：

(uint32_t)c                  →  0xFFFFFF80   ❌ 高位全變 1
(uint32_t)(unsigned char)c   →  0x00000080   ✅

先轉 unsigned char 把符號問題斷掉，再放大。

但在這台機器上兩者相同

實測 AArch64 的 char 是無號的：char c = -1; return c < 0; 編出來是 mov w0, #0——編譯器直接算出「不可能小於 0」。

所以 bad() 和 good() 兩個函式編出來一模一樣，都是 and w0, w0, #0xff 加 ret。

那個轉型是為了可攜性，不是為了這台機器。 同一份程式碼搬到 x86（char 有號）就會分岔——而這種 bug 只在字元 ≥ 0x80 時才出現，通常是別人送中文進來的那天。

while (...) { ; }：那個孤獨的分號

while (mmio_read32(UART0_BASE + UART_FR) & FR_TXFF) {
    ;
}

迴圈體是空的——我們只是要一直讀到 TXFF 變 0。

為什麼不寫 while (...);？因為那個分號看起來像打錯字：

while (cond);        ← 這是空迴圈，還是不小心多打一個分號？
    do_something();  ← 讀者會以為這行在迴圈裡

寫成 { ; } 是明確表態：這裡故意什麼都不做。

*s++ 的優先序

uart_putc(*s++);

++ 綁得比 * 緊，所以它是 *(s++)：

1. 取 s 目前的值當作結果  →  傳給 *
2. s 自己 +1
3. 效果：讀出現在指的字元，然後指標往後移一格

寫成 (*s)++ 意思完全不同——那是「把字元的值加一」。而 uart_puts 的參數是 const char *s，所以它根本編不過：

error: increment of read-only location '*s'

const 在這裡把一個「要到 M5 開了 MMU 才會爆」的問題，提前到編譯期擋掉了。

const char *s：const 在星號哪一邊

const char *s     內容唯讀，但 s 可以移動   ✅ 我們要這個
char * const s    s 不能移動，但內容可以改

uart_puts 裡有 *s++（移動指標），所以 const 必須在左邊。

而且它讓呼叫端安全：uart_puts("Hello") 的字串在 .rodata，const 讓編譯器在 M5 之前就先擋下寫入。

void uart_init(void)：那個 (void) 不能省

void uart_init(void);    明確說「沒有參數」
void uart_init();        在 C 裡意思是「參數不詳」❌

C++ 兩者相同，C 不是。寫成 () 的話，uart_init(1, 2, 3) 也編得過，而且不會警告。

static 在 C 裡有兩種意思

放在哪意思本專案的例子
檔案層級不對外公開，別的 .c 看不到static void bump(void)
函式裡面這個區域變數的壽命是整個程式（還沒用到）

同一個關鍵字，兩件事，看位置決定。nm 的大小寫就是在報第一種：

void kernel_main(void)               →  T kernel_main    大寫，全域
static void bump(void)               →  t bump           小寫，static
static unsigned long boot_counter;   →  b boot_counter
kernel_main 是唯一不能加 static 的

因為 boot.S 要 bl kernel_main。組語看不到 C 的作用域規則，它靠連結器把名字配對起來——加了 static，那個名字就不會出現在全域符號表，連結會失敗。

這是 C 和組語唯一的接縫。

「沒初始化就用」為什麼在這裡沒問題

boot_counter 沒給初始值，bump() 卻直接對它 ++：

static unsigned long boot_counter;
static void bump(void) { boot_counter++; }

「沒初始化就用」的警覺是對的，但那個直覺只適用於區域變數。C 把變數分成兩種「儲存期」，規則完全不同：

誰沒給初始值時x++
自動儲存期函式裡的區域變數是垃圾（上一個人留在堆疊上的東西）❌ 未定義行為
靜態儲存期全域變數、static 變數保證是 0（C 標準規定）✅ 合法

編譯器自己就把兩者分開了。同一份程式碼，只有區域變數那個被唸：

unsigned long f_local(void)  { unsigned long x; x++; return x; }
unsigned long f_static(void) { g_static++;      return g_static; }

warning: 'x' is used uninitialized [-Wuninitialized]
（g_static 一句話都沒說）
順便看一眼「未定義行為」長什麼樣

那兩個函式編出來的指令差很多：

<f_local>:                  <f_static>:
    mov x0, #0x1                ldr x0, [x1]     真的去讀
    ret                         add x0, x0, #1
                                str x0, [x1]     真的寫回
                                ret

f_local 被編譯器直接算成 1。 反正那是垃圾值，它愛怎麼算都行——這就是未定義行為的樣子：不是當掉，是編譯器有權亂來。

f_static 則老老實實讀-加-寫，因為它知道那個值有意義。

但那個「保證是 0」，在這裡是我們自己兌現的

C 標準規定靜態儲存期的變數要是 0。這是語言層面的通則，任何符合標準的實作都得做到。 但「誰去做」不是通則——每個平台不一樣：

平台誰把 .bss 清成 0
Linux 上的一般程式核心的 ELF 載入器
有些嵌入式工具鏈C 執行期啟動碼（crt0）
這個專案沒有人——所以 boot.S 自己做

怎麼證明？兩個方向

正面：那些 0 一定是執行時生出來的，不在檔案裡。 拿一個宣告了 8 MB .bss 的 Linux 程式來看：

執行檔大小 = 641,104 bytes
.bss 大小  = 8,410,768 bytes   ← 比整個檔案還大，而且型別是 NOBITS

8 MB 的 0 沒有存在檔案裡（存了也是浪費）。所以一定有人在載入時把它生出來。

反面：把那個「人」拿掉，就不是 0 了。 這是我們自己做得到的實驗——把 boot.S 的清零迴圈整段刪掉，開機前先用 -device loader 把 boot_counter 塞成 0xcafe1234：

有清零迴圈   進 kernel_main 時 boot_counter = 0x0
拿掉迴圈     進 kernel_main 時 boot_counter = 0xcafe1234

這證明它不是自動的。 C 的保證是真的，但在裸機上是我們自己實現的——少了那 6 行組語，boot_counter++ 就變成「把一個垃圾值加一」，跟區域變數的情況一模一樣。

這也是為什麼 make debug 要檢查它：它是那個保證有沒有被兌現的唯一證據。

沒給初始值 → .bss；給了非零 → .data

實測三種寫法落在哪：

static unsigned long a;      →  nm 顯示 b   .bss
static unsigned long b = 0;  →  nm 顯示 b   .bss（明著寫 0 也一樣）
static unsigned long c = 7;  →  nm 顯示 d   .data

C 保證未初始化的全域變數是 0，所以 = 0 是多餘的，編譯器一樣放 .bss（只記大小，不存內容）。

只有給非零初始值才會進 .data——那時檔案裡真的要存那個數字。這就是為什麼連結器腳本的註解說「目前還沒有 .data」：整個核心沒有任何全域變數給了非零初始值。

同一個 volatile 的道理，start.c 還沒套用

這一節花了很多篇幅講 volatile 對 MMIO 為什麼必要。但 start.c 裡那個 boot_counter 沒有 volatile，而它是 make debug 用來證明「.bss 被清了」的唯一證據。

實測用 -O2 重編整個核心：

<kernel_main>:            （略去序言兩條與位址運算）
    bl   uart_init
    bl   uart_puts
    b    .                  ← 死迴圈，就這樣

nm | grep -E 'boot_counter|bump'   →  零個結果

變數和函式連符號都不存在了。 編譯器的推論完全正確：boot_counter 是 static（外面看不到）、只被加一從來沒被讀、所以整條計算是死的，連同 bump() 一起刪掉。

那一天 make debug 的第三個檢查會變成這樣（實跑 -O2 版本量到的）：

SP        = $1 = 0x40010200
EL        = $2 = 1
bss 清了嗎 = No symbol table is loaded.  Use the "file" command.

不是壞掉，是證據消失。 前兩行照樣正確，只有第三行沉默地失去意義。

照鐵則五的判準，現在（-O0）加 volatile 不會改變任何指令，所以還不該加。但這是一則已經寫在牆上的預告：真的開 -O2 的那個 commit，除了 mmio.h 之外，還得處理這個見證變數。

8被推翻的直覺

直覺 1

「UART 要先初始化才能用」

在 QEMU 上完全不用。實測：寫一支只做 uart_puts()、完全不呼叫 uart_init() 的核心 —— 字元照樣全部出來。

而且開機時的狀態是「UARTEN = 0、鮑率沒設、字元長度沒設」。一台標示為關閉、沒有設定鮑率的 UART，照樣把字送出去了。

因為 QEMU 的 PL011 模型只是把位元組轉交給宿主機的終端機，那些設定它一個都不看。

直覺 2 —— 這一則是本節的重點

「volatile 是防止編譯器把重複的寫入合併成一次」

方向對，但實際發生的事更狠。拿掉 volatile、用 -O2 編，數一下 uart_init() 裡的 str：

-O0  有 volatile   1 條   （呼叫 mmio_write32，沒展開）
-O0  無 volatile   1 條   完全一樣
-O2  有 volatile   5 條   五次寫入都在
-O2  無 volatile   4 條  少了一條

少的那一條是 CR = 0。 編譯器看到 CR 被寫兩次（先 0、後 0x101），把第一次當成死存取（dead store——寫進去之後、還沒有人讀就被蓋掉的一次寫入）刪掉了：

-O2、無 volatile 的 uart_init：
    str  w7, [x6]     ; IBRD = 13
    str  w5, [x4]     ; FBRD = 1
    str  w3, [x2]     ; LCR_H = 0x70
    str  w1, [x0]     ; CR = 0x101
    ret
                      ← 「先關掉 UART」那一步整條不見了

而那正是註解裡宣稱「保護飛行中的字元」的那一行。編譯器把安全措施刪掉了，而且 QEMU 上照樣印出 Hello。

兩個教訓：一，volatile 不是為了現在，是為了 -O2（PROJECT_PLAN 有規定，Makefile 還沒設）。二，「拿掉它現在會壞嗎」這個判準要連編譯旗標一起問 —— 同一段程式碼在 -O0 和 -O2 下是兩個不同的答案。

直覺 3

「clk * 4 / baud 就是 TRM 的算法」

不是，那是無條件捨去，TRM 是四捨五入。24 MHz 剛好相同，48 MHz（Pi 4）差一格。細節在第 5 節。

值得記住的是它為什麼躲過檢查：唯一能驗證的平台剛好是兩種算法一致的那個。

直覺 4

「M1 的 ALIGN(16) 擋住了孤兒節插隊」

M1 的連結器腳本註解說：把 __bss_start 寫在 .bss { } 外面，ld 會把孤兒節（.eh_frame）塞進符號和區段之間，清零迴圈就會抹掉它。

照字面做重現不出來。 實測（binutils 2.38，M1 當時的原始碼）：

符號在大括號內              __bss_start = 0x400000f0   安全
符號移到外面，保留 ALIGN     __bss_start = 0x400000f0   還是安全
符號移到外面，拿掉 ALIGN     __bss_start = 0x400000a4   ← .eh_frame 在 0x400000a8，被夾住了

要兩個條件同時成立才會出事，而註解只寫了一個。

更值得記住的是：那個 ALIGN(16) 是為了「讓清零迴圈一次寫 16 bytes 不留零頭」而寫的，它擋住孤兒節純屬意外。一個為了 A 而寫的東西，剛好也擋住了不相干的 B —— 這種「靠巧合正確」的程式碼，會在某天加了一個新區段之後突然壞掉。

（M2 就加了新區段：.rodata。加進腳本之後，孤兒節的位置又變了。）

直覺 5

「同樣的原始碼建兩次，產出應該一模一樣，所以 md5 相同代表沒重建」

錯。實測連續建兩次，md5 就不同 —— 差 6 個 byte。

位置在 .strtab（string table，ELF 裡存放所有符號名字的那一區）。gcc 編譯時會產生暫存的 .o 檔，檔名每次都不一樣（ccGWRvg.o、cc3aNwQx.o⋯），而那個名字會以一個 STT_FILE 型別的符號（ELF 用來記錄「這段東西來自哪個原始檔」）留在符號表裡。

所以「md5 沒變」不能用來證明沒重建。反向仍可靠：md5 變了不代表真的重建了。要驗「有沒有重建」，看 make 的輸出有沒有跑編譯指令比較準。

之前之後寫進去的是什麼

IBRD 和 FBRD 是程式從 platform.h 的 24 MHz 與 115200 算出來的，不是寫死的常數。

TXFF 等待迴圈

連寫 64 個字元，每次寫之前記錄 FR：
  64 次讀到的值全部是 0x90，TXFF 一次都沒被拉起來
  等待迴圈總共跑了 0 圈

QEMU 瞬間排空佇列，所以這個迴圈在這裡拿掉也毫無差別。它是為了真硬體 16 深的 FIFO 而寫的。

記憶體佈局

.rodata 在 M1 之前不存在。M2 加了第一個字串常數之後，它本來是孤兒節 —— 腳本沒提到、由 ld 自己找地方擺。現在明確寫進腳本了。

想看「連結器腳本的哪一行 → 記憶體的哪一塊 → boot.S 的哪一行碰它」的三欄對照圖，在 M1 教材第 6 節。那張圖用的就是上面這組數字。

兩張表疊起來：符號不等於區段

readelf -S 看的是區段——編譯器把程式切成的幾大塊。nm 看的是符號——名字對應到哪個位址。兩者不一定重合，把它們疊在同一根軸上就看得出來。

這張圖說了四件事

1. .rodata 和 .eh_frame 一個符號都沒有。 那個 "Hello, AArch64 from EL1\n" 就住在 .rodata，但它是匿名的字串字面值——編譯器直接用位址引用，沒人需要它的名字。所以 nm 看不到，readelf 看得到。

2. .text 裡面有一段沒有名字的資料。 halt_loop 後面的 0x58–0x6f 是字面池，存著三個位址常數。objdump 只好叫它 halt_loop+0xc——用最近的前一個符號加偏移來描述。

3. __bss_start 比 .bss 區段晚 8 個 byte。 那 8 bytes 是 ALIGN(16) 推出來的，在區段裡但清零迴圈碰不到（它從 __bss_start 起跑）。「區段多大」和「迴圈清多少」是兩個數字：區段 24 bytes，迴圈只走 16。

4. __bss_end 和 .stack 的起點是同一個位址。 因為「結束的下一個」剛好等於「下一塊的開始」。清零迴圈的 b.hs 是等於就停，所以它不會寫進堆疊——差一個字就會踩過去。

還有一個不在這根軸上的符號

nm 的第一行是：

0000000000010000 A STACK_SIZE

0x10000 不是位址，是值本身——就是連結器腳本裡 STACK_SIZE = 64K; 那個 64K。

A 是 absolute，代表它不屬於任何區段。把它當位址去讀，會讀到 flash 區的垃圾。

堆疊用量

10精髓

  1. 週邊裝置的暫存器不是記憶體，編譯器不知道這件事。 volatile 是唯一告訴它的方法，而且少了它不會有錯誤訊息 —— 只會少做事。
  2. 「拿掉它現在會壞嗎」要連編譯旗標一起問。 同一段程式碼在 -O0 和 -O2 下，答案是相反的。
  3. 唯一能驗證的平台，可能剛好是看不出錯的那個。 鮑率的捨去 vs 四捨五入在 QEMU 上完全一致，只在真機的時脈上分岔。「測過了」和「在會出錯的條件下測過了」是兩件事。
  4. 一個看起來完整的抽象層，比一個明說有缺口的危險。 platform.h 說「驅動不用改」是真的，但沒說 GPIO muxing 得另外做 —— 讀者會在真板子上得到全黑畫面，然後不知道從哪查起。

11一頁式小抄

PL011 暫存器

+0x00  DR      寫進去 = 送一個字元
+0x18  FR      bit5 TXFF = 送出佇列滿了
+0x24  IBRD    鮑率除數整數部
+0x28  FBRD    鮑率除數小數部（1/64）
+0x2c  LCR_H   bit4 FEN 開 FIFO、bits[6:5] WLEN（3 = 8 bits）
+0x30  CR      bit0 UARTEN、bit8 TXE、bit9 RXE

初始化順序

1. CR = 0            先關掉（改設定不能在運轉中做）
2. IBRD、FBRD        設鮑率
3. LCR_H             設字元格式 —— 寫這個才會 latch 上一步
4. CR = UARTEN|TXE   開起來

鮑率

divisor = clk / (16 × baud)
div64   = (clk × 8 / baud + 1) / 2      整數形式的四捨五入
IBRD    = div64 / 64        FBRD = div64 % 64

24 MHz / 115200  →  833  →  (13, 1)   誤差 +0.04%

標頭裡的函式為什麼要 static inline

定義寫在標頭 → 每個 include 它的 .c 都貼一份

static   斷「兩份撞名」    少了 → multiple definition
inline   斷「沒用到被唸」  少了 → -Wunused-function（配 -Werror 就擋建置）

只寫 inline（沒 static）  → -O0 下 undefined reference

MMIO 的寬度看【裝置的暫存器】，不是【CPU 的暫存器】：
  x0-x30（CPU 裡）        64 位元
  DR/FR/IBRD（PL011 裡）  32 位元  → 資料用 uint32_t
  位址空間                64 位元  → 位址用 uintptr_t
  證據：從 IBRD 讀 8 bytes 會讀到 FBRD 黏在高 32 位元

C 的幾個容易寫錯的地方

volatile uint32_t *p     ← 目標是 volatile   ✅
uint32_t * volatile p    ← 指標自己是       ❌ 保護錯對象

const char *s            ← 內容唯讀，指標可動  ✅
char * const s           ← 反過來

void f(void)             ← 沒有參數          ✅
void f()                 ← 「參數不詳」，C 不擋 f(1,2,3)

#define M (1u << 5)      ← u 防有號左移
#define M 1u << 5        ← x & M 沒事（<< 優先序高於 &）
                            但 M + 1 會變成 1u << 6 = 64

clk * 8UL / baud         ← 有一個 UL 就整式提升到 64 位元  ✅
clk * 8   / baud         ← 全部 32 位元，換高時脈會溢位

*s++                     ← *(s++) 讀了再移動指標
(*s)++                   ← 改字元本身；參數是 const char * 所以編不過

(uint32_t)(unsigned char)c   ← 先斷符號再放大，可攜
(uint32_t)c                  ← char 有號的平台會符號延伸

兩種儲存期，規則不一樣

void f(void){ unsigned long x; x++; }   自動儲存期 → 垃圾值 → UB
static unsigned long g;       g++;      靜態儲存期 → 保證 0 → 合法

「保證 0」是 C 標準規定的通則，但【誰去做】不是：
  Linux 一般程式   核心的 ELF 載入器
  這個專案         沒有人 → boot.S 自己清

證明：拿掉 boot.S 的清零迴圈，開機前塞 0xcafe1234
      → 進 kernel_main 時它還在

變數落在哪個 section

static unsigned long a;      → .bss    只記大小
static unsigned long b = 0;  → .bss    明著寫 0 也一樣
static unsigned long c = 7;  → .data   要存那個 7

static  在檔案層級 = 不對外公開（nm 顯示小寫）
        在函式裡面 = 壽命是整個程式

讀 nm 的輸出

T / t   .text     程式碼        大寫 = 全域，小寫 = static
B / b   .bss      未初始化資料   同上
D / d   .data     已初始化資料   同上（M2 還沒有）
A       absolute  不是位址，是值本身

0000000000010000 A STACK_SIZE     ← 這是 64K 這個數字，不是位址
0000000040000340 B __bss_start    ← 這才是位址
