3MMIO：用寫記憶體的方式操作硬體

MMIO = memory-mapped I/O，記憶體對映輸入輸出。

周邊裝置（UART、計時器、中斷控制器）的控制暫存器，被硬體擺在記憶體位址空間裡。你用一般的 ldr／str 讀寫那些位址，就等於在對硬體下指令。

0x0900_0000   ← 這個位址不是 RAM，是 UART 的資料暫存器
              往這裡寫一個 byte = 送出一個字元

M1 的記憶體地圖你看過：0x0 到 0x4000_0000 那一整段都是 flash 和 MMIO，RAM 從 0x4000_0000 才開始。UART 就住在那一段裡。

位址從哪來

不是從資料手冊抄的，是問 QEMU 要的：

$ make dtb          讓 QEMU 吐出它自己的 device tree

pl011@9000000 {
    compatible = "arm,pl011", "arm,primecell";
    reg = <0x00 0x9000000 0x00 0x1000>;      ← 基底位址與大小
    clock-names = "uartclk", "apb_pclk";
    clocks = <0x8000 0x8000>;                ← 指向下面那個節點
};

apb-pclk {
    phandle = <0x8000>;
    clock-output-names = "clk24mhz";
    clock-frequency = <0x16e3600>;           ← 24,000,000 Hz
};

三個沒見過的欄位名：compatible 是「這個裝置是什麼型號」，作業系統靠它決定要用哪支驅動；reg 是「它的暫存器擺在哪、佔多大」；phandle 是節點的編號，讓別的節點可以指過來——上面 clocks = <0x8000> 指的就是下面 phandle = <0x8000> 那個時脈節點。

位址不是免費的：組一個要兩條指令

AArch64 的指令固定 32 位元，所以指令裡塞不下一個 64 位元的常數。編譯器一次搬 16 位：

mov  x0, #0x30              先放低 16 位   x0 = 0x0000_0000_0000_0030
movk x0, #0x900, lsl #16    再塞 bit16-31  x0 = 0x0000_0000_0900_0030

movk = move keep——只改指定的那 16 位，其他位元保留。（mov 會把整顆清掉再寫，所以只能用在第一次。）

所以 每一次 MMIO 存取，光是「產生位址」就花掉兩條指令。現在無所謂，M4 寫中斷處理常式時就會開始計較——那段程式碼每秒要跑幾千次。

PL011 是 ARM 設計的 UART 控制器型號。QEMU virt 和樹莓派 4 用的都是它 —— 這是 M9 移植時驅動能沿用的原因，只有位址不同。

為什麼非要 volatile 不可

編譯器看到「連續寫同一個位址三次」，會認為前兩次沒意義，只留最後一次。對 RAM 這是正確的優化。對 MMIO 是災難 —— 那三次是三個字元。

volatile 就是告訴編譯器：這個位址每一次存取都算數，不准合併、不准省略、不准換順序。

但它不會產生任何指令

這點很容易誤會。把 mmio_write32 的 volatile 拿掉，重編、比對那一條真正寫硬體的指令：

有 volatile   400000c8:  b9000001   str  w1, [x0]
無 volatile   400000c8:  b9000001   str  w1, [x0]
                         ↑ 連機器碼都一模一樣

volatile 不加指令，它禁止編譯器拿掉指令。

所以它的效果只在「有人想拿掉」的時候才看得見——-O0 下沒人要拿，兩邊自然相同；-O2 下有人要拿，那時才擋得住。第 10 節的直覺 2 就是那個場面。

但這件事現在證明不出來

本專案目前沒有加任何 -O 旗標，也就是 -O0。實測 -O0 下加不加 volatile，產出的組語逐位元組相同。

照鐵則五的字面判準（「拿掉它現在會壞嗎」），volatile 現在不會壞。

但把 -O0 換成 -O2，「拿掉 volatile」就會壞了——而且壞的方式非常漂亮，見第 10 節。

講清楚免得誤會：volatile 本身在 -O2 下是有效的，該保留的寫入一條都不會少。會壞的是「拿掉它」那一邊。-O0 看不出差別，只是因為那個等級的編譯器本來就不做這種優化。

所有 MMIO 都走同一個門

static inline void mmio_write32(uintptr_t addr, uint32_t value)
{
    *(volatile uint32_t *)addr = value;
}

專案禁止任何地方直接寫 *(volatile uint32_t *)addr = v。理由是忘記 volatile 不會有任何錯誤訊息 —— 它會安靜地少印字元。集中成兩個函式，就只剩一個地方可能寫錯。

4PL011 的六個暫存器

先講 FIFO

FIFO（first in, first out，先進先出）是一個小佇列。UART 送一個字元到線上要花時間（115200 bps 下約 87 微秒），如果軟體每送一個就得等它走完，CPU 大部分時間都在發呆。

所以硬體準備了一個 16 格的佇列：軟體把字元丟進去就走，硬體自己慢慢送。丟滿 16 個才需要等。

FR 裡的旗標就是在回報這個佇列的狀態：TXFF（transmit FIFO full）滿了、TXFE（empty）空了；RX 開頭的是接收那一側的同名旗標。

偏移名字做什麼
+0x00DRData Register。寫進去 = 送出一個字元
+0x18FRFlag Register。bit5 TXFF = 送出佇列滿了
+0x24IBRD鮑率除數的整數部
+0x28FBRD鮑率除數的小數部，單位 1/64
+0x2cLCR_HLine Control Register (High)。bit4 FEN = FIFO enable；bits[6:5] WLEN = 一個字元幾個 bit
+0x30CRControl Register。總開關
為什麼存取函式叫 mmio_write32——我們不是 64 位元嗎

因為「暫存器」這個詞在這裡指的是兩組完全不同的東西：

住在哪幾位元例子
CPU 的通用暫存器CPU 核心裡面64x0–x30、sp、pc
裝置的控制暫存器PL011 那顆晶片裡面32DR、FR、IBRD、CR

「AArch64 是 64 位元」講的是第一組——那個認知完全正確，x0 確實是 64 個 bit。

但 PL011 是掛在匯流排上的另一顆晶片，它裡面那些暫存器由它自己的設計決定，是 32 位元。兩組暫存器互不相干，只是名字都叫「暫存器」。

證據：一次讀 8 個 byte，讀到的是兩顆黏在一起

IBRD 在 0x09000024、FBRD 在 0x09000028，中間差 4。實測：

分開讀，一次 4 bytes：
  0x09000024 (IBRD) = 0xd
  0x09000028 (FBRD) = 0x1

從 0x09000024 一口氣讀 8 bytes：
  0x09000024        = 0x10000000d
                        ↑        ↑
                      FBRD     IBRD

那不是「一顆 64 位元暫存器」，是兩顆 32 位元的排在一起。 如果 PL011 的暫存器真的是 64 位元，IBRD 和 FBRD 就不會只差 4 個 byte。

所以函式簽章裡兩種寬度都在

void mmio_write32(uintptr_t addr, uint32_t value)
                   ↑ 64 位元        ↑ 32 位元
                   要 64 位元才裝    因為 PL011 的
                   得下 AArch64      控制暫存器就是
                   的位址            32 位元寬

位址是 64 位元，因為它指的是 AArch64 的位址空間。資料是 32 位元，因為那顆硬體暫存器就這麼寬。

寫錯寬度，編譯器不會攔你

兩種都是合法的 C，差別只在產生哪一條指令：

*(volatile uint64_t *)0x09000024 = 0xd;   →  str x1, [x0]   寫 8 bytes ❌
*(volatile uint32_t *)0x09000024 = 0xd;   →  str w1, [x0]   寫 4 bytes ✅

（x1 是 64 位元暫存器，w1 是同一顆的低 32 位元。）

上面那條會把 IBRD 和隔壁的 FBRD 一起蓋掉——鮑率的小數部被清成 0，而沒有任何錯誤訊息。

記憶體你想寫幾位元都行；MMIO 的寬度是硬體規定的。

M4 的中斷控制器確實有 64 位元的裝置暫存器，那時才會需要 mmio_write64——到那時再加。

開機時它們長什麼樣

用 GDB 在 uart_init() 執行之前讀：

CR    = 0x300     bit8 TXE=1、bit9 RXE=1，但 bit0 UARTEN = 0
IBRD  = 0x0       鮑率完全沒設
FBRD  = 0x0
LCR_H = 0x0       字元長度沒設
FR    = 0x90      bit7 TXFE（送出佇列空）=1、bit4 RXFE（接收佇列空）=1

UARTEN = 0，這台 UART 標示為「沒有啟用」。 記住這一點，第 10 節會用到。

5鮑率：一個除法拆成兩個暫存器

鮑率（baud rate）= 一秒送幾個 bit。兩端要講好，不然收到的是亂碼。

UART 拿到一個固定時脈，內部先除以 16，再除以我們給的除數：

divisor = 時脈 / (16 × 鮑率)
        = 24,000,000 / (16 × 115200)
        = 13.0208

13 太慢、14 太快。 所以硬體把除數拆成兩半，用「13 又 1/64」來逼近：

IBRD = 13                        整數部
FBRD = round(0.0208 × 64) = 1    小數部，單位 1/64

實際跑出來的鮑率是 24e6 / (16 × (13 + 1/64)) = 115246.1，誤差 +0.04%。UART 容許約 ±2%，很穩。

寫 LCR_H 才會「鎖上」鮑率

寫進 IBRD 和 FBRD 的值不會立刻生效。PL011 是在你寫 LCR_H 的那一刻，才把那兩個值一起搬進真正在用的內部暫存器——這個動作叫 latch（鎖存）。

所以順序反了（先 LCR_H 再 IBRD／FBRD），鮑率就不會生效，而且沒有任何錯誤訊息——只是對方收到亂碼。

（TRM = Technical Reference Manual，晶片廠給的技術參考手冊。PL011 的是 ARM DDI 0183。上面這條規則就寫在裡面。）

程式碼裡那個 4 是哪來的

與其分別算整數部和小數部，不如整個除數都用 1/64 當單位，只做一次除法：

64 × divisor = 64 × 時脈 / (16 × 鮑率)
             = (64/16) × 時脈 / 鮑率
             = 4 × 時脈 / 鮑率

64/16 = 4。所以 div64 = 4 × clk / baud，然後 IBRD = div64 / 64、FBRD = div64 % 64。

這個寫法順手解掉一個進位問題

如果分開算，小數部四捨五入後可能變成 64 —— 那會溢出 FBRD 只有 6 位元的欄位，寫進去變成 0，鮑率整個跑掉。

用同一個值除／取餘就不會：div64 到了 64 的倍數，IBRD 自己加一、FBRD 自己歸零。兩個暫存器從同一個數字推出來，進位是免費的。

一個我原本寫錯的地方

第一版寫的是 div64 = clk * 4 / baud —— 那是無條件捨去，而 TRM 說的是四捨五入。

在 QEMU 上兩者結果一樣，所以看不出來。但換到樹莓派 4 的時脈就分岔了：

差別多常出現？ 掃 1–100 MHz、每 0.5 MHz 算一次（鮑率固定 115200）：199 個時脈裡有 100 個會分岔——大約一半。

時脈捨去（第一版）四捨五入（TRM）
24 MHz(13, 1)(13, 1) 相同

「那我在 M2 的時候怎麼會知道樹莓派是 48 MHz？」

你不會知道。 這個專案現在沒有任何東西能告訴你——make dtb 問到的是 QEMU 的 24 MHz，手上也沒有實機。

M2 能自己驗證的，是跟平台無關的那一半：「這個寫法是捨去，TRM 說的是四捨五入，兩者在約一半的時脈上不同」。上面那張表全部是本機算的，一個硬體都不需要。

「48 MHz」是以文件為準的補充——樹莓派韌體 init_uart_clock 的預設值，本專案尚無實機可驗，而且 config.txt 改得動它。它在這裡的角色只是「一個真實存在的分岔例子」，不是論證的基礎。把它換成 9 MHz，結論一模一樣。

這正是這個專案兩種引用要分開標的原因：實測的寫數值與量法，文件的只寫「文件說什麼、還沒驗」。混在一起，讀者會以為整段都驗過了。

誤差 0.04% 對 UART 無害，所以捨去版不是 bug —— 但註解不該讓人以為它是標準算法。

改成整數形式的四捨五入：

div64 = (clk * 8 / baud + 1) / 2

（×8 再 +1 除以 2，就是 ×4 之後 +0.5 取整。）

6三個設計選擇

位址放 platform.h

QEMU virt      PL011 @ 0x0900_0000    時脈 24 MHz（device tree 寫死）
樹莓派 4        PL011 @ 0xFE20_1000    時脈由韌體決定

同一份驅動邏輯，只有位址不同。 集中在一個檔案，M9 就是新增一份 platform.h。

但「驅動完全不用改」是句過頭的話

移植到 Pi 4 至少還有兩件事不在驅動裡：

  • GPIO 腳位 muxing：晶片上的接腳不夠用，所以同一根腳可以「切換」成不同功能——UART、I2C、SPI、或單純的開關。這個切換叫 muxing（multiplexing，多工），每種功能有個編號叫 ALT0、ALT1⋯。BCM2711 的 GPIO 14/15 預設不是 UART，要設成 ALT0 才會真的接到腳位上。不做的話 —— 驅動一切正常，畫面全黑。
  • 時脈不是固定值：Pi 4 的 PL011 時脈由韌體（config.txt 的 init_uart_clock）決定，不像 QEMU 這樣寫在 device tree 裡。所以第 5 節那個「48 MHz」是韌體預設值，不是硬體常數——platform.h 的 UART0_CLK_HZ 到 M9 要填什麼，得上板量過才知道。

第一版的註解寫「the driver itself must not need editing」，讀起來像「改三個數字就好」。改成有提到這兩件事 —— 一個看起來完整的抽象層，比一個明說有缺口的抽象層危險。

\n 的轉換放在 uart_putc，不放 uart_puts

終端機收到 \n（換行）只會往下移一行，不會回到最左邊。要回最左邊得送 \r（歸位）。少了它，第二行會從第一行結尾的位置開始，畫面變成階梯狀。

第一版把轉換寫在 uart_puts 裡，結果是：

uart_puts("\n")   →  0d 0a   ✅
uart_putc('\n')   →  0a      ❌ 裸的換行

下一包就會撞到 —— printf 幾乎一定是逐字元呼叫 uart_putc，那時 printf("...\n") 就會輸出裸 LF，而症狀看起來像「終端機壞了」。

所以轉換搬進 uart_putc，讓它成為唯一出口；真正寫暫存器的 uart_putc_raw() 藏在後面。

RXE 沒有寫進去

CR 只設了 UARTEN | TXE，沒有 RXE（接收啟用）。

因為現在沒有任何東西會讀 —— 沒有 uart_getc()、沒有中斷。輸入 echo 是 M2 的第四包，那個 commit 自然會帶來加它的理由。

所以實測 CR = 0x101，不是 0x301。

7C 語言：這些寫法為什麼是這樣

M2 是第一個有 C 的里程碑，也是第一個有標頭檔的。這一節把新出現的 C 寫法一次講完——每一條都對應到 include/ 或 drivers/ 裡真的存在的一行。

標頭檔：#ifndef 三行是幹嘛的

#ifndef MMIO_H      如果還沒定義過 MMIO_H
#define MMIO_H      就定義它
...
#endif

叫 include guard（引入守衛）。#include 是純文字貼上，同一個檔被貼兩次就會「函式重複定義」而編譯失敗。有了守衛，第二次進來時 MMIO_H 已存在，整段跳過。

但這個專案現在拿掉守衛也不會爆

實測把五個標頭（mmio.h、platform.h、uart.h、string.h、printf.h）的 #ifndef 全部刪掉，四個 .c 照樣零警告編過——因為五個標頭互不 include，目前沒有任何一條會繞回同一個檔的路徑。

它現在是「便宜的保險」，不是「拿掉會壞的東西」。真正需要它的那天是：某個標頭開始 include 另一個標頭。

這裡本來預測「M2 的下一包 lib/string.c 大概就會是那天」——預測錯了。 lib/string.c 與 lib/printf.c 都寫完了，五個標頭仍然互不 include： string.h 只 include 系統的 <stddef.h>，printf.h 一個都不 include。 拿掉守衛，現在仍然 exit 0。

為什麼會猜錯？我當時想的是「函式一多，標頭之間自然會互相引用」。但這個專案的標頭都很扁—— 每個檔只宣告自己那組函式，型別一律從系統標頭來。會逼出 include guard 的不是「檔案變多」，是「出現共用的自訂型別」： M4 的中斷會有一個 struct irq_desc，M7 的 context switch 會有 struct task， 那種東西一定得放進某個標頭讓別人 include。那才是那一天。

明明 -nostdlib，為什麼能用 <stdint.h>？

因為它是 freestanding 標頭。即使沒有標準函式庫，編譯器也必須提供這幾個：

關鍵是它們只有型別和巨集，沒有任何函式——不需要任何東西被連結進來。

memcpy 就不一樣了。但它不是編不過——#include <string.h> 照樣過，因為交叉編譯器的搜尋路徑上有 glibc 的標頭。它死在連結：

uintptr_t：為什麼不用 void *

static inline void mmio_write32(uintptr_t addr, uint32_t value)

uintptr_t 是「大到能裝下一個指標的整數型別」，AArch64 上是 64 位元。

用整數而不是指標，是因為我們拿到的本來就是一個數字，而且要對它做算術：

mmio_write32(UART0_BASE + UART_CR, 0);
             ↑ 0x09000000 + 0x30，這是整數加法

如果參數宣告成 void *，+ 0x30 在標準 C 裡是違反約束（constraint violation）——標準要求編譯器出診斷訊息。GCC 把它當擴充功能，而且預設一句話都不說：

-Wall -Wextra -Werror        完全沉默
-pedantic                    warning: pointer of type 'void *' used in arithmetic
-pedantic-errors             error

「違反約束」和「未定義行為」不一樣：前者標準要求編譯器告訴你，後者標準完全不管會發生什麼。這裡是前者，只是我們沒開 -pedantic，所以沒人告訴我們。

*(volatile uint32_t *)addr 怎麼念

由內往外拆：

addr                        一個 64 位元整數
(uint32_t *)addr            把它當成「指向 32 位元的指標」
(volatile uint32_t *)addr   而且那個目標是 volatile
*(volatile uint32_t *)addr  去那個位址讀／寫
volatile 貼在星號哪一邊 
volatile uint32_t *p    ← p 指向的東西是 volatile   ✅ 我們要這個
uint32_t * volatile p   ← p 這個變數自己是 volatile ⚠️ 保護錯對象

星號左邊修飾「被指的東西」，右邊修飾「指標自己」。 寫錯的話編譯器不會抱怨——它是合法的 C。

實測三種寫法，各連寫三次 *p，-O2：

volatile 在左（目標）    3 條 str   ✅ 正是我們要的
volatile 在右（指標）    4 條 str   ← 沒少，但多了讀指標的雜務
兩邊都沒有              1 條 str   ← 前兩次被合併掉了

所以貼右邊不是「完全沒用」，是「用錯地方而恰好有副作用」：指標自己 volatile → 每次都得重新讀指標 → 目標也就跟著每次重讀。它靠副作用達成了目的，代價是多出來的指令，而且換個寫法（例如把指標存進區域變數）保證就沒了。

依賴副作用得到的正確，跟寫對是兩件事。

static inline 放在標頭裡

先講為什麼會有這個處境。一般函式是「宣告放標頭、定義放 .c」：

mmio.h   void mmio_write32(uintptr_t, uint32_t);   只是宣告
mmio.c   void mmio_write32(...) { ... }            定義在這

但 mmio_write32 只有一行。為它開一個 .c 檔、還要付一次函式呼叫的代價，划不來。所以定義直接寫進標頭。

代價是：#include 是純文字貼上，那份定義會被複製到每一個 include 它的 .c 裡。兩個關鍵字各處理這個複製帶來的一個麻煩。

麻煩一：撞名 → static 解決

pl011.c  貼一份 mmio_write32
uart2.c  貼一份 mmio_write32
連結器： multiple definition of 'mmio_write32'   ❌

static 的意思是「這一份只有我這個 .c 看得到」，於是兩份各自獨立，不會撞。

代價是真的產生兩份程式碼——但函式這麼小，-O2 會展開掉，代價是零。

麻煩二：沒用到會被唸 → inline 解決

這才是 inline 在這裡的真正作用，跟「展開比較快」無關。

標頭被貼進每個 .c。如果某個 .c 只寫不讀，mmio_read32 就成了「定義了卻沒人用的 static 函式」。實測同一份程式碼，只換旗標：

（什麼都不加）    編過，一句話都沒說
-Wall             編過，但有警告
                  warning: 'r32' defined but not used [-Wunused-function]
-Wall -Werror     ❌ 建置失敗
                  error: 'r32' defined but not used [-Werror=unused-function]
-Werror 沒有做任何新檢查

它只是把所有警告升級成錯誤。上面三行的訊息文字幾乎一樣，只有 warning 變成 error。

所以完整的因果鏈有三段：

1. 定義在標頭      →  每個 .c 都貼一份
2. 某個 .c 沒用到  →  -Wall 裡的 -Wunused-function 出來唸
3. 我們有 -Werror  →  唸變成擋

三段裡拿掉任何一段，建置都會過。 inline 是在斷第 2 段——它等於跟編譯器說「這函式住在標頭裡，沒人用是正常的」。

但今天拿掉 inline 也不會壞 
誰 include 了 mmio.h：  只有 drivers/uart/pl011.c
它用到 mmio_write32：  6 次
它用到 mmio_read32：   1 次

把 static inline 改成 static，整個核心重編  →  exit 0

只有一個檔 include，而且兩個函式都用到了，所以第 2 段觸發不了。

照鐵則五的判準，inline 現在不是承重的。但它離承重只差一步——下一個 include mmio.h 卻只寫不讀的 .c 出現，建置就會斷。

這裡本來預測「M2 的下一包 lib/ 很可能就是」——也錯了。 實測把 mmio.h 的 static inline 改成純 static，加了 string.c 和 printf.c 之後仍然 exit 0。 原因很簡單：lib/ 底下沒有任何一個檔 include mmio.h—— 到今天為止，mmio.h 的唯一使用者還是 drivers/uart/pl011.c。

兩個預測都猜「下一包」，兩個都落空，原因也一樣：我用「程式碼會變多」去推「相依會變複雜」， 但這兩件事沒有必然關係。 lib/ 是純計算，不碰硬體，所以它跟 MMIO 那一層完全沒有接觸面。 真正會踩到的是 M4 —— 中斷處理常式要讀 GIC 的暫存器，那時才會出現第二個 include mmio.h 的檔。

三種寫法的下場

關鍵字作用不寫會怎樣
static inline
我們用的		每個 .c 各自一份，不對外公開；建議展開—
兩個都不寫一個普通的全域函式兩個 .c include 同一個標頭 → multiple definition of 'mmio_write32'

最後那一列是重點：inline 單獨用，是給「另有一份外部定義」的情況準備的。編譯器可以選擇不展開，那時就得去找那份外部定義——而我們沒有，於是連結器找不到。

這就是為什麼慣用寫法是 static inline：static 保證每個 .c 都有自己的一份，展不展開都不會缺人。

而且那一列是 -O 相依的

-O2 下同一份程式碼連結得過——因為編譯器真的展開了，根本不需要那份外部定義。

所以「只寫 inline 會壞」這句話，只在 -O0 成立。這正是第 12 節精髓第 2 條說的：「拿掉它現在會壞嗎」要連編譯旗標一起問。

順帶：inline 對「要不要展開」真的只是建議

實測 -O0 下它完全沒展開——mmio_write32 變成一個真的函式，而且是這樣：

<mmio_write32>:
    sub  sp, sp, #0x10      挖 16 bytes
    str  x0, [sp, #8]       把參數存到堆疊
    str  w1, [sp, #4]
    ldr  x0, [sp, #8]       ⋯又立刻讀回來
    ldr  w1, [sp, #4]
    str  w1, [x0]           ★ 只有這條真的碰硬體
    nop
    add  sp, sp, #0x10

九條指令，八條是雜務。 存下去又馬上讀回來，純粹因為 -O0 不做任何優化。-O2 下整個函式會被展開成那一條 str。

(1u << 5)：那個 u 和那對括號

#define FR_TXFF   (1u << 5)

u： 1 是有號 int，有號數左移到最高位是未定義行為（1 << 31）。我們現在最多移 8 位（CR_TXE）還安全，但旗標是位元樣式、不是數量，本來就該用無號。

括號： 這條我第一版寫反了，值得留下來。

直覺會說「少了括號，x & FR_TXFF 會變成 (x & 1u) << 5」。實測不是。

#define M_NOPAR 1u << 5
#define M_PAR  (1u << 5)

x & M_NOPAR      →  and   w0, w0, #0x20   ┐ 完全一樣
x & M_PAR        →  and   w0, w0, #0x20   ┘
(x & 1u) << 5    →  ubfiz w0, w0, #5, #1  ← 這是另一回事

<< 的優先序高於 &，所以 x & 1u << 5 本來就等於 x & (1u << 5)。位元遮罩這個用法，加不加括號都對。

括號真正救到的是加減法——它們的優先序比 << 高：

M_NOPAR + 1   →   1u << 5 + 1   →   1u << 6   =  64   ❌
M_PAR   + 1   →   (1u << 5) + 1              =  33   ✅
但這個坑在本專案掉不進去

-Wparentheses 在 -Wall 裡，而我們有 -Werror：

error: suggest parentheses around '+' inside '<<' [-Werror=parentheses]

所以那個 64 不是會安靜發生的陷阱，是硬錯誤。真正救到的不是「我記得加括號」這個習慣，是 -Wall -Werror。

（對照上面 void * 那條：同樣是「標準說不行」，那條在 -Wall -Wextra -Werror 下完全沉默，要 -pedantic 才叫。旗標管得到哪些、管不到哪些，沒有規律，只能一條一條試。）

所以規則還是「巨集內容用括號包起來」，但理由不是我原本寫的那個。「這條規則救了我」和「我知道它救了什麼」是兩件事——我照著規則寫對了程式碼，卻把理由講反了，直到有人去編一次才發現。

（順帶：#define UART_DR 0x00 那六個沒有括號，因為單一 token 不可能被拆開。需要括號的是「裡面有運算子」的巨集。）

UL 後綴：運算寬度由運算元決定

#define UART0_CLK_HZ    24000000UL

規則是：運算的寬度由運算元決定，不是由你要存進去的變數決定。

uint64_t x = a * b;    ← a、b 都是 32 位元的話，
                          乘法照樣在 32 位元裡溢位，然後才把壞掉的結果放大
但這裡防溢位的不是 platform.h 的 UL

我原本以為是。實際的算式是：

UART0_CLK_HZ * 8UL / UART0_BAUD

那個 8UL 已經把整式拉到 64 位元了——只要有一個運算元是 unsigned long，另一邊就會被提升上去。

實測：把 platform.h 的 UL 全部拿掉、時脈換成 600 MHz（會讓 32 位元溢位的量級）：

CLK_INT * 8UL / BAUD  →  20833   ✅ 正解，UL 拿掉也沒事
CLK_INT * 8   / BAUD  →   2192   ❌ 兩邊都拿掉才壞
                             warning: integer overflow … results in '505032704'

所以 platform.h 的 UL 目前是備而不用的——它的價值在「下一個人抄這個巨集去寫別的算式」時才兌現。

這一則的教訓不在 UL，在「我以為某個東西在保護我，但保護我的其實是別的地方」。要確認一個防護有沒有作用，只有一個方法：拿掉它，看會不會壞。

(uint32_t)(unsigned char)c：為什麼要兩層

mmio_write32(UART0_BASE + UART_DR, (uint32_t)(unsigned char)c);

char 的正負號是實作定義的——C 標準沒有規定，各平台自己決定。

如果 char 是有號的，c = 0x80（128）會被當成 −128，放大時做符號延伸：

(uint32_t)c                  →  0xFFFFFF80   ❌ 高位全變 1
(uint32_t)(unsigned char)c   →  0x00000080   ✅

先轉 unsigned char 把符號問題斷掉，再放大。

但在這台機器上兩者相同

實測 AArch64 的 char 是無號的：char c = -1; return c < 0; 編出來是 mov w0, #0——編譯器直接算出「不可能小於 0」。

所以 bad() 和 good() 兩個函式編出來一模一樣，都是 and w0, w0, #0xff 加 ret。

那個轉型是為了可攜性，不是為了這台機器。 同一份程式碼搬到 x86（char 有號）就會分岔——而這種 bug 只在字元 ≥ 0x80 時才出現，通常是別人送中文進來的那天。

while (...) { ; }：那個孤獨的分號

while (mmio_read32(UART0_BASE + UART_FR) & FR_TXFF) {
    ;
}

迴圈體是空的——我們只是要一直讀到 TXFF 變 0。

為什麼不寫 while (...);？因為那個分號看起來像打錯字：

while (cond);        ← 這是空迴圈，還是不小心多打一個分號？
    do_something();  ← 讀者會以為這行在迴圈裡

寫成 { ; } 是明確表態：這裡故意什麼都不做。

*s++ 的優先序

uart_putc(*s++);

++ 綁得比 * 緊，所以它是 *(s++)：

1. 取 s 目前的值當作結果  →  傳給 *
2. s 自己 +1
3. 效果：讀出現在指的字元，然後指標往後移一格

寫成 (*s)++ 意思完全不同——那是「把字元的值加一」。而 uart_puts 的參數是 const char *s，所以它根本編不過：

error: increment of read-only location '*s'

const 在這裡把一個「要到 M5 開了 MMU 才會爆」的問題，提前到編譯期擋掉了。

const char *s：const 在星號哪一邊

const char *s     內容唯讀，但 s 可以移動   ✅ 我們要這個
char * const s    s 不能移動，但內容可以改

uart_puts 裡有 *s++（移動指標），所以 const 必須在左邊。

而且它讓呼叫端安全：uart_puts("Hello") 的字串在 .rodata，const 讓編譯器在 M5 之前就先擋下寫入。

void uart_init(void)：那個 (void) 不能省

void uart_init(void);    明確說「沒有參數」
void uart_init();        在 C 裡意思是「參數不詳」❌

C++ 兩者相同，C 不是。寫成 () 的話，uart_init(1, 2, 3) 也編得過，而且不會警告。

static 在 C 裡有兩種意思

放在哪意思本專案的例子
檔案層級不對外公開，別的 .c 看不到static void bump(void)
函式裡面這個區域變數的壽命是整個程式（還沒用到）

同一個關鍵字，兩件事，看位置決定。nm 的大小寫就是在報第一種：

void kernel_main(void)               →  T kernel_main    大寫，全域
static void bump(void)               →  t bump           小寫，static
static unsigned long boot_counter;   →  b boot_counter
kernel_main 是唯一不能加 static 的

因為 boot.S 要 bl kernel_main。組語看不到 C 的作用域規則，它靠連結器把名字配對起來——加了 static，那個名字就不會出現在全域符號表，連結會失敗。

這是 C 和組語唯一的接縫。

「沒初始化就用」為什麼在這裡沒問題

boot_counter 沒給初始值，bump() 卻直接對它 ++：

static unsigned long boot_counter;
static void bump(void) { boot_counter++; }

「沒初始化就用」的警覺是對的，但那個直覺只適用於區域變數。C 把變數分成兩種「儲存期」，規則完全不同：

誰沒給初始值時x++
自動儲存期函式裡的區域變數是垃圾（上一個人留在堆疊上的東西）❌ 未定義行為
靜態儲存期全域變數、static 變數保證是 0（C 標準規定）✅ 合法

編譯器自己就把兩者分開了。同一份程式碼，只有區域變數那個被唸：

unsigned long f_local(void)  { unsigned long x; x++; return x; }
unsigned long f_static(void) { g_static++;      return g_static; }

warning: 'x' is used uninitialized [-Wuninitialized]
（g_static 一句話都沒說）
順便看一眼「未定義行為」長什麼樣

那兩個函式編出來的指令差很多：

<f_local>:                  <f_static>:
    mov x0, #0x1                ldr x0, [x1]     真的去讀
    ret                         add x0, x0, #1
                                str x0, [x1]     真的寫回
                                ret

f_local 被編譯器直接算成 1。 反正那是垃圾值，它愛怎麼算都行——這就是未定義行為的樣子：不是當掉，是編譯器有權亂來。

f_static 則老老實實讀-加-寫，因為它知道那個值有意義。

但那個「保證是 0」，在這裡是我們自己兌現的

C 標準規定靜態儲存期的變數要是 0。這是語言層面的通則，任何符合標準的實作都得做到。 但「誰去做」不是通則——每個平台不一樣：

平台誰把 .bss 清成 0
Linux 上的一般程式核心的 ELF 載入器
有些嵌入式工具鏈C 執行期啟動碼（crt0）
這個專案沒有人——所以 boot.S 自己做

怎麼證明？兩個方向

正面：那些 0 一定是執行時生出來的，不在檔案裡。 拿一個宣告了 8 MB .bss 的 Linux 程式來看：

執行檔大小 = 641,104 bytes
.bss 大小  = 8,410,768 bytes   ← 比整個檔案還大，而且型別是 NOBITS

8 MB 的 0 沒有存在檔案裡（存了也是浪費）。所以一定有人在載入時把它生出來。

反面：把那個「人」拿掉，就不是 0 了。 這是我們自己做得到的實驗——把 boot.S 的清零迴圈整段刪掉，開機前先用 -device loader 把 boot_counter 塞成 0xcafe1234：

有清零迴圈   進 kernel_main 時 boot_counter = 0x0
拿掉迴圈     進 kernel_main 時 boot_counter = 0xcafe1234

這證明它不是自動的。 C 的保證是真的，但在裸機上是我們自己實現的——少了那 6 行組語，boot_counter++ 就變成「把一個垃圾值加一」，跟區域變數的情況一模一樣。

這也是為什麼 make debug 要檢查它：它是那個保證有沒有被兌現的唯一證據。

沒給初始值 → .bss；給了非零 → .data

實測三種寫法落在哪：

static unsigned long a;      →  nm 顯示 b   .bss
static unsigned long b = 0;  →  nm 顯示 b   .bss（明著寫 0 也一樣）
static unsigned long c = 7;  →  nm 顯示 d   .data

C 保證未初始化的全域變數是 0，所以 = 0 是多餘的，編譯器一樣放 .bss（只記大小，不存內容）。

只有給非零初始值才會進 .data——那時檔案裡真的要存那個數字。這就是為什麼連結器腳本的註解說「目前還沒有 .data」：整個核心沒有任何全域變數給了非零初始值。

同一個 volatile 的道理，start.c 還沒套用

這一節花了很多篇幅講 volatile 對 MMIO 為什麼必要。但 start.c 裡那個 boot_counter 沒有 volatile，而它是 make debug 用來證明「.bss 被清了」的唯一證據。

實測用 -O2 重編整個核心：

<kernel_main>:            （略去序言兩條與位址運算）
    bl   uart_init
    bl   uart_puts
    b    .                  ← 死迴圈，就這樣

nm | grep -E 'boot_counter|bump'   →  零個結果

變數和函式連符號都不存在了。 編譯器的推論完全正確：boot_counter 是 static（外面看不到）、只被加一從來沒被讀、所以整條計算是死的，連同 bump() 一起刪掉。

那一天 make debug 的第三個檢查會變成這樣（實跑 -O2 版本量到的）：

SP        = $1 = 0x40010200
EL        = $2 = 1
bss 清了嗎 = No symbol table is loaded.  Use the "file" command.

不是壞掉，是證據消失。 前兩行照樣正確，只有第三行沉默地失去意義。

照鐵則五的判準，現在（-O0）加 volatile 不會改變任何指令，所以還不該加。但這是一則已經寫在牆上的預告：真的開 -O2 的那個 commit，除了 mmio.h 之外，還得處理這個見證變數。

8沒有 libc：memset／memcpy／strlen／strcmp 自己寫

到這裡為止，M2 的程式碼只做一件事：把字元一個一個寫進 DR。 第 7 節把那些 C 寫法逐條講完了，下一步是把 printf 做出來——但在那之前， 有一個更基本的東西不見了。

這個核心沒有 C 標準函式庫。 Makefile 從 M0 起就帶著 -nostdlib（M0 教材量過拿掉它的下場：crt1.o 被連進來， _start 重複定義，同時冒出 undefined reference to `main'）， 它的意思不只是「不把 libc 連進來」，而是 那些函式在這個環境裡根本不存在——寫下去會得到 undefined reference，連結直接失敗。

本節要補的是其中四個。它們是 docs/PROJECT_PLAN.md 在 M2 列出來的， 也是接下來真的會用到的四個：

函式做什麼誰會用到
memset把一塊記憶體全部填成同一個位元組M5 的分頁表要先清成 0
memcpy把一塊記憶體複製到另一塊M5 的驗收標準：搬一大塊記憶體，比較開 cache 前後的耗時
strlen算字串長度第 9 節的 printf，做 %s 的寬度對齊
strcmp比較兩個字串M8 的 shell 比對指令名稱

四個裡面只有 strlen 在本里程碑內就有呼叫者（第 9 節的 %s 寬度對齊）。 另外三個是使用者決定提前一起寫的，這偏離了「只寫現在就有作用的東西」那條規矩。

代價是這個：沒有呼叫者的函式，正確性只能靠論證，不能靠「開機有沒有印出東西」來檢查。 本節最後一小節（strcmp 的 unsigned char）就是這樣一個例子—— 那個轉型在這台機器上拿掉也不會壞，你永遠不會從執行結果看出它的必要性。

這一節講的不是「怎麼寫一個 memcpy」——那是大一的作業。 講的是在 MMU 還沒開的裸機上寫，跟在 Linux 上寫有什麼不一樣。 真正跟裸機有關的差別只有一個，它決定了搬運迴圈怎麼寫（下一小節）； 其餘四小節講的是 ISO C 本來就有的坑，只是在這裡沒有 libc 幫你擋、也沒有作業系統在你越界時攔你。

為什麼是逐 byte 搬

一般的 memcpy 會盡量一次搬 8 個 byte，快一倍。我們不這樣寫，理由不是懶，是架構規定。

AArch64 規定：stage 1 位址轉換關閉時，所有記憶體一律視為 Device-nGnRnE。

「stage 1」是什麼

就是我們平常講的 MMU：把程式看到的虛擬位址翻成實體位址那一層。ARM 叫它 stage 1， 是因為虛擬化的機器還有第二層：客體作業系統以為自己翻完了，Hypervisor 再把結果翻一次，那層叫 stage 2。

我們是 EL1 的核心，沒有 Hypervisor，所以只會碰到 stage 1。這份教材裡「stage 1 轉換」和「MMU」講的是同一件事 —— 用 ARM 的詞是為了對得上手冊，因為手冊那句話就是這樣寫的。

由 SCTLR_EL1 的 bit 0（M） 開關，M5 才會把它設成 1。

Device-nGnRnE 是什麼

ARM 把記憶體分成兩大類。Normal 是一般的 RAM，CPU 可以隨意重排、合併、預取。 Device 是給周邊裝置用的，每一次存取都算數，不可以動手腳 —— 就是第 3 節講 volatile 時那個道理，只是這次是 CPU 層級而不是編譯器層級。

後面四個字母是四個開關，都是「不准」：

nG   non-Gathering                不准把兩次存取合併成一次
nR   non-Reordering               不准調換順序
nE   no Early write acknowledgement   不准提早回報「寫好了」

nGnRnE 是最嚴格的一檔，全部都不准。而它還附帶一條：不允許未對齊存取。

MMU 要到 M5 才開。在那之前整片記憶體都是 Device，所以一個對著奇數位址做 8-byte 讀取的 memcpy，在真硬體上會產生 Alignment fault。

但這句話要說準確。 Device 記憶體禁的是「未對齊」，不是「一次 8 bytes」。

一個先把兩端對齊、中間 8 bytes 搬、尾巴補 byte 的 memcpy，架構上完全合法。 選逐 byte 的真正理由是：它不需要那份對齊處理。而那份處理要處理的正是「未對齊」這件事， 而未對齊在 QEMU 上預設驗不出來 —— 見第 10 節直覺 8。

restrict：把約定寫進型別

void *memcpy(void *restrict dst, const void *restrict src, size_t n);

restrict 是 C99 加的關鍵字，意思是「我保證這兩個指標指向的區域不重疊」。

ISO C 規定 memcpy 的來源與目的不得重疊，重疊是未定義行為。 處理重疊是另一個函式 memmove 的工作。

為什麼不乾脆讓 memcpy 也處理重疊、比較安全？因為那會讓讀者學到一件錯的事。 真實世界的 memcpy（glibc、musl、Linux kernel）都不處理重疊， 你在這裡養成的習慣，換個環境就會炸。restrict 把這個約定從註解升級成型別的一部分。

while (n-- > 0)，不是 while (--n)

這是本節最容易寫錯的一行。n 的型別是 size_t，無號。

n = 0 時：
  n-- > 0    先拿 0 去比較 → 0 > 0 為假 → 迴圈不跑    ✓
  --n        先減 → 0 - 1 = 0xffffffffffffffff → 迴圈要跑 16 EB    ✗
                    （EB = exabyte，1 EB 約十億 GB）

症狀是畫面停住，沒有任何錯誤訊息。 從症狀完全反推不回原因。

memset 的 c 為什麼是 int

void *memset(void *dst, int c, size_t n);

參數是 int，但實際只有低 8 位元會被寫進去。標準就是這樣定義的。所以：

memset(p, 0x1ff, 1);   →   p[0] 變成 0xff，不是 0x1ff

實作裡明確寫一次 (unsigned char)c，讓這個截斷看得見，而不是靠隱式轉換偷偷發生。

strcmp 為什麼要轉 unsigned char

標準規定 strcmp 以 unsigned char 比較。第 7 節量過：AArch64 的 char 本來就是無號的。 那這個轉型不就是多餘的？

有轉型   AArch64 預設        PASS
         -fsigned-char       PASS
無轉型   AArch64 預設        PASS      ← 完全看不出差別
         -fsigned-char       FAIL      strcmp("\x80", "\x01") 回傳 -129

x86 的 char 是有號的。同一份程式碼，0x80 在 AArch64 上是 128（大於 0x01）， 在 x86 上是 −128（小於 0x01），比較結果的正負號相反。

這是本里程碑最值得記的一種 bug：它在你的機器上永遠不會出現。

9printf：可變參數，撞上一顆關著的浮點單元

上一節補完了四個函式，其中 strlen 是為了這一節才寫的。現在做 printf。

為什麼需要它：目前核心只有 uart_puts，而它只能印寫死的字串。 要印「ESR_EL1 現在是多少」就沒轍了——那是一個執行時才知道的數字。 M3 的例外處理整包都靠這個：例外發生時，唯一能告訴你「發生什麼事」的就是那幾個暫存器的值。

但這一節真正的內容不是格式化字串怎麼解析。是 printf 一寫完， 核心就當掉了——而原因跟 printf 的邏輯完全無關。 下面照著當時的順序走一遍：先看可變參數在 AArch64 怎麼傳，那是當機的起點。

（先說清楚：這個 trap 是在一份臨時的自我測試裡撞到的。它為什麼也是交付版的問題—— 以及它一度不是——見第 10 節直覺 10 與直覺 11。）

可變參數在 AArch64 怎麼傳

AAPCS64（ARM 64 位元的呼叫慣例）規定：

前 8 個整數參數      x0 – x7
前 8 個浮點參數      q0 – q7      ← 注意這一行
多出來的                 堆疊
q0 和 v0 是同一個暫存器

AArch64 有 32 個 128 位元的浮點／向量暫存器。同一顆暫存器有好幾個名字，差別只在你打算用它的幾個 bit：

v0   當成向量看（例如 4 個 32-bit 一起算）
q0   當成完整的 128 bit 看     ← 存／取整顆時用這個名字
d0   只用低 64 bit（double）
s0   只用低 32 bit（float）
h0 / b0   低 16 / 低 8 bit

所以下面說「參數走 q0–q7」（8 個）和後面算成本說「v0–v31」（32 個）沒有矛盾： 傳參數只用前 8 顆，但要保存狀態時 32 顆都得存。

C 層的三個工具：va_list / va_start / va_arg

C 不讓你直接讀 x0–x7。<stdarg.h>（第 7 節列的自由環境標頭之一） 提供三個東西把那件事包起來：

va_list ap;              一個「走到哪了」的游標
va_start(ap, fmt);       初始化：從 fmt 的下一個參數開始
x = va_arg(ap, int);     取出一個，型別要自己講，游標往前
va_end(ap);              收尾

va_arg 的第二個參數是型別，不是值——編譯器要靠它決定「這次該從游標讀幾個 byte」。 講錯型別不會有警告，只會讀錯位置，後面全跟著錯。這就是後面 %c 為什麼要寫 va_arg(ap, int) 而不是 char 的原因。

底下講的是這三個巨集在 AArch64 上實際被編譯成什麼——那才是當機的來源。

printf 在執行到 va_start 之前，並不知道格式字串裡會要幾個參數、什麼型別。 所以 -O0 下編譯器產生的函式序言（prologue，函式開頭那段固定的準備動作）會先把這些暫存器存進堆疊上一塊叫「暫存器儲存區」的地方（實際存的是 x1–x7 與 q0–q7，共 15 個；x0 是格式字串本身，另外存）， 之後 va_arg 再從那裡一個一個拿。

那裡面有 8 個是浮點暫存器。即使你的格式字串裡一個 %f 都沒有。

「-O0 下」這四個字是關鍵：-O1 以上 gcc 會發現那 8 條存進去沒人讀而刪掉。本專案目前沒設 -O，所以就是 -O0。詳見第 10 節直覺 11。

然後核心就當掉了——在印出任何字元之前

先講兩個詞：trap 與 0x200

問題在這裡：EL1 在重設狀態下根本不准執行 FP/SIMD 指令。 那 8 條 str q 一執行就會被攔下來。下面先解釋「被攔下來」到底是什麼意思。

trap（攔截）＝ CPU 執行到某條它不被允許執行的指令時，不執行它， 改成強制跳到一個固定的地方。這跟 ARM 說的「同步例外」是同一件事 —— 同步，是因為它由某一條指令當場引發， 不像中斷那樣隨時會來。

跳去哪？跳到例外向量表，基底位址放在 VBAR_EL1 這個暫存器裡。 向量表分成 16 個入口，每個佔 0x80。「從 EL1 掉進 EL1 的同步例外」 落在 基底 + 0x200——精確地說，是「同一個 EL、而且用 SP_EL1」那一組； 同樣是同 EL 的同步例外，如果當時用的是 SP_EL0，入口會是基底 + 0x000。 我們現在是用 SP_EL1，所以是 0x200——但那不是 boot.S 設的，見第 10 節直覺 12。 M3 要親手蓋這張表，那時 16 個入口都會碰到。

VBAR_EL1 的重設值是 0（M1 量過），而我們還沒寫過它 —— M3 才會做向量表。 所以 0 + 0x200 = 0x200，那裡是一片沒有程式的記憶體。CPU 跳過去，執行到的東西不是我們的核心， 於是後面每一行程式都不會再跑。這就是「開機一個字都印不出來」的原因：kernel_main 先呼叫 uart_init()（它不印字）， 接著第一個 printf 就在送出任何字元之前被 trap 走了。

CPACR_EL1 是控制「EL1／EL0 能不能碰浮點與 SIMD」的暫存器，其中 FPEN 是 bits[21:20]：

FPEN意思
0b00EL0 和 EL1 碰 FP/SIMD 一律 trap　← 重設值
0b01只有 EL0 trap
0b10同 0b00：EL0 與 EL1 都 trap
0b11都不 trap

我們從來沒設定過它，所以它是 0b00。實測（核心自己 mrs 讀出來印）：

CPACR_EL1 = 0000000000000000
calling printf...
（沒有下一行了）

用 GDB 在 0x200 設中斷點，抓到的現場：

$pc      = 0x200          同 EL 的同步例外進入點
$ESR_EL1 = 0x1fe00000
$ELR_EL1 = 0x40000618     x/1i → <printf+40>: str q0, [sp, #112]

出事的正是序言存 q0 那一條。前面存 x1–x7 的都沒事（x0 更早、在 [sp,#24]）：

400005f0 <printf>:
  400005f0:  a9ad7bfd   stp x29, x30, [sp, #-304]!
  ...
  40000610:  f90093e6   str x6, [sp, #288]      整數暫存器，過
  40000614:  f90097e7   str x7, [sp, #296]      整數暫存器，過
  40000618:  3d801fe0   str q0, [sp, #112]      ← trap
  4000061c:  3d8023e1   str q1, [sp, #128]
  40000620:  3d8027e2   str q2, [sp, #144]

怎麼讀 ESR_EL1

ESR_EL1（Exception Syndrome Register）是「這次例外是為什麼」的答案，最重要的是最高 6 位元的 EC（Exception Class）：

0x1fe00000 = 0001 1111 1110 0000 0000 0000 0000 0000

EC   = bits[31:26] = 0b000111 = 0x07   FP/SIMD 被 CPACR_EL1.FPEN 擋下
IL   = bit 25      = 1                32 位元指令
CV   = bit 24      = 1                下面的 COND 欄位有效
COND = bits[23:20] = 0b1110           AL（無條件執行）

想自己驗算的話會卡在這裡：0x07 << 26 = 0x1C000000，跟 0x1FE00000 差了 0x02E00000。 差的就是 IL／CV／COND 這三欄。不知道它們的存在，會以為自己算錯。

兩種修法：不產生 FP 指令，還是把 FP 打開

修法代價
-mgeneral-regs-only編譯器完全不產生 FP/SIMD 指令
在 boot.S 設 CPACR_EL1.FPEN = 0b11每次中斷與 context switch 都要多存 520 bytes（見下段。這一格是論證，不是實測 —— M4 的中斷與 M7 的 context switch 都還不存在）

選了旗標。理由是「誰付錢存 FP」這個問題還沒解決：

整數狀態   x0–x30 + sp + pc                      264 bytes
FP 狀態    v0–v31（各 128 bit）+ FPSR + FPCR     520 bytes

多存 FP 之後，每個執行緒的狀態從 264 變成 784 bytes —— 接近三倍
（FP 那份本身是整數那份的 1.97 倍）

context switch 一秒幾百次，多存 520 bytes 還能忍。但中斷處理常式一秒可能幾萬次 —— 只要處理常式裡有一條 FP 指令，它就會蓋掉被中斷的那個執行緒的 v 暫存器， 於是每一次進中斷都得先存那 520 bytes，即使那次中斷根本沒碰 FP。

Linux 的做法是：核心可以用 FP，但必須包在 kernel_fpu_begin() 與 kernel_fpu_end() 中間，由那對函式負責存檔。我們沒有那對函式，也還沒有中斷， 所以整個關掉，把這個問題留到 M7 真的有 context switch 時再面對。

format 屬性：它擋得住什麼

int printf(const char *fmt, ...) __attribute__((format(printf, 1, 2)));
                                                        ↑  ↑
                                          格式字串是第 1 個參數
                                                    參數從第 2 個開始

加了這個屬性，gcc 會拿格式字串去型別檢查每一個呼叫點， -Werror 把不符變成建置失敗。裸機環境沒有別的東西會檢查這些。

實測它有多有效 —— 寫自我測試時，這四行讓 make 直接失敗：

printf("")           error: zero-length gnu_printf format string
printf("a%")         error: spurious trailing '%' in format
printf("%q")         error: conversion lacks type at end of format
printf("%s", NULL)   error: '%s' directive argument is null

要測這四個的執行期行為，只好把格式字串放進變數才繞得過。 這反過來證明：它只檢查字面值。 格式字串一旦是變數，保護就完全消失。

它擋不住什麼 —— 而且第一個踩到的是我自己

屬性檢查的是「型別合不合 ISO C」，不是「我們這個 printf 有沒有實作」。

旗標（- + # 空白）、精度（.n）、長度修飾字（l、hh） 全都是合法的 ISO printf。gcc 一聲不吭，而我們的解析器把它們丟進 default: 原樣印出 —— va_arg 從沒被呼叫，後面每一個參數都往前錯一格。

實測（建置零警告）：

printf("A %%016lx -> [%016lx] then [%d]\n", 0x1fe00000UL, 7);
printf("B %%-5d   -> [%-5d] then [%d]\n", 42, 7);
printf("C %%.2s    -> [%.2s] then [%d]\n", "abcdef", 7);

A %016lx -> [%lx] then [534773760]      534773760 = 0x1fe00000，是第一個參數
B %-5d   -> [%-5d] then [42]            42 跑到第二個位置去了
C %.2s    -> [%.2s] then [1073744784]   字串指標被當成十進位整數印出來
                                        （這是個 .rodata 位址，佈局相依，你跑出來會不同）

A 那一行正是這個 printf 存在的理由 —— 前面才說「M3 要印 ESR_EL1」， 而真的寫 printf("%016lx", esr) 就會印出四個字元 %lx。

所以 include/printf.h 的檔頭現在明寫：支援哪幾個、其餘會怎麼壞、以及 format 屬性為什麼擋不住。 一個「安全網」最危險的時候，是你以為它蓋住了它其實沒蓋的地方。

%s 的寬度對齊：strlen 在這裡被用到

第 8 節說 strlen 是為了這一節寫的。就是這裡。

「最小寬度」是格式規格裡數字的那一段：%5d 的意思是「至少佔 5 格，不夠的補空白」。 對數字和字串都適用：

printf("[%6s]", "hi")    →   [    hi]     不夠 6 格，左邊補 4 個空白
printf("[%2s]", "hello") →   [hello]      已經超過 2 格，不截斷

要補幾個空白，得先知道字串有多長——而「知道字串有多長」就是 strlen。 lib/printf.c 裡負責這件事的是 put_str()。

在讀它之前先認識兩個它會用到的內部函式——都是 static，只在這個檔案裡活動：

struct out { int count; };   唯一的欄位：到目前為止送出了幾個字元

static void emit(struct out *o, char c)         送一個字元，順便計數
{
    uart_putc(c);
    o->count++;
}

static void pad(struct out *o, char c, int n)   送 n 個 c；n <= 0 就一個都不送
{
    while (n-- > 0) {
        emit(o, c);
    }
}

struct out 只是一個計數器。printf 依標準要回傳「總共印了幾個字元」， 而真正送字的地方散在好幾個函式裡，所以拿一個指標一路傳下去，每送一個字就加一。 （為什麼不乾脆用全域變數？見本節最後那張設計選擇表。）

pad 的 while (n-- > 0) 跟第 8 節那個長得一樣，但安全的理由相反

第 8 節講 memset 時說：這樣寫是因為 n 是 size_t（無號）， 寫成 while (--n) 的話 n = 0 會變成 0xffffffffffffffff。

pad 的 n 是 int（有號）。而且它本來就會收到負數—— width - len 在「寬度比字串短」時就是負的。有號數不會繞回去，-3 > 0 為假，迴圈直接不跑。

同一個寫法，一邊靠「無號不能減到負的」、一邊靠「有號可以是負的」。 這也是為什麼上面 %2s 對 "hello" 那個例子不需要任何額外判斷就不會截斷。

static void put_str(struct out *o, const char *s, int width)
{
    if (s == NULL) {
        s = "(null)";        // 印字面文字，不是讀位址 0
    }

    int len = (int)strlen(s);      // ← 上一節那四個函式的第一個真實呼叫點

    pad(o, ' ', width - len);      // 補 width-len 個空白
    for (int i = 0; i < len; i++) {
        emit(o, s[i]);
    }
}

pad() 收到負數不動作，所以 width 比 len 小的時候 （上面 %2s 對 "hello" 那個例子）自然就是不補、不截斷。

那個 if (s == NULL) 為什麼在？ 前面才說 printf("%s", NULL) 會被 format 屬性當場擋下、make 直接失敗——照鐵則五「拿掉現在會壞嗎」， 它應該是死碼。但屬性只檢查字面值的格式字串：只要格式字串是變數， 或那個 NULL 是執行時才算出來的指標，屬性一個字都不會說。 真讓它讀位址 0，M5 開了 MMU 之後就是一次 fault。這一行擋的是那種情況。

但要說清楚一件事：這條路徑開機時並不會走到。 kernel_main 印的是 printf("Hello, AArch64 from EL1\n")， 裡面沒有 %s，所以 switch 不會進 case 's':， put_str 和 strlen 一條指令都不會執行。實測用 GDB 下斷點：

break emit       開機時命中      ← 對照組，證明手法有效
break put_str    從未命中
break strlen     從未命中
序列埠仍然印出   Hello, AArch64 from EL1

那 strlen 現在到底是不是「有作用」的？是，但作用在連結期，不在執行期。 把 lib/string.c 裡的 strlen 刪掉再建置：

printf.c:(.text+0xb0): undefined reference to `strlen'
collect2: error: ld returned 1 exit status

連結器不管那條 bl 會不會被執行到，它只看到 put_str 裡有一個 對 strlen 的參照，就要求有人提供。「binary 裡有 bl X」和 「X 會被執行」是兩件不同的事——第 10 節直覺 10 講的正是同一條界線 （那 8 條 str q 存在，但在第一版的樹上永遠不會被執行）。

所以 strlen 是四個裡面唯一「拿掉現在就會壞」的一個，只是壞在建置階段。 另外三個連這個都沒有：把 memset 刪掉，建置照樣成功。

第 8 節那四個函式裡，只有 strlen 走到了這一步。 memset、memcpy、strcmp 到寫下這段為止都還沒有呼叫者—— M2 還有輸入 echo 與 panic() 兩包沒寫，那兩包會不會用到，等寫了才知道 （第 7 節有兩個同款預測，兩個都猜錯了）。這是提前寫它們要付的代價，第 8 節開頭有說明。

10被推翻的直覺

這一節收的不是「常見誤解」，而是我在寫這份教材的過程中，自己相信過而且寫下來、 後來被實驗推翻的說法。每一則的格式都一樣：先引用當初寫的那句話，再給推翻它的最小重現。

會特別留著它們，是因為「原本以為 A、實際是 B」比「B 是對的」有用得多—— 你三個月後重讀，多半也會先想到 A。前五則是寫第一包（UART）期間發現的，後七則來自 string.c 與 printf 這兩包，也就是第 8、9 節的內容。

直覺 1

「UART 要先初始化才能用」

在 QEMU 上完全不用。實測：寫一支只做 uart_puts()、完全不呼叫 uart_init() 的核心 —— 字元照樣全部出來。

而且開機時的狀態是「UARTEN = 0、鮑率沒設、字元長度沒設」。一台標示為關閉、沒有設定鮑率的 UART，照樣把字送出去了。

因為 QEMU 的 PL011 模型只是把位元組轉交給宿主機的終端機，那些設定它一個都不看。

直覺 2

「volatile 是防止編譯器把重複的寫入合併成一次」

方向對，但實際發生的事更狠。拿掉 volatile、用 -O2 編，數一下 uart_init() 裡的 str：

-O0  有 volatile   1 條   （呼叫 mmio_write32，沒展開）
-O0  無 volatile   1 條   完全一樣
-O2  有 volatile   5 條   五次寫入都在
-O2  無 volatile   4 條  少了一條

少的那一條是 CR = 0。 編譯器看到 CR 被寫兩次（先 0、後 0x101），把第一次當成死存取（dead store——寫進去之後、還沒有人讀就被蓋掉的一次寫入）刪掉了：

-O2、無 volatile 的 uart_init：
    str  w7, [x6]     ; IBRD = 13
    str  w5, [x4]     ; FBRD = 1
    str  w3, [x2]     ; LCR_H = 0x70
    str  w1, [x0]     ; CR = 0x101
    ret
                      ← 「先關掉 UART」那一步整條不見了

而那正是註解裡宣稱「保護飛行中的字元」的那一行。編譯器把安全措施刪掉了，而且 QEMU 上照樣印出 Hello。

兩個教訓：一，volatile 不是為了現在，是為了 -O2（PROJECT_PLAN 有規定，Makefile 還沒設）。二，「拿掉它現在會壞嗎」這個判準要連編譯旗標一起問 —— 同一段程式碼在 -O0 和 -O2 下是兩個不同的答案。

直覺 3

「clk * 4 / baud 就是 TRM 的算法」

不是，那是無條件捨去，TRM 是四捨五入。24 MHz 剛好相同，48 MHz（Pi 4）差一格。細節在第 5 節。

值得記住的是它為什麼躲過檢查：唯一能驗證的平台剛好是兩種算法一致的那個。

直覺 4

「M1 的 ALIGN(16) 擋住了孤兒節插隊」

M1 的連結器腳本註解說：把 __bss_start 寫在 .bss { } 外面，ld 會把孤兒節（.eh_frame）塞進符號和區段之間，清零迴圈就會抹掉它。

照字面做重現不出來。 實測（binutils 2.38，M1 當時的原始碼）：

符號在大括號內              __bss_start = 0x400000f0   安全
符號移到外面，保留 ALIGN     __bss_start = 0x400000f0   還是安全
符號移到外面，拿掉 ALIGN     __bss_start = 0x400000a4   ← .eh_frame 在 0x400000a8，被夾住了

要兩個條件同時成立才會出事，而註解只寫了一個。

更值得記住的是：那個 ALIGN(16) 是為了「讓清零迴圈一次寫 16 bytes 不留零頭」而寫的，它擋住孤兒節純屬意外。一個為了 A 而寫的東西，剛好也擋住了不相干的 B —— 這種「靠巧合正確」的程式碼，會在某天加了一個新區段之後突然壞掉。

（M2 就加了新區段：.rodata。加進腳本之後，孤兒節的位置又變了。）

直覺 5

「同樣的原始碼建兩次，產出應該一模一樣，所以 md5 相同代表沒重建」

錯。實測連續建兩次，md5 就不同 —— 差 6 個 byte。

位置在 .strtab（string table，ELF 裡存放所有符號名字的那一區）。gcc 編譯時會產生暫存的 .o 檔，檔名每次都不一樣（ccGWRvg.o、cc3aNwQx.o⋯），而那個名字會以一個 STT_FILE 型別的符號（ELF 用來記錄「這段東西來自哪個原始檔」）留在符號表裡。

所以「md5 沒變」不能用來證明沒重建。反向仍可靠：md5 變了不代表真的重建了。要驗「有沒有重建」，看 make 的輸出有沒有跑編譯指令比較準。

直覺 6 —— 這一則和下一則是同一個誤解

「gcc 不會把我手寫的迴圈變回 memcpy 呼叫」

寫 lib/string.c 之前先擔心了一件事：gcc 有個最佳化叫迴圈樣式識別 （-ftree-loop-distribute-patterns），會認出「這個迴圈在做的事就是 memset」， 然後把整個迴圈換成一句 bl memset。如果被換掉的正是 memset 自己，那就是無窮遞迴。

我實測後宣布「gcc 11.4.0 沒做這個轉換」，並據此決定不加 -fno-tree-loop-distribute-patterns。 結論碰巧對，理由完全錯。

同一份原始碼，只換旗標（用 nm -u 看「這個 .o 需要別人提供什麼」）：

my_clear / my_copy 的逐 byte 迴圈
  -ffreestanding -O2               （空的）沒有生出呼叫
  -O2（拿掉 -ffreestanding）      U memset      ← 它會做

U ＝ undefined，「我用到這個符號，但它不在我這個檔案裡，連結時要有人補上」。 第 13 節小抄裡 nm 的其他代號（T／B／D／A）都是「我提供」，只有 U 是「我需要」。

擋住它的是 -ffreestanding，不是 gcc 做不到。 -ffreestanding 隱含 -fno-builtin，那才是關鍵 —— 它讓 gcc 完全忘記 memset／memcpy／strlen 這些名字有特殊意義。

我當初的實測全部跑在專案自己的旗標組合裡，所以永遠看不到另一半。 對照組要換的是「你懷疑的那個變因」，不是「你手邊剛好有的設定」。

（順帶：函式本身就叫 memset 時，gcc 不會把它變成呼叫自己，所以無窮遞迴這個具體恐懼不成立。 但那是另一個保護，跟 -ffreestanding 無關。）

直覺 7

「函式簽章寫錯，-Wbuiltin-declaration-mismatch 會擋下來」

把 strlen 宣告成回傳 int（標準是 size_t），實測：

-ffreestanding -Wall -Wextra -Werror     exit 0，一個診斷都沒有
拿掉 -ffreestanding                       error: conflicting types for built-in
                                          function 'strlen'
                                          [-Werror=builtin-declaration-mismatch]

同一個原因：-ffreestanding 關掉了 builtin，那個診斷在本專案根本不會出現。 （而且它是 warning，是 -Werror 讓它致命的 —— 這是第 7 節那條「-Werror 才是把警告變成錯誤的那一環」的又一個例子。）

那簽章寫錯到底是誰擋下來的？最普通的一件事：標頭和定義不一致。

error: conflicting types for 'strlen'; have 'size_t(const char *)'

簽章跟標準一致仍然重要，但保護來自我們自己寫的那個 .h， 不是來自「編譯器認得這些名字」。搞錯誰在保護你，那個保護消失時你不會發現。

直覺 8

「QEMU 不做對齊檢查」

第 8 節說：MMU 關掉時整片記憶體算 Device，未對齊存取應該要 fault。實測 QEMU 照跑，於是我第一版寫下「QEMU 不強制對齊」。 太籠統，而且會讓人以為這件事在 QEMU 上根本無法觀察。

SCTLR_EL1 = 0x00c50838   （bit0 M=0 MMU 關、bit1 A=0）
  讀 buf + 1（未對齊）      照跑，沒有 fault

把 SCTLR_EL1.A 設成 1 → 0x00c5083a
  讀同一個 buf + 1         立刻 trap
  ESR_EL1 = 0x96000021
  FAR_EL1 = buf + 1          Fault Address Register：出事的那個位址

用第 9 節那個方法拆 ESR_EL1：

0x96000021

EC   = bits[31:26] = 0b100101 = 0x25   Data Abort（同一個 EL）
DFSC = bits[5:0]   = 0b100001 = 0x21   Data Fault Status Code
                                       ＝ Alignment fault

DFSC（Data Fault Status Code）是 ESR_EL1 最低 6 位元，只有在 EC 是 Data Abort 時才有意義 —— 它回答「這個 Data Abort 具體是哪一種」。0x21 就是對齊錯誤。

FAR_EL1 的實際值取決於那份測試碼的佈局，換一份就不一樣，所以這裡只寫它等於 buf + 1。

QEMU 有實作對齊檢查，只是預設沒開。 它沒實作的是另一條推論：「MMU 關掉 ⇒ 整片記憶體算 Device ⇒ 未對齊一律 fault」。真板子兩條都做。

差別很實際：原本的說法會讓你以為只能等真硬體，實際上設一個位元就能親眼看到那個 fault。

（另外：M1 記過「SP 未對齊 QEMU 照跑」。看起來像同一件事，機制卻不同 —— SP 對齊歸 SCTLR_EL1.SA 管，資料對齊歸記憶體型別和 SCTLR_EL1.A 管， 是兩個獨立的開關。把它們講成「同一個模式」，會害人去 ARM ARM 查錯章節。）

直覺 9

「三點取樣就能量出門檻」

那 8 條指令存在，但永遠不會被執行。所以 Makefile 註解寫的「拿掉這個旗標就卡在 0x200」， 在要 commit 的那棵樹上是假的。

有旗標      Hello, AArch64 from EL1
沒有旗標    （完全空白，一個字都沒有）

教訓不在旗標，在判準怎麼用：「拿掉它會壞嗎」問的是「在要交付的那棵樹上會不會壞」， 不是「在我的實驗裡會不會壞」。 一段沒有呼叫者的程式碼，它的所有保護措施也一樣沒有呼叫者。

直覺 11 —— 上一則的規則，我自己也沒套完

「加了 -mgeneral-regs-only，拿掉就開機空白，所以這個旗標有理由了」

直覺 10 補上了「要在要交付的那棵樹上問」。但精髓第 2 條還有另一半： 「拿掉它會壞嗎」要連編譯旗標一起問。 我把這條套在「哪棵樹」上，卻沒套在「哪個 -O」上。

沒有 -mgeneral-regs-only，換最佳化等級：

  -O0    q/v 指令 8 條    開機 （完全空白）
  -O1    q/v 指令 0 條    開機 Hello, AArch64 from EL1
  -O2    q/v 指令 0 條    開機 Hello, AArch64 from EL1

-O1 以上，gcc 會發現那 8 條 str q 存進去之後沒人讀，直接刪掉 —— 這個旗標在 -O1 以上就不需要了。

那還要不要加？要。 但理由要說準：

  • 本專案現在沒有設 -O，也就是 -O0，所以這個 fault 是現在進行式；
  • PROJECT_PLAN §5.1 規定日後要開 -O2。真的開了之後，這個旗標的失敗訊息就會消失 —— 但它擋的另一件事不會消失：見直覺 9 那張表，結構賦值產生的 ldp q0, q1 在 -O2 下照樣會出現， 那才是它長期存在的理由。

（Makefile 的註解寫的是「-O0 下可變參數序言會存 q0-q7」， 那句話一直是精確的 —— 是這份教材的正文比程式碼的註解還鬆。）

兩張表疊起來：符號不等於區段

readelf -S 看的是區段——編譯器把程式切成的幾大塊。nm 看的是符號——名字對應到哪個位址。兩者不一定重合，把它們疊在同一根軸上就看得出來。

這張圖說了四件事

1. .rodata 和 .eh_frame 一個符號都沒有。 那個 "Hello, AArch64 from EL1\n" 就住在 .rodata，但它是匿名的字串字面值——編譯器直接用位址引用，沒人需要它的名字。所以 nm 看不到，readelf 看得到。

2. .text 裡面有一段沒有名字的資料。 halt_loop 後面的 0x58–0x6f 是字面池，存著三個位址常數。objdump 只好叫它 halt_loop+0xc——用最近的前一個符號加偏移來描述。

3. __bss_start 比 .bss 區段晚 8 個 byte。 那 8 bytes 是 ALIGN(16) 推出來的，在區段裡但清零迴圈碰不到（它從 __bss_start 起跑）。「區段多大」和「迴圈清多少」是兩個數字：區段 24 bytes，迴圈只走 16。

4. __bss_end 和 .stack 的起點是同一個位址。 因為「結束的下一個」剛好等於「下一塊的開始」。清零迴圈的 b.hs 是等於就停，所以它不會寫進堆疊——差一個字就會踩過去。

還有一個不在這根軸上的符號

nm 的第一行是：

0000000000010000 A STACK_SIZE

0x10000 不是位址，是值本身——就是連結器腳本裡 STACK_SIZE = 64K; 那個 64K。

A 是 absolute，代表它不屬於任何區段。把它當位址去讀，會讀到 flash 區的垃圾。

12精髓

  1. 週邊裝置的暫存器不是記憶體，編譯器不知道這件事。 volatile 是唯一告訴它的方法，而且少了它不會有錯誤訊息 —— 只會少做事。
  2. 「拿掉它現在會壞嗎」要連編譯旗標一起問。 同一段程式碼在 -O0 和 -O2 下，答案是相反的。
  3. 唯一能驗證的平台，可能剛好是看不出錯的那個。 鮑率的捨去 vs 四捨五入在 QEMU 上完全一致，只在真機的時脈上分岔。「測過了」和「在會出錯的條件下測過了」是兩件事。
  4. 一個看起來完整的抽象層，比一個明說有缺口的危險。 platform.h 說「驅動不用改」是真的，但沒說 GPIO muxing 得另外做 —— 讀者會在真板子上得到全黑畫面，然後不知道從哪查起。
  5. 搞錯「是誰在保護你」，那個保護消失時你不會發現。 直覺 6 和直覺 7 是同一個誤解的兩種表現：以為 gcc 認得 memset 這些名字會幫忙把關，實際上 -ffreestanding 早就把那整套關掉了。對照組要換的是你懷疑的那個變因，不是你手邊剛好有的設定。
  6. 「拿掉它會壞嗎」問的是「在要交付的那棵樹上」。 -mgeneral-regs-only 在實驗裡救了一次當機，但在要 commit 的樹上，printf 一次都沒被呼叫 —— 沒有呼叫者的程式碼，它的保護措施也一樣沒有呼叫者。

13一頁式小抄

PL011 暫存器

+0x00  DR      寫進去 = 送一個字元
+0x18  FR      bit5 TXFF = 送出佇列滿了
+0x24  IBRD    鮑率除數整數部
+0x28  FBRD    鮑率除數小數部（1/64）
+0x2c  LCR_H   bit4 FEN 開 FIFO、bits[6:5] WLEN（3 = 8 bits）
+0x30  CR      bit0 UARTEN、bit8 TXE、bit9 RXE

初始化順序

1. CR = 0            先關掉（改設定不能在運轉中做）
2. IBRD、FBRD        設鮑率
3. LCR_H             設字元格式 —— 寫這個才會 latch 上一步
4. CR = UARTEN|TXE   開起來

鮑率

divisor = clk / (16 × baud)
div64   = (clk × 8 / baud + 1) / 2      整數形式的四捨五入
IBRD    = div64 / 64        FBRD = div64 % 64

24 MHz / 115200  →  833  →  (13, 1)   誤差 +0.04%

標頭裡的函式為什麼要 static inline

定義寫在標頭 → 每個 include 它的 .c 都貼一份

static   斷「兩份撞名」    少了 → multiple definition
inline   斷「沒用到被唸」  少了 → -Wunused-function（配 -Werror 就擋建置）

只寫 inline（沒 static）  → -O0 下 undefined reference

MMIO 的寬度看【裝置的暫存器】，不是【CPU 的暫存器】：
  x0-x30（CPU 裡）        64 位元
  DR/FR/IBRD（PL011 裡）  32 位元  → 資料用 uint32_t
  位址空間                64 位元  → 位址用 uintptr_t
  證據：從 IBRD 讀 8 bytes 會讀到 FBRD 黏在高 32 位元

C 的幾個容易寫錯的地方

volatile uint32_t *p     ← 目標是 volatile   ✅
uint32_t * volatile p    ← 指標自己是       ❌ 保護錯對象

const char *s            ← 內容唯讀，指標可動  ✅
char * const s           ← 反過來

void f(void)             ← 沒有參數          ✅
void f()                 ← 「參數不詳」，C 不擋 f(1,2,3)

#define M (1u << 5)      ← u 防有號左移
#define M 1u << 5        ← x & M 沒事（<< 優先序高於 &）
                            但 M + 1 會變成 1u << 6 = 64

clk * 8UL / baud         ← 有一個 UL 就整式提升到 64 位元  ✅
clk * 8   / baud         ← 全部 32 位元，換高時脈會溢位

*s++                     ← *(s++) 讀了再移動指標
(*s)++                   ← 改字元本身；參數是 const char * 所以編不過

(uint32_t)(unsigned char)c   ← 先斷符號再放大，可攜
(uint32_t)c                  ← char 有號的平台會符號延伸

      → 進 kernel_main 時它還在

MMU 關掉時的記憶體

stage 1 轉換關閉 → 整片記憶體視為 Device-nGnRnE
    nG  不准合併存取
    nR  不准調換順序
    nE  不准提早回報寫好了
    ＋  不允許未對齊存取

SCTLR_EL1  bit0 M   MMU 開關
           bit1 A   資料對齊檢查
           bit3 SA  堆疊指標對齊檢查      ← 和 A 是不同的開關

QEMU 預設 A=0，所以未對齊照跑。設 A=1 就看得到 fault：
    ESR_EL1 = 0x96000021   EC=0x25 Data Abort、DFSC=0x21 Alignment

可變參數與浮點

AAPCS64   整數走 x0-x7、浮點走 q0-q7、多的走堆疊
          -O0 下可變參數序言會存 q0-q7，就算你沒寫過 float

CPACR_EL1.FPEN  bits[21:20]   0b00 = EL0/EL1 一律 trap（重設值）
                              0b11 = 都不 trap

踩到就是：pc=0x200、ESR_EL1=0x1fe00000
          EC = bits[31:26] = 0x07   FP/SIMD 被 FPEN 擋下

解法：-mgeneral-regs-only（Linux 也是這樣做）
      別在 boot.S 開 FPEN —— 那要付 520 bytes/次中斷的存檔成本
