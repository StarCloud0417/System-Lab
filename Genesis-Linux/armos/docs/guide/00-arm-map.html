怎麼用這份文件

先讀這份，再讀 M0、M1 的教材。 那些教材是深度——把一件事講透；這份是廣度——告訴你那件事在整張圖的哪個位置，以及旁邊還有什麼。

現在打開會看到一大片灰色，只有兩格是綠的。那不是缺點，那正是你需要的比例感：boot.S 那 28 行，在「設定一顆 ARM 處理器」這件事裡佔多少。

0先講一個貫穿全篇的東西：特權等級

底下每一節都會提到「EL幾」。先花三十秒把它講完。

AArch64 把權限分成四層，數字越大權限越高：

EL3   安全韌體（Secure Monitor）        開機最早期，我們碰不到
EL2   虛擬機管理器（hypervisor）        樹莓派韌體把我們丟在這裡
EL1   作業系統核心  ← 我們要待的地方     Linux 核心也在這一層
EL0   一般使用者程式                    M8 之後才會用到

hypervisor（虛擬機管理器）是「跑作業系統的作業系統」——一台機器上同時跑好幾個 OS 時，管理它們的那一層。這個專案不寫 hypervisor，但韌體常常把我們丟在那一層，所以得自己走下來。

三件事現在知道就好：

  • 每一層有自己一整套系統暫存器。 VBAR_EL1 和 VBAR_EL2 名字像，物理上是兩顆不同的暫存器
  • 往上是自動的，往下要自己走。 出事時硬體把你抬上去；要下來只有 eret 一條路
  • 我們的目標是永遠待在 EL1，因為所有教材、Linux 原始碼、以及 M8 的「EL0 出事自動送到 EL1」都假設核心在那裡

細節在 M1 教材第 3–5 節。

1時間軸：從按下電源到 shell

先講最大的問題：我們的第一行程式碼，是在什麼時候開始跑的？

  • 通電 不做 電源穩定、時脈起振。純硬體，沒有任何軟體參與
  • BootROM 不做 燒死在晶片裡的唯讀程式，改不了。它的工作是「找到下一棒」——從 SD 卡、eMMC 或 SPI flash 讀出韌體
  • 韌體（樹莓派是 start4.elf，伺服器是 U-Boot／UEFI） 不做 初始化記憶體控制器（DRAM 這時才能用）、讀 device tree（描述這台機器有哪些硬體、各在哪個位址的一份清單）、把核心映像搬進 RAM、決定交棒時的特權等級
  • _start —— 我們從這裡接手 M0 ✓ CPU 執行的第一條「我們寫的」指令。在此之前發生的所有事，我們都無權過問，只能接受
  • 統一起點：降到 EL1、設堆疊、清 .bss（放「沒給初始值的全域變數」的那塊記憶體，C 保證它讀出來是 0——但那個保證要有人兌現）M1 ✓ 把「韌體給什麼就是什麼」變成一個固定的已知狀態，C 語言才跑得起來
  • 第一個輸出：UART 驅動 M2 在這之前，唯一的觀察手段是 GDB。有了它才能 printf 除錯
  • 例外向量表 M3 在這之前，任何錯誤都是無聲的——CPU 跳到 0x200 然後執行垃圾
  • 中斷：GIC（Generic Interrupt Controller，決定哪個裝置的中斷送給哪顆核心的那塊硬體）+ 計時器，然後打開 DAIF M4 在這之前 CPU 只會照著程式走。有了中斷，外界才能打斷它
  • MMU：分頁表、虛擬位址 M5 在這之前所有位址都是實體位址。開了之後核心會搬到 0xffff_... 的高位址
  • 記憶體配置器 M6
  • 排程器：多工 M7
  • 使用者模式 + 系統呼叫 + shell M8 到這裡才用得上 EL0（最底層）。shell 就在這一站——不是最後才有
  • 移植樹莓派：真機，四顆核心同時進來 M9 用 MPIDR_EL1 篩掉 core 1–3，只讓 core 0 往下走。這裡是 Stage A 的終點
  • SMP：真的叫醒另外三顆核心 M10 選配 喚醒機制兩個平台不一樣：QEMU 用 PSCI（Power State Coordination Interface，一組跟韌體要求「幫我開這顆核心」的標準呼叫），樹莓派 4 用 spin-table（副核心在固定位址上打轉等人寫值）
  • fork / exec / Copy-on-Write M11 選配

M10、M11 標「選配」是計畫裡就決定的：專案最常見的死法不是技術太難，是範圍失控。M9 上板成功之後再決定要不要加做。

值得注意的是前三格我們完全碰不到。BootROM 改不了，韌體是別人寫的。所以「開機」對這個專案來說，是從別人已經做完一堆事之後才開始的。

那我們錯過了什麼？

DRAM 的初始化。這是韌體最複雜的工作之一（訓練時序、校準阻抗），而且每顆記憶體晶片都不一樣。跳過它不是偷懶——沒有韌體先做完這件事，連載入核心的地方都沒有。

QEMU 更乾脆：它直接把 ELF 載進模擬的 RAM，連韌體都省了。這也是為什麼 -M virt 進來就是 EL1——沒有 hypervisor 需要那一層。

兩個意外

1. 中斷開機就已經全遮了。 我們寫進 SPSR_EL2 的 0x3c5 裡那四個 1，其實只是「維持現狀」，不是「關掉它們」。真正打開是 M4 的事。

2. SCTLR_EL1.SA（bit 3）重置後是 1——SP 對齊檢查「開著」。但在 QEMU 上它不生效。

實測：把 SP 設成 0x4001002c（mod 16 = 12，錯得很徹底），然後跑一條跟 C 序言一樣的 stp x24, xzr, [sp, #-16]!——

SCTLR（CPU 自己 mrs 讀）= 0xc50838
  SA bit3              = 1        檢查是開的
SP mod 16              = 12       故意錯的
stp 之後讀回來          = 0xbeef   寫成功了
活著旗標                = 1        沒有例外
PC                     = 0x4000002c 不是 0x200

暫存器說要檢查，模擬器沒有做。 所以連結器腳本那個 ALIGN(16)，在 QEMU 上拿掉現在不會壞——它是為了 M9 上真機而寫的。

這是這份地圖第一個「在模擬器上驗不出來」的例子，值得記住：SCTLR 讀出來的值是真的，那顆 bit 代表的行為在這個平台上不是真的。M9 上板時要回來重驗這一條。

3暫存器地圖

QEMU 的 gdb 介面在 virtualization=on 下開放 411 顆暫存器。不要一顆一顆看，分成四類就好。

第一類：每天都會用到（約 34 顆）

x0 – x30      通用暫存器，64 位元
x30           link register —— bl 把回程位址寫在這，不是寫在堆疊
sp            堆疊指標。每一層有自己的（SP_EL0 / SP_EL1 / …）
pc            現在執行到哪。不能直接寫，只能靠跳躍指令改
xzr / wzr     零暫存器：讀永遠是 0，寫進去等於丟掉

哪顆拿來傳參數、哪顆呼叫前要自己存好（呼叫慣例 AAPCS64），是寫 C 與組語互相呼叫時的事，不是「設定一顆處理器」的一環。M8 做系統呼叫時再展開。

另外還有浮點／向量那一組。不做 這個專案不碰浮點。

順帶一個容易數錯的地方

gdb 列出 194 個浮點相關的名字：v／q／d／s／h／b 各 32 個，加上 fpcr 和 fpsr。

但實體上只有 32 顆。那六組是同一顆暫存器的六種寬度視角（128／128／64／32／16／8 位元），就像 x0 和 w0 的關係。「有幾個名字」和「有幾顆暫存器」是兩件事。

一個計畫變更：MPIDR_EL1 從 M1 移到 M9

docs/PROJECT_PLAN.md 原本把「依 MPIDR_EL1 篩選 core 0」排在 M1，但現在的 kernel/boot.S 沒有這段程式碼。

理由是實測：QEMU 的 -M virt 加 -smp 4 不會放出副核心——它們被關在「電源關閉」狀態，要等軟體用 PSCI 主動叫醒。實測 CPU#1–#3 停在 _start，一條指令都沒執行過。

所以那段篩選程式碼在 QEMU 上根本不會被執行到，寫了也驗不了。照「拿掉它現在會壞嗎」的判準，答案是不會，所以整包留到 M9 移植真機時再做——那時四顆核心才是真的一起進來。

兩件事這張圖說得比文字清楚

1. 低位址不是 RAM。 0x0 到 0x4000_0000 這 1 GB 全是 flash 和 MMIO（周邊裝置的暫存器）。這就是為什麼 SP = 0 時往下寫會出事——那裡根本不是記憶體。

2. 0x200 落在 flash 裡的 device tree。 不是「一片空白」，是 QEMU 放在那裡的硬體清單。CPU 跳過去之後，是在把 ASCII 當指令執行。

M5 之後這張圖會變成什麼

開了 MMU，核心會搬到 0xffff_... 開頭的高位址，使用者程式留在低位址。上面那張實體地圖不會消失，但從此要透過分頁表才看得到。

那也是為什麼 boot.S 現在比較位址用 b.hs（無號）而不是 b.ge（有號）——最高位元變成 1 之後，有號比較會把位址當成負數。M1 ✓

5例外：唯一的控制流轉移機制

CPU 平常一條一條往下執行。要打斷它，只有兩種辦法：程式自己跳（b、bl、ret），或者發生例外。

「例外」不只是錯誤。中斷、系統呼叫、分頁錯誤、除以零，全都走同一套機制。

四種例外 × 四個來源 = 16 格

向量表的基底放在 VBAR_ELx，往下 16 格，每格 0x80 bytes：

              同步        IRQ        FIQ       SError
             （自己造成）（一般中斷）（快速中斷）（系統錯誤）

同一層、用 SP_EL0    +0x000     +0x080     +0x100     +0x180
同一層、用 SP_ELx    +0x200     +0x280     +0x300     +0x380
低一層、AArch64      +0x400     +0x480     +0x500     +0x580
低一層、AArch32      +0x600     +0x680     +0x700     +0x780
SP_EL0 和 SP_ELx 差在哪

同一層可以選用哪一支堆疊指標——這由 PSTATE.SPSel 一個位元決定，也就是我們寫進 SPSR_EL2 的 0x3c5 裡的 bit 0。

SPSel = 0  →  用 SP_EL0（大家共用那一支）   叫 EL1t，走第 1 列
SPSel = 1  →  用 SP_EL1（這一層專屬的）     叫 EL1h，走第 2 列

我們選 1（EL1h），所以核心出事時走第 2 列——那就是為什麼你撞到的是 +0x200 而不是 +0x000。

你已經撞過第二列了

+0x200 就是「同一層、用 SP_ELx、同步例外」。M1 的三種當機全部落在這一格：

怎麼撞的ELESR 的 EC
沒設堆疊，stp 寫到不存在的位址10x25 Data Abort
在 EL1 碰 EL2 的暫存器10x00 Unknown
eret 的兩個設定打架20x0e Illegal Execution state
這一列要讀 ESR_EL2——例外送到 EL2 去了

VBAR_EL1 重置是 0，所以基底 + 0x200 = 0x200。CPU 是規規矩矩去查表的，只是那裡沒有表。

這張表驗到什麼程度

四列的第一欄（同步）都實測過——自己裝一張 16 格的表，每格寫個編號再打轉，然後用四種不同方式觸發例外：

怎麼觸發落在第幾格偏移
SPSel=0（EL1t）造 data abort0+0x000 ✅
SPSel=1（EL1h）造 data abort4+0x200 ✅
降到 EL0（64 位元）後 svc8+0x400 ✅
降到 EL0（32 位元）後 svc12+0x600 ✅

IRQ／FIQ／SError 三欄還沒實測——要先有 GIC 才打得出中斷，那是 M4 的題目。格距 0x80 與 16 格的順序另外對照過 Linux 的 arch/arm64/kernel/entry.S（表基底 .align 11 = 2048 對齊，每格 .align 7 = 128 bytes）。

硬體只會把你抬上去，從來不會主動放下來。 出事時 CPU 自動跳到高一層；要往下只有一個指令：eret，而且它的語意是「返回」——你得先假裝自己是從下面被叫上來的。

M1 就是在做這件事：填好 ELR_EL2（回哪裡）、SPSR_EL2（回去之後是誰）、HCR_EL2（下面守什麼規矩），然後 eret。M1 ✓
