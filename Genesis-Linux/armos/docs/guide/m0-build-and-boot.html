armos · 里程碑 M0

從零到第一條指令

一個 12 bytes 的核心，怎麼被建置出來、被載到 0x4000_0000、然後真的被 CPU 執行

1要解決什麼問題

目標小得有點荒謬：讓一顆 ARM64 的 CPU 執行三條我們自己寫的指令，並且能證明它真的執行了。

沒有作業系統、沒有 bootloader、沒有 C 標準函式庫、沒有 printf。難的不是那三條指令，是它們周圍的一切都不存在：

  • 平常寫程式，作業系統的 loader 會決定程式放在記憶體哪裡。現在沒有 loader，位址要自己決定——而且要跟硬體對得上。
  • 平常 main() 會被自動呼叫。現在沒有人會呼叫任何東西，得自己指定第一條指令在哪。
  • 平常程式錯了會 segfault、會有錯誤訊息。現在錯了就是一片黑，沒有任何回饋。

所以 M0 真正要建立的，是一條看得見的回饋迴路：改一行 → 建置 → 跑起來 → 看得到差異。這條迴路建立不起來，後面每個里程碑都是在瞎猜。

2動手：建置與觀察

後面幾節都在解釋原理，但原理讀十遍不如親眼看一次。這一節是一份可以照著打的操作步驟，六步做完大約十分鐘，你會親眼看到這個核心被建置、被載入、以及被 CPU 執行。建議先做完這一節，再回頭讀第 3 節之後的說明。

步驟 0：準備工具

四樣東西：交叉編譯器、模擬器、除錯器、device tree 工具。Ubuntu / Debian 上：

sudo apt install gcc-aarch64-linux-gnu qemu-system-arm \
                 gdb-multiarch device-tree-compiler make

裝好之後確認一下（版本不必完全一樣，但差太多的話本文的數字可能對不上）：

$ aarch64-linux-gnu-gcc --version | head -1
aarch64-linux-gnu-gcc (Ubuntu 11.4.0-1ubuntu1~22.04.3) 11.4.0
$ qemu-system-aarch64 --version | head -1
QEMU emulator version 6.2.0 (Debian 1:6.2+dfsg-2ubuntu6.31)
$ gdb-multiarch --version | head -1
GNU gdb (Ubuntu 12.1-0ubuntu1~22.04.2) 12.1

為什麼是交叉編譯器？你的電腦大概是 x86-64，而目標是 ARM64。aarch64-linux-gnu- 這個前綴的意思就是「在這台機器上跑，但產生 ARM64 的碼」。名字裡雖然有 linux-gnu，我們靠 -nostdlib 把它跟 Linux 的部分切乾淨。

步驟 1：建置

$ cd Genesis-Linux/armos
$ make
mkdir -p build
aarch64-linux-gnu-gcc -Wall -Wextra -Werror -ffreestanding -nostdlib -static \
    -Wl,-T,linker/kernel-qemu.ld -Wl,--build-id=none -o build/kernel.elf kernel/boot.S

應該看到：就這兩行，沒有別的。本專案開著 -Werror，任何警告都會變成錯誤，所以「安靜」就是成功。

沒看到的話：command not found 代表步驟 0 沒裝完；Nothing to be done for 'all' 代表已經建過了，先 make clean。

步驟 2：看看做出了什麼

$ make dump

輸出有點長，只要盯三個地方：

看哪裡應該是意思
反組譯只有 3 條指令，從 0000000040000000 <_start> 開始程式碼落在對的位址
Entry point address0x40000000QEMU 會從這裡開始執行
LOAD 那行的 PhysAddr0x40000000QEMU 會把內容搬到這裡

這三個數字一致，代表「要放的位置」和「要跳的位置」對上了。核心還不會輸出任何字，這是這個階段唯一的靜態檢查手段。

步驟 3：跑起來（畫面會是黑的）

$ make qemu

應該看到：一片空白。這是正確的——UART 驅動要到 M1 才有，現在的核心沒有任何輸出能力。

離開方式：先按 Ctrl-A，放開，再按 X。（不是同時按三個鍵。Ctrl-A 是 QEMU 的跳脫鍵，按完之後它會等你下一個指令。）

這一步唯一能確認的是「QEMU 沒有報錯就退出」。至於 CPU 到底有沒有在執行，看不出來——這正是下一步存在的理由。

步驟 4：證明 CPU 真的在執行 ← 這是本里程碑的驗收

$ make debug

應該看到：

0x0000000040000000 in _start ()
Breakpoint 1 at 0x40000008

Breakpoint 1, 0x0000000040000008 in halt_loop ()
$1 = 1

Breakpoint 1, 0x0000000040000008 in halt_loop ()
$2 = 2
(gdb)

$1 和 $2 是不同的值 —— 過關。這兩個數字證明了兩件事：映像確實被載進去了（不然斷點不會命中），而且 CPU 確實在執行我們寫的指令（不然 x0 不會變）。

停在 (gdb) 之後可以自己繼續看：

(gdb) c                繼續，再停一次（x0 會是 3）
(gdb) p $x0            印暫存器
(gdb) p/x $cpsr        0x400003c5 —— 開機時的處理器狀態
(gdb) info threads     確認只有一顆核心
(gdb) x/3i $pc         看目前位置的三條指令
(gdb) q                離開（QEMU 會被一起收掉）

出問題的話：如果它說 port 1234 已被佔用，代表上一隻 QEMU 沒關乾淨，執行 pkill -f qemu-system-aarch64 再試。這個守衛很重要——沒有它的話 GDB 會靜默連上舊的那一隻，畫面變成「指令是舊映像的、符號名是新 ELF 的」，而且不會有任何錯誤訊息。

步驟 5：查平台位址的出處

$ make dtb | grep -A3 'memory@'
memory@40000000 {
    reg = <0x00 0x40000000 0x00 0x8000000>;
    device_type = "memory";
};

這就是 0x4000_0000 的來源，不是慣例也不是抄來的。第 4 節會解釋這四個數字怎麼讀。

步驟 6：動手把它弄壞（最重要的一步）

前五步都在確認「一切正常」。但真正學到東西的方式是故意弄壞，然後看症狀——因為裸機開發沒有 segfault 幫你擋，你唯一的技能就是從症狀反推原因。

3完整路徑

從一個 .S 檔到 CPU 執行，中間經過這些人的手：

圖上為什麼寫 cc1 -E，不是 gcc、也不是 cpp

gcc 本身不做前處理、組譯或連結，它是個 driver（排程者）：解析你給的旗標，決定該依序叫起哪些真正幹活的程式。用 -v 就能看到它實際叫了誰：

$ aarch64-linux-gnu-gcc -v -c kernel/boot.S
 .../11/cc1 -E -lang-asm ... kernel/boot.S -o /tmp/ccIduG8y.s
 .../aarch64-linux-gnu/bin/as -EL -mabi=lp64 -o ... /tmp/ccIduG8y.s

所以前處理是 cc1 用 -E -lang-asm 模式做的。至於 cpp —— 系統上確實有這個執行檔（/usr/bin/aarch64-linux-gnu-cpp），但它自己也只是另一個 driver，內部同樣是跑 cc1 -E。gcc 處理 .S 時不會繞過去叫 cpp。「cpp」是這個階段的通稱，不是這裡被執行的程式。

連結那一格同理：gcc 叫的是 collect2，由它再去叫 ld。圖上直接寫 ld 是因為 collect2 在這個專案裡不做任何額外的事，但知道中間還隔了一層，看 -v 的輸出時才不會困惑。

build/kernel.elf 是怎麼來的

只有一個原始檔，所以整個建置就是一條命令，沒有中間的 .o。用 make -n（只印不做）可以看到 make 實際會執行什麼。如果它回你 Nothing to be done for 'all'，那不是壞掉，是產物已經是最新的——先 make clean，或改用 make -Bn 強制印出：

$ make -n
aarch64-linux-gnu-gcc -Wall -Wextra -Werror \
    -ffreestanding -nostdlib -static \
    -Wl,-T,linker/kernel-qemu.ld -Wl,--build-id=none \
    -o build/kernel.elf kernel/boot.S

這一條命令裡，gcc 依序做了前處理、組譯、連結三件事。想看中間產物的話下 -c 就會停在 .o。

角色檔案進版控？
要執行的程式kernel/boot.S是
放在哪裡的規則linker/kernel-qemu.ld是
建置產物build/kernel.elf否

build/ 底下的東西全部可以由原始碼重新產生，所以整個目錄被 .gitignore 排除。make clean 就是直接把它刪掉。

build/virt.dtb 是怎麼來的 —— 它不是「編譯」來的

這裡容易誤會。專案裡沒有任何 .dts 原始檔，virt.dtb 也不是我們寫的。它是 QEMU 在初始化機器時依當下的命令列參數即時合成的，dumpdtb= 只是叫它把合成結果寫出來然後直接結束：

$ make dtb
qemu-system-aarch64 -M virt -cpu cortex-a72 \
    -machine dumpdtb=build/virt.dtb -nographic
    → qemu-system-aarch64: info: dtb dumped to build/virt.dtb. Exiting.

dtc -I dtb -O dts build/virt.dtb        # 二進位 .dtb 轉成人看得懂的 .dts

「即時合成」不是說法上的講究，是可以驗證的。改命令列參數，產生出來的 device tree 就跟著變：

命令列device tree 裡的節點
-m 128M（預設）reg = <0x00 0x40000000 0x00 0x8000000>
-m 512Mreg = <0x00 0x40000000 0x00 0x20000000>
-smp 1（預設）1 個 cpu@ 節點
-smp 44 個 cpu@ 節點

所以要分清楚兩件事：RAM 的起始位址 0x4000_0000 是 virt 這個機器模型定死的（改命令列也不會變），而長度是 -m 決定的。我們的 Makefile 沒有下 -m，所以拿到 QEMU 的預設值 128 MiB。

移植時這裡會變

真實硬體上沒有 QEMU 幫你合成 device tree —— 那份 .dtb 由韌體或 bootloader 提供（樹莓派放在開機分割區裡），再依 boot protocol 把它的位址透過 x0 傳給核心。角色相同，來源不同。這也是為什麼 boot.S 裡那行 mov x0, xzr 在真機上會是個問題。

關鍵在最後一段：-kernel 讓 QEMU 扮演作業系統 loader 的角色。它讀 ELF 檔的 program header，把每個 PT_LOAD 區段搬到 header 記載的實體位址，然後從進入點開始執行。

4心智模型

先說清楚：-M virt 是什麼

QEMU 模擬的不是某一塊真實存在的開發板，而是一塊為了虛擬化而設計的通用板子，名字就叫 virt。它沒有實體對應物，好處是佈局乾淨、週邊都是標準元件（PL011 UART、GICv2 中斷控制器），不必處理任何真實硬體的歷史包袱。

-cpu cortex-a72 則是選 CPU 核心，這裡刻意選跟移植目標 Raspberry Pi 4（BCM2711）同一顆，讓「在 QEMU 上寫的指令能不能在真機上跑」這件事少一個變因。

模型一：記憶體不是一整片，是一張地圖

寫應用程式時，記憶體像一片無差別的空地，作業系統給你哪塊你就用哪塊。裸機不是。位址本身就有意義——某些位址背後是 RAM，某些位址背後根本不是記憶體，而是硬體暫存器。

0x4000_0000 這個數字不是慣例，也不需要相信任何人。它寫在這塊板子自己的 device tree 裡：

輸出是完整的 388 行 dts，memory 節點在三百多行處。要直接撈：make dtb | grep -A3 'memory@'。

$ make dtb | grep -A3 'memory@'
memory@40000000 {
    reg = <0x00 0x40000000 0x00 0x8000000>;
    device_type = "memory";
};

四個數字讀作「起始位址 0x0_4000_0000，長度 0x0_800_0000」（各拆成高低兩個 32-bit）。換一塊板子，第一件事就是找出這個節點。

模型二：linker script 只有一個變數在動

linker script 看起來像一種陌生語言，但它的核心只有一個東西：位置計數器 .。它就是「我現在發到哪個位址了」的游標。

  • 對 . 賦值 = 把游標移到那裡
  • 放進一個 section = 游標往前推該 section 的長度

整份 ELF 裡每一個位址，都是這一個游標移動的結果。理解了這件事，linker script 就從「咒語」變成「一段從上往下執行的程式」。

模型三：section 和 segment 是兩層不同的東西

先講 ELF 是什麼。ELF 是 Linux 世界的執行檔格式，而它其實是一份檔案配兩張目錄——同一堆內容，用兩種方式編目，給兩種不同的讀者看：

目錄單位給誰看怎麼查
section header tablesection（.text、.data、.symtab…）連結器：切得細，方便挑選、合併、丟棄readelf -S
program header tablesegment（PT_LOAD…）載入器：只關心「哪一段要搬進記憶體、搬到哪」readelf -l

所以我們在 linker script 裡操作的是 section，而 QEMU 載入時讀的是 segment；ld 在產生檔案時自己決定怎麼把 section 打包成 segment。PT_LOAD 就是 segment 的一種型別，意思是「這段內容必須先在記憶體裡，程式才跑得起來」。

ELF header 本身（readelf -h）則記著整份檔案的總目：架構、型別、兩張表在哪，以及 e_entry——執行要從哪個位址開始。

這是最容易卡住的觀念。我們在 linker script 裡寫的是 section（.text、.data），但 QEMU 載入時看的是 segment（program header 裡的 PT_LOAD）。

5逐段拆解

boot.S — 為什麼不是 b .

.section .text.boot, "ax"       建立一個叫 .text.boot 的 section
.global _start                  讓這個符號在連結時看得見

_start:
    mov     x0, xzr
halt_loop:
    add     x0, x0, #1
    b       halt_loop

前兩行常被略過，但它們決定了整個佈局能不能成立：

  • "ax" 是這個 section 的旗標：allocatable（執行時要佔記憶體，相對的是除錯資訊那種只存在檔案裡的）＋ executable。可寫的資料段會是 "aw"。
  • section 的名字 .text.boot 就是 linker script 裡 *(.text.boot) 要抓的那個字串。兩邊是純字串比對，打錯不會有任何錯誤訊息——見第 7 節直覺 2。
  • .global _start 把符號從「本檔案私有」提升成「連結時可見」。少了它，ENTRY(_start) 找不到這個符號，ld 會退而使用 fallback 鏈（直覺 1）。

裸機教學裡最常見的收尾是 b .（原地跳躍，無窮迴圈）。這裡刻意不用，理由是可觀測性：

停住的核心和空轉的核心，從外面看完全一樣。如果映像根本沒被載進去、或者 _start 不在正確的位址上，b . 給不出任何線索。而一個一直遞增的 x0，只要在 GDB 裡停兩次、比對數值，就能證明 CPU 真的在執行我們寫的指令。

這一行在 M1 就會拿掉——等 UART 能直接印字，就不需要拐彎抹角了。

xzr：為什麼沒有 x31

AArch64 有 31 個通用暫存器 x0–x30。編碼上的 31 號依指令形式解讀成 XZR（零暫存器）或 SP，沒有 x31 這個東西：

指令編碼31 號的身分
mov x0, xzraa1f03e0XZR（實際是 orr x0, xzr, xzr）
mov x1, sp910003e1SP（實際是 add x1, sp, #0）
mov x2, #0d2800002沒用到 31 號，是另一條指令 MOVZ

linker script — 怎麼讀這個檔

這是三個檔案裡語法最陌生的一個，它不像 C、也不像 shell。但真正要認的只有五種寫法。把註解拿掉之後，整份腳本其實只有這幾行：

ENTRY(_start)                       ──① 進入點

SECTIONS                            ──② 佈局規則的容器
{
    . = 0x40000000;                 ──③ 移動位置計數器

    .text : {                       ──④ 建立一個輸出 section
        *(.text.boot)               ──⑤ 挑輸入 section 塞進去
        *(.text .text.*)
    }
}
寫法意思
①ENTRY(符號)把這個符號的位址填進 ELF header 的 e_entry。QEMU 讀的就是這個欄位。放在 SECTIONS 外面
②SECTIONS { … }所有「東西放哪裡」的規則都寫在這對大括號裡。裡面由上往下依序執行
③. = 位址;. 是位置計數器。賦值 = 把游標移到那裡。分號不能省
④輸出名 : { 規則 }在輸出檔裡建立一個叫「輸出名」的 section。冒號是這個語法的一部分，不是標籤
⑤檔案樣式(section 樣式)從符合「檔案樣式」的輸入檔裡，把符合「section 樣式」的 section 抓進來。* = 所有輸入檔。* 也可以用在 section 名上，例如 .text.*

認得這五種，整份腳本就從「咒語」變成「一段從上往下執行的程式」：把游標移到 0x4000_0000，建一個叫 .text 的輸出 section，先把所有輸入檔的 .text.boot 倒進去，再把 .text 和 .text.* 倒進去。游標隨著內容往前推。

兩個沒寫出來、但你會想問的

沒被任何 *() 規則挑走的輸入 section 會怎樣？它叫 orphan section（孤兒），ld 會自己決定放哪裡，而且不會警告。直覺 2 就是在講這件事。

為什麼不用寫 OUTPUT_FORMAT / OUTPUT_ARCH？因為我們是透過 aarch64-linux-gnu-gcc 呼叫 ld，工具鏈本身已經決定了目標架構與位元組序，腳本不必再指定一次。直接用 ld 時才需要。

M1 的預告：加上 .bss 之後會長什麼樣

現在的腳本只有 .text，因為 boot.S 沒有任何資料。等 M1 進了 C 語言，全域變數會產生 .bss，而沒有作業系統幫你把它清零——那是核心自己的工作。屆時這份腳本大約會多出這一段：

    . = ALIGN(8);                   把游標推到 8 的倍數
    __bss_start = .;                定義一個符號，值 = 游標當下位置
    .bss (NOLOAD) : {               NOLOAD：只佔位址，不佔檔案空間
        *(.bss .bss.*)
        *(COMMON)
    }
    __bss_end = .;

兩個新語法：ALIGN(n) 把位置計數器推到 n 的倍數；符號 = .; 在腳本裡定義一個符號，組合語言和 C 都能取用它的位址。歸零迴圈就是靠 __bss_start 和 __bss_end 知道該清哪一段。同理，印字串需要的 .rodata 也是照這個樣子加一段。

M1 真正的第一道關卡：堆疊

比 .bss 歸零更早會咬人的是堆疊指標。第 6 節量到的機器狀態裡有一項是「SP 進入時為 0」——只要呼叫任何一個 C 函式，進去第一件事就是往 SP 指的地方推東西，也就是往 0x0 以下寫。那裡不是 RAM，是 flash 與 MMIO。

症狀是「進 C 就死，而且死得莫名其妙」，因為錯誤發生在函式序言，跟你寫的邏輯無關。所以進 C 之前，boot.S 必須先做兩件事：把 SP 設到一塊真正的 RAM，然後清 .bss。linker script 屆時也要多提供一個堆疊頂端的符號。

(NOLOAD) 是因為 .bss 全是零，沒必要把幾 KB 的零存進 ELF 檔；它只要在記憶體裡佔住位置就好。這也是為什麼 make dump 裡 FileSiz 和 MemSiz 是兩個獨立的欄位——有了 .bss 之後，MemSiz 會比 FileSiz 大。

Makefile — 每個旗標對應一個失敗

拿掉這個旗標會發生什麼
-nostdlibcrt1.o 被連進來，它自己也定義 _start：multiple definition of '_start'，同時因為 crt1.o 要呼叫 main 而冒出 undefined reference to 'main'。兩個症狀都是這個旗標的。實際會噴三十行左右，其餘多是 __init_array / __ehdr_start / _end 這類連帶失敗，往上找那兩條就好
-Wl,-T改用 ld 內建佈局，載入位址變成 0x400078
--build-id=none.note.gnu.build-id 佔住 0x4000_0000，.text 被擠到 0x4000_0024
-ffreestanding對這個檔案沒有任何可觀察的差異。它是編譯期開關，作用要到 M1 進 C 才顯現
-static多出 .interp／.dynamic／.got，但在 QEMU 上照樣開得起來（見第 7 節）
最容易漏掉的一行

把 linker script 列進 build/kernel.elf 的相依項。少了它，改完 linker script 執行 make 會顯示 Nothing to be done，沿用舊的 ELF——建置是「成功」的，位址卻是舊的。這種錯最難查，因為所有訊號都說沒問題。

6實測數據

以下都量於 binutils 2.38 / gcc 11.4.0 / QEMU 6.2.0 / gdb 12.1（Ubuntu 22.04）。ld 的孤兒 section 擺放規則、gdb 的 prologue 判斷、預設頁大小三者都會隨版本改變，換工具鏈請重新量。

建置產物

$ make dump
0000000040000000 <_start>:
    40000000:  aa1f03e0   mov  x0, xzr
0000000040000004 <halt_loop>:
    40000004:  91000400   add  x0, x0, #0x1
    40000008:  17ffffff   b    40000004

  Entry point address:  0x40000000
  LOAD  Offset 0x10000  VirtAddr 0x40000000  PhysAddr 0x40000000
        FileSiz 0xc     MemSiz 0xc           Align 0x10000

Offset 0x10000 是 segment 在檔案裡的位移，不是記憶體位址。ELF 規定 segment 的檔案位移與虛擬位址必須對 Align 同餘，而 VirtAddr 是 0x4000_0000（0x10000 的倍數），所以 Offset 也只能是 0x10000 的倍數——這就是那一大段填充的由來。0x10000（64 KiB）是 ld 對 aarch64 的預設 max-page-size。

66088 這個數字是這樣湊出來的：

0x10000  = 65536   前面的 ELF header、program header 與對齊填充
    + 12 = 65548   .text 的三條指令
   …            +  .symtab / .strtab / .shstrtab
       = 65768   section header table 的起點（readelf -h 的 Start of section headers）
+ 5 × 64 =   320   五個 section header，每個 64 bytes
       = 66088

加上 -Wl,-z,max-page-size=4096 檔案會縮成 4648 bytes。QEMU 不在意這件事，所以不加——多一個旗標就多一個要解釋的東西。

VirtAddr 和 PhysAddr 為什麼是同一個值

因為 MMU 還沒開。沒有分頁表，虛擬位址就等於實體位址，兩欄自然相同。等 M5 把 MMU 打開、核心搬到高位址（例如 0xffff_0000_…）之後，這兩欄就會分家：VirtAddr 是程式碼裡用的位址，PhysAddr 是它實際被放進 RAM 的位置。linker script 用 AT() 指定後者。

證明 CPU 真的在執行

$ make debug
0x0000000040000000 in _start ()
Breakpoint 1 at 0x40000008

Breakpoint 1, 0x0000000040000008 in halt_loop ()
$1 = 1

Breakpoint 1, 0x0000000040000008 in halt_loop ()
$2 = 2
(gdb)

x0 兩次不同 → CPU 真的在執行我們寫的指令，不是卡死、也不是根本沒載進去。這就是 M0 的驗收。

make debug 自動做完這兩次比對之後，會把你留在 (gdb) 提示字元前，接下來可以自己探索：

(gdb) c              繼續，再停一次（x0 會是 3）
(gdb) p $x0          印暫存器
(gdb) p/x $cpsr      0x400003c5
(gdb) x/3i $pc       看目前位置的三條指令
(gdb) q              離開（QEMU 會被一起收掉）
為什麼 debug 用 break halt_loop 而不是 break *halt_loop

直覺 4 會說明 break *halt_loop 才停得到真正的第一條指令。這裡刻意不用星號，因為斷點落在哪其實不影響結論（要的是「兩次的值不同」），而讓讀者親眼看到 0x4000_0008 這個「意料之外」的位址，比事先繞過它更有教育意義。想要乾淨的行為，在 (gdb) 裡自己下 break *halt_loop 就好。

開機當下的機器狀態

項目量法結果
特權等級p/x $cpsr → 0x400003c5，取 bits[3:0]0b0101 = EL1h
中斷遮罩同上，取 bits[9:6]0b1111 = DAIF 全遮
暫存器p $x0 … p $spx0–x3、SP 全為 0
核心數info threads只有 CPU#0
RAM 內容倒出整個 128 MiB 掃描非零的只有核心自己那 12 bytes

0x400003c5 這個值怎麼讀：低 4 位 0b0101 裡，bits[3:2] = 01 是 EL 編號（所以是 EL1；EL2 會是 10、EL3 是 11），bit[0] 是 SPSel——1 表示用該 EL 自己的堆疊指標 SP_EL1，寫作 EL1h（h = handler）；0 表示沿用 SP_EL0，寫作 EL1t（t = thread）。再往上 bits[9:6] = 0b1111 是 DAIF，四個中斷都被遮住（開頭那個 0x4000_0000 則是條件旗標 Z，跟開機狀態無關）——這也是開機狀態的一部分，M4 開中斷時要處理的就是它。

注意 p $CurrentEL 在 gdb 12.1 回傳 void——它沒有把這個系統暫存器暴露給遠端目標，所以只能繞道 PSTATE。

7被推翻的直覺

這一節是這份教材裡最貴的部分。以下每一條都是「原本以為是這樣，實測之後發現不是」。

直覺 1

「沒寫 ENTRY()，ld 會去找 _start」

錯。ld 的 fallback 鏈是：符號 start（沒有底線）→ .text 的第一個 byte → 位址 0。_start 根本不在鏈上。

那為什麼平常省略 ENTRY() 還是能動？因為 ld 內建的預設腳本裡寫了 ENTRY(_start)；而 -T 會把整份內建腳本換掉，那行 ENTRY 也就一起沒了。

這條的教訓不只是結論，是怎麼設計實驗：如果把 _start 留在 .text 開頭去測，兩種假說都預測 0x4000_0000，實驗不可能失敗，也就什麼都證明不了。要在 _start 前面墊三個 nop，兩個答案才會分岔。

直覺 2

「section 名稱拼錯，_start 就不在 0x4000_0000 了」

錯，而且錯得很安靜。拼成 .text.b00t 會被下一行 *(.text .text.*) 接住；拼成 .txet.boot 變成真正的孤兒 section（orphan section：沒有被 linker script 裡任何一條 *() 規則挑走的輸入 section，ld 只好自己找地方放），而 ld 把孤兒放在 . 的當下位置——剛好也是 0x4000_0000。兩種拼錯都能開機，而且 ld 一個警告都不會給。

那 *(.text.boot) 那行到底在做什麼？是排序。輸入檔多於一個時才看得出來：

有那行：  40000000 _start      4000000c other_func   e_entry 40000000
沒那行：  40000000 other_func  40000004 _start       e_entry 40000004

（這裡的 other_func 只有一條 ret。指令數不同，位址自然跟著移，但誰排前面的結論不變。）

直覺 3

「.note.gnu.build-id 佔住載入位址，核心就開不起來」

在 QEMU 上照樣開得起來，因為 e_entry 跟著 .text 一起移到 0x4000_0024，QEMU 照著跳就對了。

真正會死的是攤平成 raw binary 之後（Raspberry Pi 的 kernel8.img 就是這種格式，從第 0 個 byte 直接開始執行）：

00000000: 0400 0000 1400 0000 0300 0000 474e 5500   ....GNU.
   0:  00000004   udf  #4      ← 未定義指令，當場死

所以 --build-id=none 是為了移植到樹莓派而下的，不是為了現在。

直覺 4

「GDB 的斷點會停在 halt_loop 的第一行」

不會。在沒有除錯資訊時 GDB 靠掃描指令猜 prologue，會把開頭連續的一整串 add 都跳過。這裡只有一條，所以停在 b（0x4000_0008），第一次看到的 x0 已經是 1。改成三條 add，它會一路跳到第四條指令。

加上 -g 重新建置，GDB 改查行號表，斷點就回到 0x4000_0004、第一次停 x0 = 0。想繞過整件事，用 break *halt_loop（星號 = 照我給的位址下，別自己動）。

直覺 5

「mov x0, xzr 是無害的」

今天無害——實測 QEMU 交過來時 x0 本來就是 0。但 AArch64 的 boot protocol 規定 bootloader 用 x0 傳 device tree 的位址，樹莓派的 firmware 就是這樣做的。這一行在真機上會把 DTB 指標洗掉，而且救不回來。M1 會移除它。

直覺 6

「.bss 沒清零，馬上就會看到 bug」

在 QEMU 上永遠看不到。實測把整個 128 MiB RAM 倒出來掃描，非零的只有核心自己那 12 bytes——QEMU 交過來的記憶體本來就是乾淨的。

這是一個在這個平台上做不出來的實驗。M1 還是要寫歸零迴圈，理由只能是推理，不能是實測。知道哪些事情「這裡驗不了」，跟知道哪些事情驗得了一樣重要。

8精隨

如果 M0 只能留下三句話：

  1. 位址是硬體的性質，不是慣例。 0x4000_0000 不是背來的，是從 device tree 查來的。換板子時要重查的東西，就是這種東西。
  2. 先建立回饋迴路，再寫功能。 三條指令的價值不在指令本身，在於它讓「改一行 → 看到差異」這條路打通了。b . 之所以被換掉，就是因為它不提供回饋。
  3. 「建置成功」不等於「做對了」。 M0 遇到的三個坑——linker script 沒列進相依、section 名稱拼錯、build-id 佔住載入位址——全部都是建置完全成功的情況下發生的。裸機開發沒有 segfault 幫你擋，唯一的防線是自己動手量。

9面試 60 秒

Q：一個裸機核心從編譯到執行，中間發生了什麼？

原始碼經過組譯得到 .o，連結時用自訂的 linker script 取代 ld 的預設佈局，指定程式碼放在 0x4000_0000——這個位址來自目標板的 device tree，是 RAM 的起點，再低就是 MMIO 了。linker script 的 ENTRY() 會填 ELF header 的 e_entry。QEMU 以 -kernel 扮演 ELF loader，把 PT_LOAD 區段搬到 program header 記載的實體位址，再把 PC 設到進入點。整個過程沒有作業系統參與，所以要自己下 -nostdlib 擋掉 C 啟動檔，否則它會帶進自己的 _start 造成重複定義。

Q：怎麼確認核心真的在跑？

用 QEMU 的 -S -s 停在第一條指令並開 GDB 遠端埠。核心停在一個遞增暫存器的迴圈，不是 b .——因為停住的核心和空轉的核心從外面看一樣，遞增值才能區分。連續中斷兩次，值不同就證明在執行。（readelf 只能確認 ELF 建對了，證明不了 CPU 有沒有跑，這是兩回事。）
