armos · 里程碑 M1

開機流程：從韌體手上接過機器

M0 讓 CPU 跑起來了。M1 要把它整理成一個乾淨的已知狀態，才能交給 C 語言

1要解決什麼問題

M0 結束時，核心停在一個遞增暫存器的迴圈裡。它會動，但機器的狀態是韌體給什麼就是什麼——我們從來沒問過現在是什麼狀況。

問題是不同平台給的東西不一樣：

平台交給我們時的狀態
QEMU -M virtEL1、單核、SP = 0、BSS 未清
QEMU -M virt,virtualization=onEL2、單核、SP = 0、BSS 未清
Raspberry Pi 4EL2、四顆核心全開、SP 未定義、BSS 未清
（依規格文件，本專案尚無實機可驗；上面兩列是本機實測）

C 語言完全不知道這些事。它假設：有一個能用的堆疊、未初始化的全域變數是 0、而且只有一個執行流程。這三件事沒有人會幫你準備。

所以 M1 的工作是：把上面那張表的差異抹平，變成一個固定的起點，然後才跳進 C。

2動手：跑起來看

這個里程碑的重點是「同一份程式在兩種起點下都要落在 EL1」，所以要跑兩次。五步，大約十分鐘。

這一節不需要看懂名詞

底下會出現 CurrentEL、HCR_EL2、eret、mrs 這些東西，現在都不用懂。這一節的目的是先讓你看到現象——尤其是步驟 5 那兩種當機的樣子。看過之後再讀第 3 節之後的解釋，會比一開始就啃名詞好記得多。

每個名詞第一次出現時都標了在第幾節解釋，想先查也可以。

怎麼讀 CurrentEL（這顆暫存器是什麼，第 3 節會講）

p $CurrentEL 在 gdb 12.1 會回 void——它沒有把這顆系統暫存器暴露給遠端目標。兩種替代做法：

方法一：從 PSTATE 反推。p ($cpsr >> 2) & 3，取 bits[3:2]。這是最方便的。

方法二：讓程式自己讀給你看。 我們的 _start 第一行就是 mrs x9, CurrentEL，執行完 x9 裡就是答案。

但不能直接在 make debug 的提示字元下 stepi。 那個目標為了自動比對兩次 x10，已經 continue 過兩次，等你拿到 (gdb) 時程式早就跑到 halt_loop 了，這時 stepi 只是在迴圈裡踏步，x9 讀出來會是 0x40000028（adr 留下的殘值），不是 EL 編號。

要看進入點，得自己起一份不會自動 continue 的：

$ qemu-system-aarch64 -M virt -cpu cortex-a72 -display none \
      -serial null -kernel build/kernel.elf -S -gdb tcp::12345 &
$ gdb-multiarch -q build/kernel.elf -ex 'target remote :12345'

(gdb) stepi          執行第一條指令 mrs x9, CurrentEL
(gdb) p/x $x9
$1 = 0x4             ← 一般開機；換成 virt,virtualization=on 會是 0x8

這也是為什麼方法一比較實用：p ($cpsr >> 2) & 3 任何時候都問得到，不必care程式跑到哪了。

同一個限制對 HCR_EL2、SPSR_EL2、VBAR_EL1 全都適用——gdb 12.1 一律回 void。想看那些暫存器，就寫一小段只做 mrs 的暫時程式，讓它把值搬進通用暫存器。第 7 節那兩個 _EL2 的值就是這樣量出來的。

步驟 4：用 EL2 開機（模擬樹莓派）

Makefile 有對應的目標：

$ make qemu-el2      直接跑
$ make debug-el2     停在第一條指令並接上 GDB

它們就是把 -M virt 換成 -M virt,virtualization=on，其餘完全一樣。展開的完整指令是：

qemu-system-aarch64 -M virt,virtualization=on -cpu cortex-a72 \
    -display none -serial file:build/serial.log \
    -kernel build/kernel.elf -S -s

make debug-el2 應該印出跟步驟 3 一模一樣的 $1 = 1 / $2 = 2。停在 (gdb) 之後確認自己在 EL1：

(gdb) p ($cpsr >> 2) & 3
$3 = 1                     ← 進來時是 EL2，現在已經降到 EL1
(gdb) p/x $cpsr
$4 = 0x3c5                 ← 正是我們寫進 SPSR_EL2 的值

兩個目標印出相同的 x10，但走的路完全不同——這就是降級有效的證明。

順帶一提，兩條路徑的 $cpsr 高位不一樣：一般開機是 0x600003c5，EL2 路徑是 0x3c5。差的 0x6000_0000 是條件旗標 NZCV，一般開機那條被 cmp 設過，而 EL2 那條在 eret 時被 SPSR_EL2 的值整個覆蓋掉了。低 12 位才是我們關心的狀態。

步驟 5：把它弄壞（最重要的一步）

前四步都在確認「一切正常」。真正學到東西是靠看壞掉的樣子。

先確認怎麼復原

實驗 2 值得看清楚。少了「先問樓層」，在 QEMU 一般開機（已經是 EL1）就會直接去寫 HCR_EL2，而那顆暫存器在 EL1 讀不到：

(gdb) p/x $pc
$1 = 0x200                 ← 不是我們的程式碼
(gdb) p $x10
$2 = 0                     ← 計數器一次都沒跑到
(gdb) x/2i $pc

0x200 這個位址不是隨機的。 例外向量表的基底位址存在 VBAR_EL1，它重置後是 0；而「同一層、同步例外」的入口剛好在基底 + 0x200。所以 CPU 是規規矩矩地跳去處理例外了——只是那個位址上什麼都沒有，因為例外向量表要到 M3 才會建。

這就是本專案反覆強調的那種失敗：沒有錯誤訊息，只有一個跑到不知道哪裡去的 PC。

實驗 2（沒判斷 EL）實驗 3（沒設 RW）
發生在哪msr hcr_el2 當下eret 之後的下一次取指令
當時的 EL12（換層失敗了）

看 EL 就能分辨——這是裸機除錯的典型手法：症狀相同時，去找那個會分岔的欄位。

3先認識「特權等級」

ARM64 把權力分成四層，叫 Exception Level（例外等級），簡稱 EL。數字越大權力越大。

每一層都有自己一整套系統暫存器。名字後面的 _EL1、_EL2 就是在講「這個暫存器屬於哪一層」。例如例外向量表的位址，EL1 用 VBAR_EL1，EL2 用 VBAR_EL2，是兩個不同的暫存器。

系統暫存器怎麼讀寫

通用暫存器 x0–x30 可以直接拿來運算。系統暫存器不行，必須先搬出來：

mrs  x9, CurrentEL      系統暫存器 → 通用暫存器（Move to Register from System）
msr  hcr_el2, x9        通用暫存器 → 系統暫存器（Move to System Register）

4為什麼要從 EL2 降到 EL1

直接講結論：今天不降也完全能跑。 實測把降級程式碼整段拿掉，核心在 EL2 照樣正常執行，沒有任何錯誤訊息。

降級的理由全部在後面的里程碑：

什麼時候會用到的東西待在 EL2 的話
M3 例外處理VBAR_EL1要改用 VBAR_EL2
M5 開 MMUTTBR0_EL1要改用 TTBR0_EL2
M8 使用者模式EL0 出事自動跳到 EL1要額外設定才跳得到 EL2

而課本、Linux 原始碼、以及本專案參考的所有資料，走的都是 EL1 這條路。待在 EL2 會處處對不上。

還有一個更直接的理由：兩個平台給的起點不一樣。不統一的話，M3 之後每一段跟特權等級有關的程式碼都要寫兩個版本。

這個決定違反了專案自己的規則

本專案的原則之一是「只寫現在就有作用的東西，判準是拿掉它現在會壞嗎」。而這段降級程式碼拿掉不會壞——嚴格講它應該推遲到 M3，因為那才是「我在哪一層」第一次真的產生差別的時間點（要設 VBAR_EL1）。

還是現在做的理由是 M1 的定位：這個里程碑的主題就是「把機器整理成一個乾淨的已知狀態，再交給 C 語言」。設堆疊指標、清 BSS 都是這件事，「現在在哪一層」同樣是那個狀態的一部分。若留到 M3，M1 交給 C 的會是一個「視平台而異」的狀態，跟這個里程碑的目的相違；而且屆時這段程式碼還要回頭改寫。

代價要記下來：多了十幾行今天不做也不會壞的程式碼；而且從此綁定了「核心跑在 EL1」這個前提。日後若要做 hypervisor（自己跑在 EL2、管理底下的客戶 OS），這個決定要整個推翻。目前的規劃裡沒有這件事。

5降級是怎麼做到的

ARM 沒有「降低特權等級」這條指令。往上是硬體自動的（發生例外時），往下只能靠軟體自己走。

唯一的辦法是借用 eret——它本來的用途是「例外處理完了，回到原本的地方」。既然「回去」的時候可以指定要回到哪一層，那就假裝自己剛處理完例外，把目的地填成 EL1，然後按下去。

那些數值是怎麼來的

HCR_EL2 的 bit 31（RW）決定 EL1 用 64 位元還是 32 位元。實測這台機器上 HCR_EL2 開機時是 0x0，也就是 RW = 0 → EL1 是 32 位元。

不設它會怎樣？直覺上會猜「A64 指令被當成 A32 解讀，整個亂掉」。實測不是這樣。

eret 之前   EL = 2
eret 之後   pc = 0x40000020（el1_entry）   EL = 2   PSTATE.IL = 1
再一步      pc = 0x200

HCR_EL2.RW = 0（EL1 是 32 位元）跟 SPSR_EL2.M[4] = 0（要求 64 位元）互相矛盾，這叫 illegal exception return（非法的例外返回）。硬體的處理方式是：不換層、把 PSTATE 的 IL 位元（bit 20，Illegal Execution state）設起來，然後下一次取指令就直接 trap 到例外向量。

所以症狀跟「忘記先判斷 EL」很像（都是 pc = 0x200、x10 = 0），但成因完全不同：一個是在 EL1 誤碰 EL2 暫存器，一個是 eret 的兩個設定打架。A64 指令從頭到尾沒有被當成 A32 執行過。

SPSR_EL2 填 0x3c5，拆開來看：

欄位值意思
M[3:0]（bits[3:0]）0101EL1h。M[3:2] = 01 是 EL 編號 → EL1；M[1] 保留為 0；M[0] = 1 是 SPSel → 用自己的 SP_EL1。跟 CurrentEL 一樣，EL 編號都放在 bits[3:2]
M[4]（bit 4）0降下去之後用 AArch64（64 位元）。這一位和 HCR_EL2.RW 講的是同一件事，兩邊都要對
D A I F（bits[9:6]）1111四種中斷全部遮起來。D=Debug、A=SError、I=IRQ、F=FIQ

注意 DAIF 這個欄位跨在半位元組（4 bit）的分界上——bit9、bit8 屬於左邊那組，bit7、bit6 屬於中間那組。所以看 0x3c5 的十六進位寫法反而不容易對出來，要照上面的 bit 編號一格一格數。

這個數字不是查表查來的，是抄 QEMU 自己的答案：M0 量過，QEMU 直接從 EL1 進入時 $cpsr 的低 12 位就是 0x3c5。我們只是把那個狀態手動複製一份。

全名遮起來的原因
DDebug 除錯例外例外向量表要到 M3 才有。現在放中斷進來，CPU 會跳到一個空位址，而且因為沒有例外處理器，連錯誤訊息都不會有。先關起來，等有人接得住再開。
ASError 非同步錯誤
IIRQ 一般中斷
FFIQ 快速中斷

EL1h 和 EL1t 差在哪

每一層都有自己的堆疊指標。但 EL1 可以選要用自己的 SP_EL1，還是借用 SP_EL0：

寫法bits[3:0]用哪支堆疊指標
EL1h（h = handler）0101SP_EL1 ← 我們要這個
EL1t（t = thread）0100SP_EL0

只差最低那一個 bit。 填錯的話下一步設的堆疊指標會設到「沒人在用的那一支」，一呼叫函式就死，而且症狀完全看不出原因。

為什麼要先問「我在哪一層」

因為 QEMU 一般開機直接就是 EL1，而 _EL2 結尾的暫存器在 EL1 根本讀不到。不問就做，在 QEMU 上會當場觸發例外。

「無聲當機」聽起來像形容詞，但它有具體的位址。實測把那三行判斷刪掉之後：

p/x $pc   →  0x200      不是我們的程式碼
p $x10    →  0          計數器一次都沒跑到

0x200 不是隨機的。例外向量表的基底位址存在 VBAR_EL1，重置後是 0；而「同一層、同步例外」的入口在基底 + 0x200。CPU 是規規矩矩地跳去處理例外了——只是那個位址上是記憶體垃圾，因為例外向量表要到 M3 才建。

6逐行拆解

_start:
    mrs     x9, CurrentEL           讀「我在哪一層」
    cmp     x9, #(1 << 2)           跟 4 比（EL1 × 4）
    b.eq    el1_entry               已經在 EL1 → 整段跳過

    mov     x9, #(1 << 31)          📋 規矩：EL1 用 64 位元
    msr     hcr_el2, x9
    mov     x9, #0x3c5              🪪 身分：EL1h、中斷全遮
    msr     spsr_el2, x9
    adr     x9, el1_entry           📍 目的地
    msr     elr_el2, x9
    eret                            出發

el1_entry:                          兩條路在這裡會合，保證在 EL1

adr 是什麼指令

adr x9, el1_entry 的意思是「把 el1_entry 這個標籤的位址放進 x9」——不是去那個位址讀值，是取位址本身。

它跟另外兩個很像的寫法差在這裡：

寫法做什麼範圍
adr x9, label取位址。用「現在的 PC 加一個位移」算出來±1 MB
ldr x9, =label取位址。編譯器把絕對位址存在附近，再讀出來不限
ldr x9, [x10]去 x10 指的位址讀一個值—

這裡用 adr 有一個實際好處：它算出來的是相對位址，所以整段程式碼被搬到記憶體別的地方也照樣正確。ldr = 存的是絕對位址，搬家就錯了。M5 開 MMU 把核心搬到高位址時，這個差別會變得很重要。

反組譯可以看到它確實被算成了絕對位址：

4000001c:  10000069   adr  x9, 40000028 <el1_entry>

為什麼 CurrentEL 要跟 4 比

CurrentEL 只有 bits[3:2] 有意義，其他位元永遠是 0。所以整個暫存器讀出來剛好是 EL 編號 × 4：

EL1  →  0b0100  =  0x4
EL2  →  0b1000  =  0x8

為什麼用 x9 / x10，不用 x0

AArch64 的開機協定規定 x0 帶著 device tree 的位址，樹莓派的韌體就是這樣傳的。M0 的 mov x0, xzr 會把它洗掉——在 QEMU 上剛好無害（x0 本來就是 0），但移植到真機就是災難。

所以現在所有暫用都改成 x9／x10，把 x0–x3 原封不動留給後面的里程碑。

7實測數據

這一節是數值彙整，方便日後查；操作步驟在第 2 節。量於 binutils 2.38 / gcc 11.4.0 / QEMU 6.2.0 / gdb 12.1（Ubuntu 22.04）。

這些 _EL2 的值是怎麼量出來的

gdb 12.1 讀不到 HCR_EL2、SPSR_EL2、VBAR_EL1 這些系統暫存器（一律回 void）。下面的數值是寫一段只做 mrs 的暫時核心，把值搬進通用暫存器再讀出來的：

_start:
    mrs     x11, hcr_el2
    mrs     x12, spsr_el2
halt:
    b       halt

這個手法對任何 gdb 讀不到的系統暫存器都適用，後面的里程碑會一直用到。

兩種開機方式進來時的狀態

$ qemu-system-aarch64 -M virt ...
  CurrentEL = 0x4      → EL1

$ qemu-system-aarch64 -M virt,virtualization=on ...
  CurrentEL = 0x8      → EL2
  HCR_EL2   = 0x0      → RW = 0，也就是「EL1 用 32 位元」
  SPSR_EL2  = 0x0

降級前後

開機方式進入點的 EL跑起來之後的 EL
-M virt11 ✅ 跳過降級
-M virt,virtualization=on21 ✅ 走完降級
對照組：把降級程式碼拿掉22 ❌ 卡在 EL2

最後一列是重點。這個實驗被刻意設計成可能失敗——有降級和沒降級預測不同的答案，所以結果才有意義。

降級之後 $cpsr 讀出來是 0x3c5，跟我們寫進 SPSR_EL2 的值一模一樣，也跟 QEMU 直接進 EL1 時的低位相同。

8被推翻的直覺

直覺 1

「QEMU 加上 -smp 4，四顆核心就會一起衝進來，所以要寫程式篩選 core 0」

錯。實測 -smp 4 讓它自由跑三秒之後：

CPU#0  [running]  停在 halt_loop     ← 只有這顆跑了
CPU#1  [halted ]  停在 _start
CPU#2  [halted ]  停在 _start
CPU#3  [halted ]  停在 _start        ← 一條指令都沒執行

QEMU 的 virt 機器不會在開機時放出副核心。它們被關在「電源關閉」狀態，要等軟體用 PSCI（Power State Coordination Interface，電源狀態協調介面）主動叫醒才會動。

所以核心篩選的程式碼在 QEMU 上根本不會被執行到，寫了也驗不了。這件事整包留到 M9 移植樹莓派時再做——那時四顆核心才是真的一起進來。

直覺 2

「跑在 EL2 權限比較高，應該什麼都能做，那待著就好」

權限確實比較高，而且今天真的照樣跑。但「權限高」不等於「方便」——每一層有自己一整套暫存器，EL2 那一套跟所有教材、Linux 原始碼用的都不一樣。

更關鍵的是 M8：使用者程式跑在 EL0，出事時硬體預設把它送到 EL1。核心在 EL2 的話，這條最基本的路要額外設定才走得通。

直覺 3

「pkill -f qemu-system-aarch64 可以安全地清掉殘留的 QEMU」

這條指令會把執行它的那個 shell 自己也殺掉。因為 -f 比對的是完整命令列，而執行這條指令的 shell，其命令列裡就含有 qemu-system-aarch64 這串字。

症狀是指令沒有輸出、然後行程被 SIGTERM 收掉，離開碼 143（128 + 訊號 15）。

但這只在特定情境下會發生，實測分成兩種：

誰執行這條指令它自己的命令列結果
互動式終端機直接敲-bash，不含目標字串不會死
Makefile recipe、bash -c '...'、CI 腳本含目標字串自殺

pgrep -f 有同樣的問題。那改成 -x（比對行程名而非命令列）呢？會遇到第二個坑：

$ ps -eo pid,comm | grep qemu
   5132 qemu-system-aar          ← 名字被截斷了

$ pgrep -x qemu-system-aarch64   （無輸出，找不到）
$ pgrep -x qemu-system-aar
5132

Linux 的行程名（comm）上限是 15 個字元，而 qemu-system-aarch64 有 19 個。-x 要求完全相同，所以拿全名去比永遠比不到——而且不會有任何錯誤訊息，只是安靜地什麼都沒殺到。

正確寫法：pkill -x qemu-system-aar（截斷後的名字），或用 ss -ltnp 從佔用的 port 反查 PID 再精確 kill。

9精髓

  1. 權力往上是自動的，往下要自己走。 硬體只在出事時把你抬上去，從來不會主動把你放下來。降級是軟體的責任，而且要借用「返回」這個機制來完成。
  2. 先問狀態，再動作。 同一份程式碼要能在兩種平台跑，唯一的辦法是先問「我現在是什麼情況」。不問就做，在其中一種平台上必然出事。
  3. 沒有例外處理器的時候，所有錯誤都是無聲的。 這也是 DAIF 要先全遮的原因——不是因為中斷有害，是因為現在沒有人接得住。

10一頁式小抄

三個暫存器

HCR_EL2到了 EL1 要守什麼規矩bit31 = 1 → 64 位元
SPSR_EL2回去之後是誰0x3c5 → EL1h + DAIF 遮
ELR_EL2回去之後從哪跑el1_entry

關鍵數值

CurrentEL = EL 編號 × 4      EL1 → 0x4    EL2 → 0x8
SPSR bits[3:0]               0101 = EL1h  0100 = EL1t
SPSR bits[9:6]               1111 = DAIF 全遮
HCR_EL2 bit31 (RW)           1 = EL1 用 AArch64

GDB 速查

p/x $cpsr                看處理器狀態
p ($cpsr >> 2) & 3       取出 EL 編號
info threads             確認幾顆核心在跑

qemu-system-aarch64 -M virt ...                     進來就 EL1
qemu-system-aarch64 -M virt,virtualization=on ...   進來是 EL2
