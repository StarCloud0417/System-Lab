armos · 里程碑 M1

開機流程：從韌體手上接過機器

M0 讓 CPU 跑起來了。M1 要把它整理成一個乾淨的已知狀態——固定的層級、一個堆疊、一塊歸零的記憶體——才能交給 C 語言

不確定這個里程碑在整張圖的哪個位置？先看 ARM64 全局地圖。

1要解決什麼問題

M0 結束時，核心停在一個遞增暫存器的迴圈裡。它會動，但機器的狀態是韌體給什麼就是什麼——我們從來沒問過現在是什麼狀況。

問題是不同平台給的東西不一樣：

平台交給我們時的狀態
QEMU -M virtEL1、單核、SP = 0、BSS 未清
QEMU -M virt,virtualization=onEL2、單核、SP = 0、BSS 未清
Raspberry Pi 4EL2、四顆核心全開、SP 未定義、BSS 未清
（依規格文件，本專案尚無實機可驗；上面兩列是本機實測）

（SP 是堆疊指標，記著「暫存不下的東西放在記憶體哪裡」，第 7 節細講；BSS 是編譯器放「沒給初始值的全域變數」的地方，第 8 節細講。這兩個名詞現在知道大概是什麼就好。）

C 語言完全不知道這些事。它假設：有一個能用的堆疊、未初始化的全域變數是 0、而且只有一個執行流程。這三件事沒有人會幫你準備。

所以 M1 的工作是：把上面那張表的差異抹平，變成一個固定的起點，然後才跳進 C。

步驟 3：一般開機（進來就是 EL1）

$ make debug

Breakpoint 1, 0x000000004000009c in kernel_main ()

EL        = $2 = 1

(gdb)

三個數字各對應 M1 的一件事：EL 是 1（降級成功或本來就在）、SP 不是 0（堆疊有設）、boot_counter 是 0（.bss 清過了）。

SP 為什麼是 0x400100f0，不是 __stack_top 的 0x40010100？

差了 16，不是 bug。break kernel_main 下的斷點會跳過函式序言（prologue）——也就是 stp x29, x30, [sp, #-16]! 那一條。等你看到提示字元，那 16 個 byte 已經推上去了。第 7.1 節有單步的完整過程。

先講 $cpsr 是什麼

AArch64 把「處理器目前的狀態」叫做 PSTATE（processor state）——現在在哪一層、中斷有沒有被遮、上一次比較的結果是什麼，全都在裡面。

但 gdb 裡沒有 $pstate，要打 $cpsr。 CPSR 是 32 位元 ARM 時代的名字，gdb 沿用了它來裝 AArch64 的 PSTATE。看到 $cpsr 不要以為教材寫錯暫存器了，這只是個歷史包袱。

它的 bits[3:2] 就是目前的 EL 編號，所以 p ($cpsr >> 2) & 3 隨時問得到「我在第幾層」。make debug 印的 EL 就是這樣算的。

gdb 讀得到哪些系統暫存器

QEMU 的 gdb 介面開放了幾百顆暫存器（maint print remote-registers 列得出來），而且數量跟著機器變：

-M virt                     383 顆
-M virt,virtualization=on   411 顆

差的不是整整 28 顆，而是多 29 顆、少 1 顆：多的是 HCR_EL2、SPSR_EL2、VBAR_EL2 這類EL2 的控制暫存器；少的是 RVBAR_EL1——QEMU 只在「最高的那一層」暴露 RVBAR，開了 EL2 之後它就變成 RVBAR_EL2 了。

（-M virt 下並非完全沒有帶 _EL2 字樣的暫存器，ACTLR_EL2、DACR32_EL2 等四顆還在，也讀得到值。「名字裡有 _EL2」和「這台機器有 EL2」是兩件事。）

HCR_EL2、SPSR_EL2、TTBR0_EL1、ESR_EL1 這些後面會用到的，都讀得到（_EL2 那幾顆要用 virtualization=on 開機）：

(gdb) p/x $HCR_EL2      0x0        降級之後 0x80000000
(gdb) p/x $SPSR_EL2     0x0        降級之後 0x3c5
(gdb) p/x $VBAR         0x0        EL1 的向量表基底
(gdb) p/x $SCTLR        0xc50838   EL1 的系統控制

$hcr_el2 → void小寫一律大寫：$HCR_EL2

0x200 這個位址不是隨機的。 例外向量表的基底位址存在 VBAR_EL1，它重置後是 0；而「同一層、同步例外」的入口剛好在基底 + 0x200。所以 CPU 是規規矩矩地跳去處理例外了——只是那裡沒有向量表，要到 M3 才會建。

那裡是什麼？也查得到，而且很有意思：

(gdb) x/2xw 0x0
0x0:  0xedfe0dd0  0x00001000

(gdb) x/4xb 0x0
0x0:  0xd0  0x0d  0xfe  0xed      ← 一個 byte 一個 byte 讀：d00dfeed

(gdb) x/s 0x200
0x200: "020000"                   ← DTB 的字串區

x/2xw 印的是一個 32 位元的數，而 magic 在檔案裡是四個 byte，所以顯示順序看起來是反的。x/4xb 一個 byte 一個 byte 印才對得起來。不是跑錯了。

QEMU 把這台機器的 device tree 放在位址 0（總長 1 MB），所以 0x200 落在它的字串區裡面。CPU 是在把 device tree 的 ASCII 當成指令執行——難怪印出來是 adr x16, 0x60845 和 udf。第 6 節會講到 x0 帶著 device tree 位址，講的就是這個東西。

這就是本專案反覆強調的那種失敗：沒有錯誤訊息，只有一個跑到不知道哪裡去的 PC。實驗 4 的堆疊沒設、第 7.6 節的堆疊爆掉，最後都落在同一個 0x200——三種完全不同的錯，長成同一個樣子。這正是 M3 要先蓋例外向量表的原因。

看 EL 就能分辨——這是裸機除錯的典型手法：症狀相同時，去找那個會分岔的欄位。

怎麼讀 ESR_EL1

ESR = Exception Syndrome Register，硬體用它告訴你「為什麼會有這個例外」。最有用的是 EC 欄位（bits[31:26]），也就是例外的種類：

(gdb) p/x $ESR_EL1 >> 26

0x25   Data Abort，同一層         ← 堆疊沒設那種（lab 的 step3）
0x00   Unknown                    ← 在 EL1 碰 EL2 暫存器（lab 的 step8）

實測兩者的完整值是 0x96000040 和 0x2000000。0x25 那筆還可以再看 FAR_EL1（Fault Address Register，出事的位址），實測是 0xfffffffffffffff0——正是 sp - 16。

lab/m1 的 make step3 和 make step8 都會印這兩個值。

3先認識「特權等級」

ARM64 把權力分成四層，叫 Exception Level（例外等級），簡稱 EL。數字越大權力越大。

每一層都有自己一整套系統暫存器。名字後面的 _EL1、_EL2 就是在講「這個暫存器屬於哪一層」。例如例外向量表的位址，EL1 用 VBAR_EL1，EL2 用 VBAR_EL2，是兩個不同的暫存器。

系統暫存器怎麼讀寫

通用暫存器 x0–x30 可以直接拿來運算。系統暫存器不行，必須先搬出來：

mrs  x9, CurrentEL      系統暫存器 → 通用暫存器（Move to Register from System）
msr  hcr_el2, x9        通用暫存器 → 系統暫存器（Move to System Register）

4為什麼要從 EL2 降到 EL1

直接講結論：今天不降也完全能跑。 實測把降級程式碼整段拿掉，核心在 EL2 照樣正常執行，沒有任何錯誤訊息。

降級的理由全部在後面的里程碑：

什麼時候會用到的東西待在 EL2 的話
M3 例外處理VBAR_EL1要改用 VBAR_EL2
M5 開 MMUTTBR0_EL1要改用 TTBR0_EL2
M8 使用者模式EL0 出事自動跳到 EL1要額外設定才跳得到 EL2

而課本、Linux 原始碼、以及本專案參考的所有資料，走的都是 EL1 這條路。待在 EL2 會處處對不上。

還有一個更直接的理由：兩個平台給的起點不一樣。不統一的話，M3 之後每一段跟特權等級有關的程式碼都要寫兩個版本。

這個決定違反了專案自己的規則

本專案的原則之一是「只寫現在就有作用的東西，判準是拿掉它現在會壞嗎」。而這段降級程式碼拿掉不會壞——嚴格講它應該推遲到 M3，因為那才是「我在哪一層」第一次真的產生差別的時間點（要設 VBAR_EL1）。

還是現在做的理由是 M1 的定位：這個里程碑的主題就是「把機器整理成一個乾淨的已知狀態，再交給 C 語言」。設堆疊指標、清 BSS 都是這件事，「現在在哪一層」同樣是那個狀態的一部分。若留到 M3，M1 交給 C 的會是一個「視平台而異」的狀態，跟這個里程碑的目的相違；而且屆時這段程式碼還要回頭改寫。

代價要記下來：多了十幾行今天不做也不會壞的程式碼；而且從此綁定了「核心跑在 EL1」這個前提。日後若要做 hypervisor（自己跑在 EL2、管理底下的客戶 OS），這個決定要整個推翻。目前的規劃裡沒有這件事。

5降級是怎麼做到的

ARM 沒有「降低特權等級」這條指令。往上是硬體自動的（發生例外時），往下只能靠軟體自己走。

唯一的辦法是借用 eret——它本來的用途是「例外處理完了，回到原本的地方」。既然「回去」的時候可以指定要回到哪一層，那就假裝自己剛處理完例外，把目的地填成 EL1，然後按下去。

那些數值是怎麼來的

HCR_EL2 的 bit 31（RW）決定 EL1 用 64 位元還是 32 位元。實測這台機器上 HCR_EL2 開機時是 0x0，也就是 RW = 0 → EL1 是 32 位元。

不設它會怎樣？直覺上會猜「A64 指令被當成 A32 解讀，整個亂掉」。實測不是這樣。

eret 之前   EL = 2
eret 之後   pc = 0x40000020（el1_entry）   EL = 2   PSTATE.IL = 1
再一步      pc = 0x200

（SPSR_EL2.M[4] 是我們填的 0x3c5 裡的 bit 4，它也在講「降下去之後用 64 還是 32 位元」——整張位元圖在下一段。）

HCR_EL2.RW = 0（EL1 是 32 位元）跟 SPSR_EL2.M[4] = 0（要求 64 位元）互相矛盾，這叫 illegal exception return（非法的例外返回）。硬體的處理方式是：不換層、把 PSTATE 的 IL 位元（bit 20，Illegal Execution state）設起來，然後下一次取指令就直接 trap 到例外向量。

所以症狀跟「忘記先判斷 EL」很像（都是 pc = 0x200、sp = 0x0），但成因完全不同：一個是在 EL1 誤碰 EL2 暫存器，一個是 eret 的兩個設定打架。A64 指令從頭到尾沒有被當成 A32 執行過。

SPSR_EL2 填 0x3c5，拆開來看：

欄位值意思
M[3:0]（bits[3:0]）0101EL1h。M[3:2] = 01 是 EL 編號 → EL1；M[1] 保留為 0；M[0] = 1 是 SPSel → 用自己的 SP_EL1。跟 CurrentEL 一樣，EL 編號都放在 bits[3:2]
M[4]（bit 4）0降下去之後用 AArch64（64 位元）。這一位和 HCR_EL2.RW 講的是同一件事，兩邊都要對
D A I F（bits[9:6]）1111四種中斷全部遮起來。D=Debug、A=SError、I=IRQ、F=FIQ

注意 DAIF 這個欄位跨在半位元組（4 bit）的分界上——bit9、bit8 屬於左邊那組，bit7、bit6 屬於中間那組。所以看 0x3c5 的十六進位寫法反而不容易對出來，要照上面的 bit 編號一格一格數。

這個數字不是查表查來的，是抄 QEMU 自己的答案：M0 量過，QEMU 直接從 EL1 進入時 $cpsr 的低 12 位就是 0x3c5。我們只是把那個狀態手動複製一份。

全名遮起來的原因
DDebug 除錯例外例外向量表要到 M3 才有。現在放中斷進來，CPU 會跳到一個空位址，而且因為沒有例外處理器，連錯誤訊息都不會有。先關起來，等有人接得住再開。
ASError 非同步錯誤
IIRQ 一般中斷
FFIQ 快速中斷

EL1h 和 EL1t 差在哪

每一層都有自己的堆疊指標。但 EL1 可以選要用自己的 SP_EL1，還是借用 SP_EL0：

寫法bits[3:0]用哪支堆疊指標
EL1h（h = handler）0101SP_EL1 ← 我們要這個
EL1t（t = thread）0100SP_EL0

只差最低那一個 bit。 填錯的話下一步設的堆疊指標會設到「沒人在用的那一支」，一呼叫函式就死，而且症狀完全看不出原因。

為什麼要先問「我在哪一層」

因為 QEMU 一般開機直接就是 EL1，而 _EL2 結尾的暫存器在 EL1 根本讀不到。不問就做，在 QEMU 上會當場觸發例外。

「無聲當機」聽起來像形容詞，但它有具體的位址。實測把那三行判斷刪掉之後：

p/x $pc   →  0x200      不是我們的程式碼
p/x $sp   →  0x0        連 mov sp, x9 都還沒跑到
p ($cpsr >> 2) & 3  →  1  層級沒變過

0x200 不是隨機的。例外向量表的基底位址存在 VBAR_EL1，重置後是 0；而「同一層、同步例外」的入口在基底 + 0x200。CPU 是規規矩矩地跳去處理例外了——只是那裡放的是 QEMU 的 device tree（見第 2 節），不是向量表，因為向量表要到 M3 才建。

從 el1_entry 開始的部分自成一個主題——「怎麼把機器交給 C」——第 7、8 節專門講。這一節後面只補完前半段的細節。

adr 是什麼指令

adr x9, el1_entry 的意思是「把 el1_entry 這個標籤的位址放進 x9」——不是去那個位址讀值，是取位址本身。

它跟另外兩個很像的寫法差在這裡：

寫法做什麼範圍
adr x9, label取位址。用「現在的 PC 加一個位移」算出來±1 MB
ldr x9, =label取位址。組譯器把那個數字存在附近的字面池（literal pool），再讀出來值不限，但字面池本身要在 ±1 MB 內
ldr x9, [x10]去 x10 指的位址讀一個值—

字面池就是組譯器在你的程式碼旁邊挖的一小塊地方，專門存放塞不進指令的常數。make dump 看得到，它就在 halt_loop 後面：

40000058:  40010100  .word  0x40010100     ← __stack_top，ldr = 就是去讀這裡

adr 的好處是它不需要字面池——位移直接編碼在指令裡。把連結基底從 0x40000000 改成 0x50000000 重連一次，兩者的差別一眼可見：

基底 0x40000000            基底 0x50000000
4000001c: 10000069 adr     5000001c: 10000069 adr   ← 編碼完全相同
40000058: 40010100 .word   50000058: 50010100 .word ← 這個跟著搬家

adr 的機器碼一個位元都沒變，因為它存的是「往前 12 個 byte」；ldr = 的字面則整個換了值。M5 開 MMU 把核心搬到高位址時，這個差別會變得很重要。

objdump 會騙你

上面那行 adr x9, 40000028 印的是絕對位址，很容易以為 adr 算的就是絕對位址。不是。 那是 objdump 幫你把「PC + 12」換算好給你看的，指令本身只有那個 12。要證明它是相對的，得換基底重連一次，不能只看單一次的反組譯。

為什麼 CurrentEL 要跟 4 比

CurrentEL 只有 bits[3:2] 有意義，其他位元永遠是 0。所以整個暫存器讀出來剛好是 EL 編號 × 4：

EL1  →  0b0100  =  0x4
EL2  →  0b1000  =  0x8

為什麼用 x9 / x10，不用 x0

AArch64 的開機協定規定 x0 帶著 device tree 的位址，樹莓派的韌體就是這樣傳的。M0 的 mov x0, xzr 會把它洗掉——在 QEMU 上剛好無害（x0 本來就是 0），但移植到真機就是災難。

所以現在所有暫用都改成 x9／x10，把 x0–x3 原封不動留給後面的里程碑。

7堆疊：誰在寫，寫到哪

到這裡為止全部是組合語言。要交棒給 C，得先給它兩樣東西：一個堆疊，和一塊歸零的記憶體。這一節講第一樣。

先講「堆疊」是什麼

CPU 裡的暫存器（register，可以直接運算的儲存格）只有 31 個。函式一多、變數一多就不夠用，放不下的東西要暫時擺到記憶體去。堆疊（stack）就是專門拿來擺這些東西的一塊記憶體。

它有一個專屬暫存器 SP（stack pointer，堆疊指標）記著「目前用到哪裡」。AArch64 的堆疊往低位址長：要多用一點，就把 SP 減小。

為什麼它非有不可

因為沒人會替你準備。在 Linux 上跑的程式，堆疊是核心在載入時配好的；這裡我們就是那個核心，沒有更下層的人幫忙。重置之後 SP 實測是 0x0——不是「未定義」，是明確的零，而零不是一塊能用的記憶體。

7.1　bl 不動堆疊，它動的是暫存器

bl（branch with link，帶連結的跳躍）是呼叫函式的指令。它做兩件事：跳過去，並且把「回來要接哪裡」寫進 x30 這個暫存器（又叫 LR，link register）。

注意：寫進暫存器，不是寫進堆疊。單步跑一遍就看得到：

--- 停在 enter_c 的 bl，還沒執行 ---
pc  = 0x40000048
sp  = 0x40010100
x30 = 0x0

--- bl 執行完了 ---
pc  = 0x40000094     ← 跳到 kernel_main 了
sp  = 0x40010100     ← 一個 byte 都沒動
x30 = 0x4000004c     ← 回程位址進了暫存器

--- kernel_main 第一條 stp 執行完了 ---
pc  = 0x40000098
sp  = 0x400100f0     ← 這時候才動，而且是被 C 自己動的

所以動堆疊的不是 bl，是被呼叫的函式自己。

7.2　它自己為什麼要動

x30 只有一個。kernel_main 一旦要再呼叫別人，那次 bl 就會把自己的回程位址蓋掉。所以它得先把 x30 存到記憶體——那塊記憶體就是堆疊。

兩個函式的反組譯擺在一起就很清楚。（adrp 是 adr 的大範圍版本——先算出目標所在的那個 4 KB 頁的開頭，再用下一條 add 補上頁內位移，兩條湊成 ±4 GB。這裡它在算 boot_counter 的位址。）

bump（不呼叫別人）kernel_main（會呼叫 bump）
adrp x0, 40000000
add  x0, x0, #0xf0
ldr  x0, [x0]
add  x1, x0, #0x1
...
ret
 
stp  x29, x30, [sp, #-16]!
mov  x29, sp
bl   40000070 <bump>
b    4000009c
整段沒有一個 sp第一條就把 x30 推上堆疊

7.3　但「不呼叫別人就不用堆疊」是錯的

很容易從上面那張表歸納出「葉子函式（leaf function，不再呼叫別人的函式）不用堆疊」。實測是錯的。 本專案沒有加任何 -O 旗標，也就是 -O0（完全不最佳化），在這個設定下：

static unsigned long g;

void leaf_none (void) { g++; }
void leaf_small(void) { volatile unsigned long a=1,b=2; g=a+b; }
void leaf_array(void) { volatile unsigned long v[64]; v[0]=1; g=v[0]; }
void leaf_many (void) { volatile unsigned long a=1,b=2,c=3,d=4,e=5,
                                               f=6,h=7,i=8,j=9,k=10;
                        g=a+b+c+d+e+f+h+i+j+k; }
$ aarch64-linux-gnu-gcc -ffreestanding -nostdlib -c leaf.c -o leaf.o
$ aarch64-linux-gnu-objdump -d leaf.o

<leaf_none>:                                  整段沒有一個 sp
<leaf_small>:  d10043ff  sub  sp, sp, #0x10
<leaf_array>:  d10803ff  sub  sp, sp, #0x200
<leaf_many>:   d10143ff  sub  sp, sp, #0x50

四個都是葉子，三個動了 sp。

這些數字跟著原始碼跑，不要背

leaf_array 那個 0x200 就是 64 × 8 bytes，剛剛好。把 v[0]=1 改成一個 for 迴圈填滿整個陣列，會變成 0x210。

多出來的 16 不是全給了迴圈計數器——實測 i 只佔 4 個 byte（在 [sp, #524]，用的是 32 位元的 str wzr），陣列被推到 sp + 8，其餘是 16-byte 對齊的填補。「多了 16」和「16 是誰用掉的」是兩個問題，只看框架大小回答不了第二個，得去看反組譯裡的 [sp, #...]。

所以照著這份原始碼跑才會得到這些數字。 自己改一改再量，反而更能看出「需要多少記憶體」跟「函式裡寫了什麼」的關係。

真正的規則是：函式只要需要一塊記憶體，就會動堆疊。存 x30 是一種需要，放不進暫存器的區域變數是另一種。「葉子／非葉子」只是其中一個判準，不是全部。

7.4　我在這裡多寫了一個 noinline，然後拿掉了

寫這節的時候我在 bump() 上掛了 __attribute__((noinline))（不准把這個函式展開到呼叫端），理由聽起來很正當：不加的話，-O2 會把 bump 展開進 kernel_main，於是整個函式不再碰堆疊，這個示範就靜靜失效了。那是真的，量得到：

-O2kernel_main 的第一條指令
有 noinlinestp x29, x30, [sp, #-16]! 還是要堆疊
無 noinlineadrp x1, 40000000 展開了，整段不碰 sp

但這個專案沒有加任何 -O 旗標，也就是 -O0。 在 -O0 下加不加 noinline，bump 和 kernel_main 的機器碼一個 byte 都不差。同一支變數 boot_counter 上的 volatile 也一樣，拿掉毫無變化。

本專案的鐵則之一是：拿掉它，現在會壞嗎？不會，就不該現在寫。 兩個都不會，所以兩個都拿掉了。

真到了要開 -O2 的那天，加回去的那個 commit 會自帶一個好理由——這正是 git log 當教材的價值。

7.5　把 mov sp, x9 拿掉會怎樣

這是最值得親手做一次的實驗。刪掉那一行，其他都不動：

停在 kernel_main 第一條指令
SP = 0x0
=> 0x4000008c <kernel_main>:  stp  x29, x30, [sp, #-16]!

（執行這一條）

PC = 0x200                    ← 人不在 kernel_main 了
SP = 0x0
=> 0x200:  adr  x16, 0x60845   ← 這裡根本不是我們的程式
   0x204:  udf  #12336

發生了什麼：SP 是 0，[sp, #-16] 算出來是 0xffff_ffff_ffff_fff0，那裡沒有記憶體 → 資料中止（data abort）。VBAR_EL1 重置後是 0，同層例外的入口在 base + 0x200，所以 CPU 跳到 0x200——那裡放的是 QEMU 的 device tree，不是向量表（第 2 節）。

這正好接回第 2 節實驗 2 的那個 0x200：還沒裝例外處理器的時候，所有錯誤都是無聲的。程式不會告訴你「堆疊沒設」，它只是消失。

7.6　堆疊爆掉也一樣無聲

堆疊只有 64 KB，而且沒有任何東西守著它的底部。把 start.c 換成這一份（放到別的地方編，不要動 repo）：

static unsigned long boot_counter;

static unsigned long deep(unsigned long n)
{
    volatile unsigned long pad[8];   每層吃掉 112 bytes
    pad[0] = n;
    if (n == 0) return 0;
    return pad[0] + deep(n - 1);
}

void kernel_main(void)
{
    boot_counter = deep(100000);     64 KB 只夠約 585 層
    while (1) { }
}

多了一個函式，所有位址都往後移了，所以下面的數字跟前面幾節不是同一個 build：

這一版的配置：
  .text  ：0x40000000 .. 0x4000013f
  堆疊   ：0x40000150 .. 0x40010150（64 KB）

不用 -S，讓它自由跑三秒再接上 gdb：

SP = 0x40000070          ← 已經在堆疊底部「以下」，人在 .text 裡面
PC = 0x200               ← 又是這個死路

再看被踩到的地方——deep 這個函式的第一條指令：

檔案裡原本是：
  40000070 <deep>:  a9b97bfd   stp  x29, x30, [sp, #-112]!

跑三秒後記憶體裡變成：
  0x40000070 <deep>:  .inst 0x400000e0 ; undefined

0x400000e0 是一個回程位址。堆疊長過頭，把自己的程式碼吃掉了，然後 CPU 去執行那個被改寫的位置，於是掉進 0x200。

7.7　這裡為什麼改用 ldr =，不用 adr

第 6 節說 adr 有個好處：搬家也對。但這一段裡三個都寫成 ldr x9, =__stack_top。看起來自相矛盾，實測之後理由很具體。

先確認一件事：今天改成 adr 是編得過的。

_start      = 0x40000000
__stack_top = 0x40010100      差 0x10100 ≈ 64 KB，在 adr 的 ±1 MB 之內

$ 把三個 ldr = 全改成 adr，重新編譯
(exit 0)                      ← 沒事

但把 STACK_SIZE 從 64K 改成 4M，同一份程式碼就爆了：

(.text.boot+0x28): relocation truncated to fit:
    R_AARCH64_ADR_PREL_LO21 against symbol `__stack_top'

ADR_PREL_LO21 就是「PC 相對、21 位元」——21 位元帶正負號正好是 ±1 MB。堆疊放大到 4 MB，位移塞不進那 21 個位元，連結器只好放棄。

「那 ldr = 就沒有距離限制囉？」

也有，而且同樣是 ±1 MB——只是量的東西不一樣。

ldr x9, =0x123456789abcdef0
.space 0x80000    (512 KB)   → 編得過
.space 0x200000   (2 MB)     → Error: pc-relative load offset out of range

ldr = 量的是指令到字面池的距離，而字面池是組譯器放在你程式碼旁邊的，跟著程式碼走；adr 量的是指令到那個符號的距離，符號在哪由連結器腳本決定。

所以真正的判準不是「誰的範圍大」，是「這個距離是誰在控制」：

目標距離由誰決定該用
el1_entry同一個檔案裡隔幾條指令，我自己控制adr
__stack_top連結器腳本，改一個數字就可能飛出去ldr =

會因為改設定而壞掉的寫法，不該用在會被改的東西上。 好消息是它壞得很大聲——編譯直接失敗，不是跑起來才莫名其妙。

8.bss：那些零是誰給的

C 語言有一條保證：沒有寫初始值的全域變數，讀出來一定是 0。

static unsigned long boot_counter;   /* 沒給值 */

在 Linux 上這條保證是核心兌現的。這裡沒有核心——我們就是。所以要自己把它變成真的。

8.1　.bss 是「只記大小，不存內容」的區段

編譯器把所有沒給初始值的全域變數放進一個叫 .bss 的區段（section，執行檔裡的一塊分類區域）。它的型別是 NOBITS，字面意思就是「沒有位元組」——執行檔裡只記著它要多大、放在哪，不存任何內容。

因為零是可以推算的，何必存一堆零進檔案？實測就是這樣：

$ readelf -lS build/kernel.elf

  [ 1] .text     PROGBITS   0x40000000       ← 有內容，檔案裡真的存了
  [ 2] .eh_frame PROGBITS   0x400000a8       ← 有內容（64 bytes，到 0x400000e8）
  [ 3] .bss      NOBITS     0x400000e8       ← 沒內容
  [ 4] .stack    NOBITS     0x40000100       ← 沒內容

  LOAD   FileSiz 0xe8      MemSiz 0x10100
         檔案裡 232 bytes　　記憶體要 65792 bytes
注意：.bss 的區段位址不等於 __bss_start

區段從 0x400000e8 開始，但 __bss_start 是 0x400000f0 —— 差 8 個 byte。那是連結器腳本裡 .bss { } 開頭那個 . = ALIGN(16); 推出來的，清零迴圈永遠不會碰到那 8 個 byte（它從 __bss_start 起跑）。

沒關係，因為那裡不住任何變數。但這是「區段」和「符號」兩件事的好例子：readelf 看區段，nm 看符號，兩者不一定重合。

檔案裡 232 bytes，記憶體要 65792 bytes，差 65560 bytes。拆開來就是 .stack 的 65536、.bss 的 16，再加 8 bytes 的對齊填補（.eh_frame 結束於 0x400000e8，.bss 起於 0x400000f0）——通通是「說好了要有，但沒存」的空間。

順手拆掉一個

連結器腳本有個 NOLOAD 關鍵字，看起來就是幹這件事的，很容易想加在 .bss 上。實測加了跟沒加，產出的映像完全一樣——把符號表 strip 掉之後 md5 相同（20f924b6eb33…）。

原因是 .bss 的輸入區段本來就是 NOBITS，.stack 更是沒有任何內容可載。NOLOAD 在這裡沒有任何事情可做。

（唯一的 6 個 byte 差異是 gcc 暫存 .o 的隨機檔名 ccGWRvg.o vs cc3aNwQx.o，跟 NOLOAD 無關。差點就把它當成證據了。）

8.2　清零迴圈逐行

    ldr     x9,  =__bss_start       從哪開始
    ldr     x10, =__bss_end         到哪結束
bss_zero:
    cmp     x9, x10                 到了嗎？
    b.hs    enter_c                 到了就走
    stp     xzr, xzr, [x9], #16     寫 16 個 0，指標往前 16
    b       bss_zero

xzr 是零暫存器（zero register）——讀它永遠得到 0。stp 是 store pair，一次存兩個 64 位元暫存器，也就是一圈清 16 bytes。

後綴的 #16：post-index

[x9], #16 和 [x9, #16]! 長得像，動作順序相反。實測（兩個都從 0x1000 出發）：

寫法順序寫到哪結束時暫存器
stp xzr, xzr, [x9], #16
post-index（後遞增）		先寫，再加0x1000x9 = 0x1010
stp xzr, xzr, [x10, #-16]!
pre-index（前遞減）		先減，再寫0xff0x10 = 0xff0

清 .bss 是由低往高掃，所以要 post-index：第一圈就得寫在 __bss_start 本身，不能先跳過。

而 kernel_main 的 stp x29, x30, [sp, #-16]! 是 pre-index：堆疊往低長，SP 現在指的位置是已經用掉的，必須先退再寫。同一個指令，兩種用途，差一個驚嘆號。

b.hs：位址比大小要用無號

b.hs（higher or same）是無號比較，跟它對應的有號版本是 b.ge。今天兩個都對，因為位址是 0x4000_xxxx，最高位元是 0，有號無號沒差。

但 M5 開了 MMU 之後核心會搬到 0xffff_...，最高位元變成 1。同一組比較，兩種判斷給出相反答案：

x11 = 0xffff000000000000      （M5 之後的核心位址長這樣）
x12 = 0x1000

無號 hs 判斷 x11 >= x12  →  1   ✅ 對，它是個超大的位址
有號 ge 判斷 x11 >= x12  →  0   ❌ 錯，被當成負數了

位址沒有負數。比位址一律用無號，這不是為了將來，是本來就該這樣。

8.3　兩個 ALIGN(16)，和一個更兇的坑

連結器腳本裡的 .bss 長這樣，四行裡有三行值得解釋：

.bss : {
    . = ALIGN(16);
    __bss_start = .;        ← 符號在大括號「裡面」，這很重要
    *(.bss .bss.*)
    *(COMMON)
    . = ALIGN(16);
    __bss_end = .;
}

對齊：不然最後一圈會寫出界

迴圈一次寫 16 bytes，所以區域大小必須是 16 的倍數。要重現「不是倍數」的情況有個陷阱：1 byte 的變數必須放在另一個 .c 檔。放在 start.c 裡的話，gcc 自己就會把那個 .o 的 .bss 補到 16，大小根本變不成奇數，實驗會安靜地失效。

用的 extra.c 長這樣（位址會跟著這個檔的內容變，所以要照抄才對得上）：

static unsigned char odd_byte;
unsigned char peek(void);
unsigned char peek(void) { return odd_byte; }

再把 .bss 後面那個 ALIGN(16) 拿掉：

__bss_start__bss_end區域大小
有 ALIGN(16)0x400001100x4000012016 ✅
沒有0x400001100x400001199 ❌

大小 9 的話：迴圈看到 0x110 < 0x119 就寫下去，一寫就是 0x110–0x11f——界外 7 個 byte。開機前在界外的 0x4000011c 放一個標記：

開機前 0x4000011c = 0xa5a5a5a5
清零後 0x4000011c = 0x0             ← 被抹掉了

更兇的：符號寫在大括號外面

這個坑是原本沒發現的。__bss_start = .; 寫在 .bss { } 外面也編得過，看起來一樣：

__bss_start = .;        在外面
.bss : { ... }
__bss_end = .;

問題是 orphan section（孤兒區段）——腳本裡沒提到、由 ld 自己決定放哪的區段。.eh_frame 就是一個（gcc 為了例外處理自動產生的，我們用不到，但它在）。ld 會把它塞進符號和 .bss 之間：

__bss_start = 0x400000a4      ← 落到 .eh_frame 前面去了
.eh_frame   = 0x400000a8      64 bytes

開機前 0x400000a8 = 0x10
清零後 0x400000a8 = 0x0       ← .eh_frame 被整段抹掉

把符號移進大括號裡面，__bss_start 就只能是 .bss 的開頭，ld 沒有地方可以塞東西進來。所有位址完全不變（0x400000f0 / 0x40000100 / 0x40010100），但不再靠運氣。

為什麼這個比界外 7 bytes 嚴重

界外 7 bytes 抹掉的是堆疊的空白區；orphan section 被抹掉的是一整個有內容的區段。而且今天之所以沒事，純粹是因為前面那個 ALIGN(16) 剛好把 __bss_start 推過了 .eh_frame——一個為了對齊而寫的東西，意外擋住了一個完全不相干的問題。這種「靠巧合正確」的程式碼，會在某天加了一個新區段之後突然壞掉。

8.4　證明它真的有清（一個會失敗的實驗）

光看 boot_counter 是 0 不算證據——它本來就可能是 0。要先把它弄髒，實驗才有可能失敗，結果才有意義。

QEMU 的 -device loader 可以在開機前直接往記憶體寫值：

-device loader,addr=0x400000f0,data=0xcafe1234,data-len=4
怎麼弄髒開機前進 kernel_main 時
正式版（有清零迴圈）-device loader0xcafe12340x0 ✅
把迴圈整段刪掉GDB（見下面）0xdeadbeefcafe12340xdeadbeefcafe1234 ❌

（兩列用的是不同工具，因為 -device loader 一次寫不了 8 個 byte——原因見下面那個坑。換成同一個工具結果也一樣，我兩種組合都跑過。）

兩邊答案不同，這才叫證明。

踩到的坑：data-len 最多只能填 7

直覺會寫 data-len=8（一個 64 位元的值）。QEMU 6.2 直接 assert 掛掉：

generic_loader_reset: Assertion `s->data_len < sizeof(s->data)' failed.
Aborted (core dumped)

s->data 是 uint64_t，sizeof 是 8，而比較寫的是嚴格小於，所以上限是 7。看起來像 QEMU 的手滑。data-len=4 完全正常，寫 4 個 byte 就夠當髒值了。

要一次弄髒 8 個 byte 的話，改用 GDB：set *(unsigned long *)0x400000f0 = 0xdeadbeefcafe1234。

10被推翻的直覺

直覺 1

「QEMU 加上 -smp 4，四顆核心就會一起衝進來，所以要寫程式篩選 core 0」

錯。實測 -smp 4 讓它自由跑三秒之後：

* 1  (CPU#0 [running]) 0x400000a0 in kernel_main ()   ← 只有這顆跑了
  2  (CPU#1 [halted ]) 0x40000000 in _start ()
  3  (CPU#2 [halted ]) 0x40000000 in _start ()
  4  (CPU#3 [halted ]) 0x40000000 in _start ()        ← 一條指令都沒執行

QEMU 的 virt 機器不會在開機時放出副核心。它們被關在「電源關閉」狀態，要等軟體用 PSCI（Power State Coordination Interface，電源狀態協調介面）主動叫醒才會動。

所以核心篩選的程式碼在 QEMU 上根本不會被執行到，寫了也驗不了。這件事整包留到 M9 移植樹莓派時再做——那時四顆核心才是真的一起進來。

直覺 2

「跑在 EL2 權限比較高，應該什麼都能做，那待著就好」

權限確實比較高，而且今天真的照樣跑。但「權限高」不等於「方便」——每一層有自己一整套暫存器，EL2 那一套跟所有教材、Linux 原始碼用的都不一樣。

更關鍵的是 M8：使用者程式跑在 EL0，出事時硬體預設把它送到 EL1。核心在 EL2 的話，這條最基本的路要額外設定才走得通。

直覺 3

「pkill -f qemu-system-aarch64 可以安全地清掉殘留的 QEMU」

這條指令會把執行它的那個 shell 自己也殺掉。因為 -f 比對的是完整命令列，而執行這條指令的 shell，其命令列裡就含有 qemu-system-aarch64 這串字。

症狀是指令沒有輸出、然後行程被 SIGTERM 收掉，離開碼 143（128 + 訊號 15）。

但這只在特定情境下會發生，實測分成兩種：

誰執行這條指令它自己的命令列結果
互動式終端機直接敲-bash，不含目標字串不會死
Makefile recipe、bash -c '...'、CI 腳本含目標字串自殺

pgrep -f 有同樣的問題。那改成 -x（比對行程名而非命令列）呢？會遇到第二個坑：

$ ps -eo pid,comm | grep qemu
   5132 qemu-system-aar          ← 名字被截斷了

$ pgrep -x qemu-system-aarch64   （無輸出，找不到）
$ pgrep -x qemu-system-aar
5132

Linux 的行程名（comm）上限是 15 個字元，而 qemu-system-aarch64 有 19 個。-x 要求完全相同，所以拿全名去比永遠比不到——而且不會有任何錯誤訊息，只是安靜地什麼都沒殺到。

正確寫法：pkill -x qemu-system-aar（截斷後的名字），或用 ss -ltnp 從佔用的 port 反查 PID 再精確 kill。

直覺 4

「呼叫任何 C 函式都會往堆疊寫東西」

錯。bl 把回程位址寫進 x30 這個暫存器，堆疊一個 byte 都沒動：

bl 之前   sp = 0x40010100   x30 = 0x0
bl 之後   sp = 0x40010100   x30 = 0x4000004c   ← sp 沒變

動堆疊的是被呼叫的函式自己。這件事我原本寫錯在註解裡，是實際單步跑出來才發現的。

直覺 5

「那反過來說，不呼叫別人的葉子函式就不會用到堆疊」

也錯，而且是我在修上一條時順手寫下的第二個錯。本專案沒加 -O，也就是 -O0，實測：

leaf_small （兩個區域變數）  sub sp, sp, #0x10
leaf_array （64 元素陣列）   sub sp, sp, #0x200
leaf_many  （十個區域變數）  sub sp, sp, #0x50

三個都是葉子，三個都動 sp。真正的規則是「函式需不需要一塊記憶體」——存 x30 只是其中一種需要。

這兩條連在一起的教訓：推翻一個錯誤直覺的時候，最容易立刻建立第二個。

直覺 6

「加 noinline 和 volatile 是為了保護這個示範，該留著」

理由本身是對的——-O2 確實會把 bump 展開掉，示範會靜靜失效。但本專案沒有加任何 -O 旗標，在 -O0 下：

有 noinline  vs  無 noinline   → 指令完全相同
有 volatile  vs  無 volatile   → 指令完全相同

「拿掉它現在會壞嗎？」不會。兩個都拿掉了。「以後可能用得到」不是現在加它的理由——等真的開 -O2，那個 commit 自帶一個好理由。

直覺 7

「NOLOAD 是讓 .bss 不佔檔案空間的關鍵字，該加」

實測加了沒加，strip 之後的映像 md5 一模一樣。.bss 的輸入區段本來就是 NOBITS，.stack 更沒有內容可載。

差點被自己騙：不 strip 直接比 md5 會看到 6 個 byte 不同，看起來像「有差」。追下去才發現那是 gcc 暫存 .o 的隨機檔名（ccGWRvg.o vs cc3aNwQx.o）。比對前先想清楚「這個差異有沒有可能不是我改的東西造成的」。

直覺 8

「把堆疊放在 .bss 外面，是為了避免清零迴圈踩到它」

這個理由聽起來很合理，但站不住。實際把堆疊搬進 .bss 裡面試了——照樣跑。因為 boot.S 是先設 SP、再清 .bss，而清零迴圈本身完全不用堆疊，那時也還沒有任何東西被推上去。

真正的理由只是效率：迴圈少走 64 KB。這是一個「理由是對的，但我把它說成了正確性問題」的例子。

直覺 9

「QEMU 的 -device loader 寫不進記憶體，弄髒 .bss 只能靠 GDB」

可以寫，是我參數給錯。data-len=8 會讓 QEMU 6.2 直接 assert 掛掉：

generic_loader_reset: Assertion `s->data_len < sizeof(s->data)' failed.

s->data 是 uint64_t，比較寫的是嚴格小於，所以 上限是 7。data-len=4 完全正常。

工具掛掉不代表做不到——先看它為什麼掛。

直覺 10

「gdb 讀不到 HCR_EL2 這類系統暫存器，要自己寫一段 mrs 才看得到」

這是我寫在教材裡的話，而且是錯的。p/x $HCR_EL2 直接就有答案。我當初打的是小寫 $hcr_el2，回 void，就下結論說「讀不到」。

$hcr_el2  → void      $HCR_EL2 → 0x80000000
$VBAR_EL1 → void      $VBAR    → 0x0

而且我修正的時候又漏了第三種：用 -M virt 開機時 $HCR_EL2 也回 void，因為那台機器沒有 EL2——實測暫存器清單從 411 顆掉到 383 顆。

連這句話都還不夠準。差額 28 是淨值：少了 29 顆 EL2 控制暫存器，卻多了一顆 RVBAR_EL1（QEMU 只在最高的那一層暴露 RVBAR）。而且 -M virt 下仍有 ACTLR_EL2 等四顆名字帶 _EL2 的暫存器讀得到。「淨增減」和「哪些東西進出」是兩個問題，減法只回答得了前者。

真的沒有的只有 $CurrentEL 一顆。回 void 有三種完全不同的原因：名字打錯、後綴給錯、或這台機器沒有那一層。maint print remote-registers 一查就知道是哪一種。

直覺 11

「ldr x9, =label 沒有距離限制，adr 才有 ±1 MB」

兩個都有 ±1 MB，只是量的東西不同：

ldr x9, =0x123456789abcdef0
.space 0x200000   → Error: pc-relative load offset out of range

adr 量「指令到符號」，ldr = 量「指令到字面池」。字面池跟著程式碼走，符號由連結器決定——差別在誰控制那個距離，不在誰的範圍大。

直覺 12

「__bss_start = .; 寫在 .bss { } 大括號外面或裡面都一樣」

寫外面，ld 可以把 orphan section 塞進符號和 .bss 之間。實測 .eh_frame 就落在那裡，開機時被清零迴圈整段抹掉。

今天沒事是因為前面那個 ALIGN(16) 剛好把 __bss_start 推過了 .eh_frame——一個為了對齊寫的東西意外擋住了不相干的問題。移進大括號裡面，位址一個都沒變，但 ld 再也沒地方塞東西。

11精髓

  1. 權力往上是自動的，往下要自己走。 硬體只在出事時把你抬上去，從來不會主動把你放下來。降級是軟體的責任，而且要借用「返回」這個機制來完成。
  2. 先問狀態，再動作。 同一份程式碼要能在兩種平台跑，唯一的辦法是先問「我現在是什麼情況」。不問就做，在其中一種平台上必然出事。
  3. 沒有例外處理器的時候，所有錯誤都是無聲的。 這也是 DAIF 要先全遮的原因——不是因為中斷有害，是因為現在沒有人接得住。三種完全不同的錯（碰錯層的暫存器、堆疊沒設、堆疊爆掉）最後都落在同一個 0x200。
  4. C 的「保證」都是有人在兌現的。 有堆疊可用、全域變數是 0——這兩件事在 Linux 上是核心做的。這裡沒有核心，所以要自己補上這 12 行組合語言。語言的保證不是憑空的，是某一層軟體在維持的。
  5. 會失敗的實驗才叫實驗。 看到 boot_counter == 0 不能證明清零有效，因為它本來就可能是 0。先弄髒，答案才有兩種可能，結果才有意義。

三個暫存器

HCR_EL2到了 EL1 要守什麼規矩bit31 = 1 → 64 位元
SPSR_EL2回去之後是誰0x3c5 → EL1h + DAIF 遮
ELR_EL2回去之後從哪跑el1_entry

關鍵數值

CurrentEL = EL 編號 × 4      EL1 → 0x4    EL2 → 0x8
SPSR bits[3:0]               0101 = EL1h  0100 = EL1t
SPSR bits[9:6]               1111 = DAIF 全遮
HCR_EL2 bit31 (RW)           1 = EL1 用 AArch64

兩種開機方式

qemu-system-aarch64 -M virt ...                     進來就 EL1
qemu-system-aarch64 -M virt,virtualization=on ...   進來是 EL2

交棒給 C 的三件事

層級降到 EL1eret
堆疊SP = __stack_top不設的話 SP = 0，第一次 push 就死
零把 .bss 掃成 0不清的話全域變數是開機殘值

指令與符號

bl label            跳過去，回程位址寫進 x30（不動堆疊）
stp a, b, [x9], #16 先寫 x9，x9 再 +16   post-index（清 .bss 用）
stp a, b, [sp,#-16]! sp 先 -16，再寫      pre-index（push 用）
xzr                 零暫存器，讀出來永遠是 0
b.hs / b.cs         無號的「大於等於」，比位址要用這個
adr  x9, label      PC 相對，範圍只有 ±1 MB
ldr  x9, =label     經字面池取位址，字面池也要在 ±1 MB 內
                    （連結器決定位置的符號用這個）
